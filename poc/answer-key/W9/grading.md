## 指摘と正解の突き合わせ（同じ不具合とみなす基準）

`REVIEW.md` の指摘を 1 件ずつに分け（見出し・箇条書きの 1 項目を 1 件とする。1 項目に別々の問題が 2 つ以上書かれていれば分ける）、それぞれを次のどれか 1 つに分類する。

| 分類 | 条件 |
|---|---|
| `B1`〜`B10` に一致 | 次の 2 つを両方満たす。(1) **場所**: 正解の場所（ファイルと関数・ルート）を指している。(2) **仕組み**: 正解の「不具合」の欄の核心（下の表）を述べている。場所だけ合っていて別の問題を述べているもの、一般論（「入力検証を強化すべき」だけ）は一致にしない |
| 正解外の妥当な指摘 | 正解リストに無いが、実際に存在する問題（バグ・規約違反・保守性の明確な問題）を正しく述べている |
| 誤った指摘 | 存在しない問題、事実と違う説明、おとり（D1〜D5）を問題とする指摘 |
| 対象外 | 好みの問題・言い回し・「確認した方がよい」程度の提案・差分の外の既存コードへの一般的な感想・問題なしの確認。適合率の計算に入れない |

| 番号 | 一致とみなす核心（どれか 1 つを述べていれば可） |
|---|---|
| B1 | 作成者が null（記録なし・既存のタスク）のとき権限の確認が素通りになり、誰でも削除できる |
| B2 | 検索語を SQL に直接埋め込んでいる（インジェクション、`'` で SQL が壊れる、プレースホルダを使っていない） |
| B3 | 1 始まりの `page` に対して `OFFSET` が 1 ページ分ずれている（1 ページ目が飛ばされる） |
| B4 | `limit` の範囲（上限 50・下限 1・数値でない値）を検証していない |
| B5 | 版番号の確認と更新が不可分でなく、同時の更新で変更が失われる（`UPDATE` に版番号の条件が無い、`await` をまたいだ確認） |
| B6 | 一括更新で、存在しない ID があっても途中までの更新が残る（トランザクション・原子性が無い） |
| B7 | 検索の例外を握りつぶして 200 と空の結果を返している |
| B8 | 「今日」を UTC で求めていて、日本時間の日付とずれる |
| B9 | `deleteTask` のテストが削除の結果を確かめていない（常に通る比較） |
| B10 | 既存のマイグレーションを書き換えている（新しい番号で追加すべき、既存の DB に列が足されない） |

- 同じ不具合に一致する指摘が複数あれば、不具合としては 1 件と数える（再現率）。重複した指摘は「正しい指摘」として適合率に数えるが、具体性は最も良い 1 件で付ける。
- 1 つの指摘が 2 つの不具合の核心を両方述べていれば、両方に一致したとする（例: 「検索の catch が SQL インジェクションのエラーも隠す」は B2 と B7 の核心を両方述べていれば両方）。
- 重要度の付け方は点数に入れない（レポートに記録する）。

### 具体性（一致した不具合ごとに 0〜2 点）

| 点 | 条件 |
|---|---|
| 2 | 直し方が示されていて、正解の「正しい直し方」と同じ効果がある（不具合を解消し、新しい問題を生まない）。コード例でも文章でもよい |
| 1 | 直し方が無い、曖昧（「検証を追加する」だけ）、または直し方が誤っている・不十分（例: B2 で `'` だけを置き換える、B8 で `getTimezoneOffset()` を使いサーバーの時差に依存する） |
| 0 | 一致していない |
