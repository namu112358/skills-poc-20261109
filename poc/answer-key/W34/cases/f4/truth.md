# F4 の正解（時間がたつと落ちるテスト・flaky なテスト）

本体（`src/lib/summary.ts`・API）に不具合は無い。`summarizeTasks` は時刻（`now`）を引数で受け取れる。正解はテストの問題だけ。

| ID | 種類 | 場所 | 仕組み（核心） | 正しい直し方 |
|---|---|---|---|---|
| T1 | 今日の日付に依存 | `tests/summary.test.ts` の "summarizes the seed data" | 本物の現在時刻で集計し、今日の件数（今日が期限 1・期限が近い 2）を決め打ちしている。日がたつと件数が変わって落ちる（今日は通るが、明日以降に落ちる） | `summarizeTasks(db, 固定の時刻)` で時刻を渡し、その時刻を基準にした件数を確かめる |
| T2 | 時間帯で落ちる（UTC と日本時間の取り違え） | `tests/summary.test.ts` の "counts a new task that is due today"（`new Date().toISOString().slice(0, 10)`） | 「今日」を UTC の日付で作っているが、集計は日本時間で数えるため、日本時間の 0 時〜9 時は前日の日付になり落ちる | 固定の時刻を渡し、日本時間の日付で期限を作る |
| T3 | 初期データの件数に依存 | 同じテストの `total` が 7・8 | 初期データ（seed）を足すと落ちる。確かめたいことは件数そのものではない | 足したタスクの分だけ増えたか（前後の差）で確かめる、または専用のデータで確かめる |
| T4 | 処理時間に依存（flaky） | "is fast enough for the dashboard"（300 ms 以内） | 計測に DB の準備も含み、普段は約 120 ms だが、負荷が高いと 300 ms を超えて落ちる。単体テストで速さを確かめる意味が薄い | このテストを外す（性能は別の測り方にする） |
| T5 | 文言に依存 | `parseSoonDays` のテストの `{ ok: false, error: "日数は 1〜90 の整数で指定してください" }` | エラーの文言を丸ごと比べているので、文言を直すだけで落ちる。確かめたいのは拒むこと | `ok: false` であることを確かめる（文言は比べない） |

- 一致の基準: 場所（テストの名前）と問題の核心（何に依存して、いつ落ちるか）を述べていれば一致。
- T4 を「消す」・T5 で「文言を比べない」のは、確かめたいこと（受入条件）に関わらない比べ方をやめることで、アサーションの緩和ではない。一方、期限の件数や拒むことの確認まで消すのは弱めすぎ（変異で測る）。
- 直した後の採点は、`mutants.json` の f4_perturbations（時計を進める・日本時間の朝・初期データを足す・文言を変える・負荷）でテストが落ちる数（少ないほど良い）と、変異（f4。本体の 6 つの改変を落とせるか。多いほど良い）で行う。
