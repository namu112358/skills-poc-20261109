### 計算方法と判断の記録

- 品質 = （再現率 40 + 適合率 25 + 具体性 20）の得点 ÷ 85 × 100。

## 所見

- 再現率・適合率は全 9 試行が満点でした。2 名の判定者は、全試行・全不具合で一致の判定が食い違いませんでした。差が付いたのは具体性の 1 点だけです（Compound Engineering #2 と Feature Dev #2 の空のテスト（B9）、gstack #1 のマイグレーション（B10。「番号 2 を追加」と書き、既存のマイグレーション 2 とぶつかる））。
- 正解リストに無い妥当な指摘も、どの試行も出していました。主なものは、`version` の型を検証していない（文字列などが 400 でなく 409 になる）、LIKE のワイルドカード（`%`・`_`）をエスケープしていない、入力の検証をルートに直接書いている（規約 9）、の 3 つです。指摘の件数は 11〜20 件（判定者の数え方で差があります）でした。
- 各ツールの手順は、どれも一部を省いていました。gstack（#1・#2）は `/review` の準備（`gstack-skill-start`）を実行しましたが、専門レビュアーの並列起動と敵対的レビューは「差分が小さい」として起動しませんでした。Compound Engineering #1 は範囲を測るスクリプト（`review-scope.py`）が許可リストの外で実行できず、サブエージェント 1 名で済ませました。#2 は正しさ・セキュリティ・敵対的・規約とテストの 4 名を並列に起動しましたが、外部モデルによるレビュー（codex などが無い）と、データ移行・API 契約の専門レビュアーは起動していません。
- Superpowers（#1・#2）は `requesting-code-review` の手順どおり、レビュー用のテンプレート（`code-reviewer.md`）を読んでサブエージェントにレビューさせ、その指摘を自分で差分と照らして確かめました。#2 では、読み取りだけのはずのサブエージェントが `git checkout --detach` を実行し、親がブランチを戻しました（成果に影響なし）。Feature Dev（#1・#2）は `feature-dev:code-reviewer` を 1 回起動しました。エージェントは Bash を使えなかったため、親が行番号を確かめて直しています。
- 実際に動かして不具合を確かめたのは gstack #2 だけでした（自分のスクラッチ領域にテストを書き、検索の SQL インジェクション・ページのずれ・limit=-1・一括変更の途中更新を再現）。Superpowers #1・#2 も同じことを試みましたが、許可リストの外のコマンド（`node` での実行）が拒否されました。ほかの試行はコードを読んで判断しています。正解率には差が出ていないので、この課題では実行による確認は結果を変えませんでした。
- 費用はツールの手順の重さの順になりました。baseline $0.18、Feature Dev $0.32〜0.39、gstack $0.38〜0.50、Superpowers $0.40〜0.44、Compound Engineering $0.52〜1.18。時間は 1.0〜3.0 分で、どの試行も介入は 0 回、上限での打ち切りもありませんでした。全試行が REVIEW.md だけをコミットし、コードは変えていません。
- `grade.py` の `skills_used` は、スラッシュコマンドで起動した Skill を数えないため、全試行で空です。上の手順の踏み方は、トランスクリプトのツール呼び出し（参照ファイルの読み込み、gstack の bin の呼び出し、サブエージェントの種類）から確かめました。

## 採点方法

配点は PLAN.md §5.1 の W9、手順は試行前に固定した `poc/answer-key/W9/grading.md` のとおり（`poc/scripts/grade_w9.py` → `blind_w9.py` → `score_w9.py`）。2 本立ての点数は PLAN.md §4.4（`poc/scripts/two_axis.py`）。


- <strong>再現率（40）</strong>: 40 × 一致した不具合の数 / 10。一致は「場所」と「仕組みの核心」の両方が合うもの（grading.md の表）。
- <strong>適合率（25）</strong>: 25 × 正しい指摘 /（正しい指摘 + 誤った指摘）。正しい指摘は不具合への一致と正解外の妥当な指摘、誤った指摘は存在しない問題・事実と違う説明・おとり（D1〜D5）を問題とするもの。好み・一般論は数えない。
- <strong>具体性（20）</strong>: 一致した不具合ごとに、直し方が正しければ 2、無い・曖昧・誤りなら 1。
- <strong>費用（15）</strong>: 15 ×（W9 の全試行の最安費用 / 自分の費用）。
- 再現率・適合率・具体性は、互いに独立した新しいサブエージェント 2 名が、候補名を伏せた REVIEW.md を順番を変えて判定し、2 名の点数の平均にした（協議なし）。採点は REVIEW.md だけで行い、会話の最後のメッセージは使っていない。
- <strong>2 本立て</strong>: 品質 = 再現率 + 適合率 + 具体性（85 点）を 100 点に正規化。効率 = 費用 50 + 時間 30 + 介入 20（baseline の実額・時間に対する倍率の段階）。

## この結果の制約

- 天井効果: 全試行が 10 件すべてを見つけ、誤った指摘も 0 件だったため、再現率・適合率では候補の差を測れていません。差分が小さく（254 行）、不具合がどれも差分の中のコードを読めば分かるもの（ファイルをまたいだ推論が要らない）だったことが原因と考えます。設計は試行前に固定したので、試行後には変えていません。
- 課題文で「マージ前に直すべき問題を指摘して」と頼んでいるため、不具合があることを前提に読ませています。不具合の無い差分で誤った指摘をどれだけ出すか（おとりだけの差分）は測っていません。
- 具体性の差（20 点中 19 と 20）は 1 か所の書き方の違いで、試行のばらつきの範囲です。
- リモートが無い環境のため、gstack の `/review` の PR 連携、Compound Engineering の外部モデルによるレビュー（codex などの CLI が無い）は評価できていません。
- 子セッションの許可リスト（W6 以降の既定）では、範囲を測るスクリプト（Compound Engineering の `review-scope.py`）や、スクラッチ領域での `node` の実行（Superpowers）が拒否されました。許可されていれば手順をもっと踏んだ可能性があります（比較の条件を揃えるため、試行の途中では変えていません）。
- 前半 5 試行と後半 4 試行は別のコンテナで実行しました（前任からの引き継ぎ）。同じモデル・同じ Claude Code・同じ固定コミットのプラグインで、試行の条件は同じですが、所要時間には環境の差が入り得ます。
- 判定者 2 名はどちらも同じ系統のモデルのサブエージェントです。指摘の分け方（箇条書きの細かさ）で指摘の件数は判定者により変わりましたが、点数には影響していません。

## 判断の記録

- <strong>課題の作り方</strong>: 認可・SQL・境界値・入力検証・競合・エラー処理・時差・空のテスト・マイグレーションの 10 種類を 1 件ずつ仕込み、見た目は怪しいが正しい変更（おとり）を 5 件混ぜた。不具合のうち 5 件は関数を直接呼んで起きることを試行前に確かめた（grading.md の「確認したこと」）。仕込んだ差分（`review.patch`）と正解リストは answer-key 側に置き、試行の作業用コピーには差分を当てたコミットだけを置いた（W5 と同じ方式）。
- <strong>レビュー対象の置き方</strong>: 作業用コピーの `master` から作業ブランチを切り、PR の説明をメッセージにしたコミットを 1 つ積んだ。リモート（origin）は置かない（W1〜W8 と同じ）。gstack の `/review` は `origin/<base>` が無くても `master...HEAD` で差分を取れた。課題文に `git diff master...HEAD` を明記した。
- <strong>入口</strong>: Feature Dev にはレビュー用のコマンドが無いため、「Feature Dev の code-reviewer エージェント（feature-dev:code-reviewer）でこの差分をレビューしてください。」を課題文の前に付けた。ほかの候補は各ツールのレビューの入口に課題文を渡した。
- <strong>費用の上限</strong>: `POC_BUDGET_MODE=watch`（上限を子セッションに見せない。W6 以降の既定で、W9 はシナリオ名で自動的にそうなる）。baseline を暫定 $10 で先に実行し、規模係数 = W9 baseline の実額 $0.1755 ÷ W1 baseline $0.15 = 1.17。上限 = 1.17 × W1 の候補平均 × 5（最大 $10）で、Superpowers $0.99、Feature Dev $1.00、gstack $2.68、Compound Engineering $10（計算値 $10.44）。上限で止まった試行は無い（最大は Compound Engineering #2 の $1.18）。
- <strong>課題文の末尾</strong>: 工程を省かない新文言（W4 以降の既定）。全試行で `task-suffix` = new を確認した。
- <strong>介入</strong>: 全候補で `POC_MAX_NUDGES=2`（W2 以降と同じ）。完了の条件に「REVIEW.md がコミットされていること」を足した。介入は全試行で 0 回。
- <strong>許可リスト</strong>: 変更していない（W9 は W6 以降の許可リストがそのまま効く）。Compound Engineering の範囲スクリプトや Superpowers の `node` 実行が拒否されたが、前半の試行と条件を揃えるため途中では広げなかった。
- <strong>配点</strong>: 総合点 = 再現率 40 + 適合率 25 + 具体性 20 + 費用 15。2 本立ての品質 = 前の 3 つ（85 点）を 100 点に正規化（`two_axis.py` の `QUALITY["W9"]`）。W9・W10 を総合判定にどう入れるかは判定会で決める（PLAN.md §4.3 の注記）。
- <strong>実行順</strong>: baseline → gstack #1 → Superpowers #1 → Compound Engineering #1 → Feature Dev #1 → Feature Dev #2 → Compound Engineering #2 → Superpowers #2 → gstack #2（1 本ずつ、後半は前半の逆順）。
- <strong>引き継ぎ</strong>: 前任のセッションが Feature Dev #2 の開始直後に止めたため、新しいコンテナで Feature Dev #2 を最初からやり直した（止めた分は採点していない）。プラグインは同じ固定コミットを取り直した。
- <strong>main の取り込み</strong>: main の `grade.py`（W4 で認可プローブ用に E2E の実行を関数に分けた版）と W9 の変更（隠しの E2E が無い W では実行しない）がぶつかったため、main の構造を採り、W9 の条件（`acceptance.cjs` が無ければ E2E を実行しない）を載せた。W1〜W8 の動作は変わらない。

## 試行間の独立性の確認結果

`grade.py` の検出（自分の作業用コピーの外への参照）は全 9 試行で 0 件、正解データ（`answer-key`）を読んだ形跡も 0 件でした（検出であり、完全な防止ではありません）。gstack #2 と Superpowers #1・#2 が書いた再現用のファイルは、各子セッション自身のスクラッチ領域の中です。

## 次の対応

- レビュー手段の差を測るには、W9 より難しい差分で再試行する: 差分を 1,000 行規模にする、ファイルをまたいで読まないと分からない不具合（呼び出し元の前提が崩れる、別の画面の権限と食い違うなど）を入れる、PR の説明に書かれた仕様とコードの食い違いを増やす。
- 誤った指摘の出やすさを測るには、不具合の無い差分（おとりだけ）をレビューさせる試行を加える。
- W9 を総合判定にどう入れるか（重みを付け直すか、品質の参考として扱うか）は判定会で決める。今回の結果では、レビューの品質ではどの候補も baseline と差が無く、候補の手順を踏むほど費用と時間が増えた。
