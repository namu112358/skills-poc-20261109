所見

  • 全 10 組・40 段階（W7b〜W7e）で、落とし穴を指摘の前に外した段階は 0 でした。W7a で外したのは 10 組中 4 組で、すべて最初の段階です。
  • 後の段階の落とし穴（日本時間の日付の境目、日本時間の入力、CSV の日本時間）は、試行前の確認で「UTC の日付で絞る」「サーバーの時刻設定に頼って変換する」「UTC の ISO 形式のまま出す」実装が不合格になることを確かめていましたが、試行ではどの組もそう実装しませんでした。課題文の「日付は利用者（日本のチーム）にとっての日付」などの仕様と、既存の datetime.ts（toUtcIso・formatJst）を手がかりに、各段階で日本時間への変換を書いていました。
  • 前の段階の知見を読んだ形跡: Compound Engineering は 2 組とも、W7a の /ce-compound で残した docs/solutions/conventions/new-api-routes-use-withapi-and-apperror.md を W7b 以降の調査で読みました（#21 は W7b〜W7d、#22 は W7b・W7d・W7e）。前の段階の計画書（docs/plans/）も読んでいます。Feature Dev・gstack（と Superpowers #22 の W7e）は、前の段階で自分が更新した CLAUDE.md（API の一覧と、各機能の日時の扱いの説明）を読みました。
  • W7e の対照（5 本）: 品質はすべて 100、効率は Superpowers・baseline 100、Feature Dev 74、gstack 53、Compound Engineering 29。続けて行った W7e（2 組の平均）と比べると、費用は baseline $0.22 / $0.31、Superpowers $0.53 / $0.66、Feature Dev $1.06 / $1.01、Compound Engineering $3.31 / $5.93、gstack $2.61 / $2.09（対照 / 続けて）。Compound Engineering は、続けて行った方が前の段階の計画書・学びを読み込むぶん高くつきました。
  • 候補が CLAUDE.md に書き足したのは API の一覧と「startsAt は日本時間として受け取り UTC で保存」などの機能ごとの説明で、エラー型の決まりを書き足した組はありませんでした。gstack の学習データ（#21 の learnings.jsonl）は gstack 自身の道具の使い方で、プロジェクトの決まりではありません。
  • 費用・時間は段階の課題の大きさで上下し、段階を重ねるほど下がる傾向ははっきりしませんでした。Compound Engineering は W7a（$6.0〜6.3）から W7c（$3.6〜3.7）まで下がりましたが W7d・W7e で $4〜7.7 に戻り、#22 の W7e は上限（$7.67）に達して /ce-work の途中で止めました（止めた時点で実装とコミットは済んでおり、落とし穴 2 件とも回避・受け入れ 8/8）。
  • 介入: 「お任せします」は gstack #21 の W7a・#22 の W7c で各 1 回。ほかの段階は介入なしで終わりました。

採点方法

手順は poc/answer-key/W7/grading.md の「5 段階への延長」（試行前に固定）。試行ごとに poc/scripts/grade_w7.py、組ごとに poc/scripts/score_w7_chain.py で集計した（W7/scores-5stages.json）。

  • 品質（主表示）= W7b〜W7e の各段階の（指摘前に避けた落とし穴 P1・P2 各 25 + 受け入れ 20 × 合格率）/ 70 × 100 の平均。
  • 効率（主表示）= 各段階の費用・時間を、その段階の baseline（2 組の平均）に対する倍率で段階評価（費用 50 + 時間 30 + 介入 20。2 倍以下 = 満点、3 倍以下 = 80%、5 倍以下 = 60%、10 倍以下 = 30%）し、W7b〜W7e で平均。上限で止めた段階の費用は見積額で数える。
  • 総合点（PLAN.md §5.1 の W7 の配点）は 2 段階の組だけに付け、5 段階には付けない。
  • 学習の記録（点数に入れない）: 段階ごとの落とし穴（学習曲線）、繰り返し、前の段階の知見を読んだか（それより前のすべての段階が残したものの名前を、その段階のツール入力が名指ししたか）、W7e の対照との差。

この結果の制約

  • 各候補 2 組・対照 1 回。全組・全段階で品質が満点で、差が出なかったため、記憶の仕組みの効き目の大きさは測れていない。
  • W7a で外した 4 組がその後に繰り返さなかったことは、記憶の仕組みを持たない組（baseline #22・Superpowers #21）でも同じで、記憶の仕組みの寄与とは切り分けられない。
  • 後の段階の課題文には、仕様として「日付は利用者（日本のチーム）にとっての日付」「入力欄には日本の日時」「画面と同じ形」を書いた。これが日時の扱いの手がかりになり、決まりを知らなくても避けられた可能性がある（書かなければ仕様が曖昧になるため、書いた）。
  • 「前の段階の知見を読んだか」は、ツール入力にファイル名が現れたかで数えている。CLAUDE.md は最初からあるファイルを候補が更新したもので、読んだことが前の段階の知見を使ったことを意味するとは限らない。サブエージェントの中で読んだものは数えていない。
  • 回 22 の 4 組（baseline・Superpowers・Feature Dev・Compound Engineering）と gstack #21 の W7e は、使用量の上限で失敗したため、上限のリセット後にやり直した（下の「判断の記録」）。やり直しは同じ日のうちで、モデル・Claude Code・プラグイン・許可リストは同じ。

判断の記録

  • ユーザーの判断（2026-11-09）で、後の段階を「前の段階のコードを手本にできない」課題に変えて W7c〜W7e に延長した。課題・受け入れテスト・参照実装・落とし穴の判定・採点手順は、試行の前に固定した（参照実装で全合格、わざと決まりを破った実装で落とし穴だけ不合格を確認）。

試行間の独立性の確認結果

grade.py の検出で、5 段階の 50 試行と対照 5 本の answer_key_access（正解データを読んだ形跡）は無し。isolation_suspects（作業用コピーの外への参照）は Compound Engineering #21 の W7a・W7d の各 1 件だけで、どちらも作業用コピーの src/lib から ../../tests・../../CONCEPTS.md・../../docs/solutions を見たもの（同じ作業用コピーの中）で、他の試行への参照ではない。W7c 以降が W7a の作業用コピー・HOME を使うのは、自分の組の一部として扱った（引き継ぎの連鎖の ID は他の試行に数えない）。

結論と次の対応

  • 5 段階で言えること: 既存コードに決まりの補助（datetime.ts・errors.ts・withApi）があり、課題文に必要な仕様があれば、記憶の仕組みの有無にかかわらず、4 候補と baseline のすべてが 5 段階を通して同じ決まりを守り続けた。W7a で外しても、その後に繰り返さなかった。続けて行うことで費用・時間が下がる効果ははっきりしなかった。
  • 言えないこと: 記憶の仕組み（Compound Engineering の docs/solutions/、gstack の学習データ）が回避に効いたか。記憶を持たない組も繰り返さず、対照でも避けたため、切り分けられない。
  • 見立て: このアプリ・このモデルでは、決まりが既存コードの補助関数とテストに現れている限り、記憶の仕組みの差は出にくい。記憶の効き目を測るなら、決まりがコードに現れない運用上の約束（例: 監査ログに残す、特定の通知を送る）や、前の段階で指摘を受けたときにしか分からない決まりを課題にする必要がある。費用の差（Compound Engineering は baseline の約 12 倍）に見合う品質の差は、W7 では見られなかった。
  • 上限（$7.67）で止めた Compound Engineering #22 の W7e を上限なしでやり直すかは、ユーザーの判断待ち（止めた時点で品質は満点のため、結論は変わらない見込み）。
