# PoC W11 実在する OSS の解決済み課題 — 結果レポート

> HTML 版: [report.html](report.html)（同じデータから `poc/scripts/report_w11.py` で生成）

実在する OSS（pytest・zod・packaging・click）で、2026 年 7〜11 月に本家が解決した課題 6 件（不具合 3・機能 3）を、解決前の状態から各候補に解かせた。採点は本家の修正で追加されたテスト（隠しテスト）で行った。設計は [wf-W11-design.md](../../../tasks/wf-W11-design.md)。

## 所見

1. **品質ではほぼ差がつかなかった（天井効果）。** 6 課題のうち 4 課題（B1・B2・F2・F3）は、5 条件すべてが本家のテストを満点で通した。実在する OSS の、本家が数十〜数百行で直した課題でも、今回の課題の多くは候補なし（baseline）で解ける水準だった。
2. **差が出たのは zod の 2 課題だけで、その差は候補を入れても縮まらなかった。**
   - B3（非同期の union）: 全員が報告された症状は直したが、本家が同時に直した「待ち合わせの行き詰まり」「await の後で閉じる循環」までは届かず未解決。Feature Dev だけが新しいテスト 8/10 と一段深く直し、ほかは 5/10。
   - F1（循環参照の入力）: baseline だけが解決。4 候補は新しいテストはほぼ満点だったが、そろって同じ既存テスト「チェックは参照 1 つにつき 1 回（循環が無い場合と同じ回数）」を壊した（課題文の仕様に書いてある点）。共有された参照を使い回してチェックまで省いた実装で、計画や設計の工程を足しても、仕様の細かい制約の読み落としは防げなかった。
   - どちらも各条件 1 回だけの試行で、旧環境の B3 では Feature Dev が 10/10 で解決していた。同じ候補でも結果がぶれる範囲の差なので、「どの候補が上」とは言えない。
3. **同じ品質なら、候補なしが最も安く速い。** baseline 比の費用（中央値）は Superpowers 1.8 倍、gstack 2.2 倍、Feature Dev 3.4 倍、Compound Engineering 3.8 倍。時間（中央値）は Feature Dev 1.9 倍、Superpowers 2.0 倍、gstack 2.0 倍、Compound Engineering 2.7 倍。Compound Engineering は機能追加で特に重く（F2 で費用 16 倍、F1 で $12.41・33 分）、F3 では手順を終えても未コミットが残り、介入が 2 回要った。
4. **副次の指標**
   - 候補が書いたテストの行数（6 課題の合計）: Compound Engineering 907、Superpowers 557、gstack 523、Feature Dev 500、baseline 377。テストを多く書いても、本家のテストの通過（品質）には差が出なかった。
   - ソースの変更量は、どの条件も本家の修正（テスト以外のすべての変更。changelog・文書を含む）と同程度か少ない。B3 では全員が本家（94 行）の 1〜2 割で止まっており、変更の小ささが未解決と対応している。
   - 試行の独立性: 外部サイト・依存のインストール・公開版のソースへの参照の形跡は、本採点の 30 試行で 0 件。拒否された操作は全候補に共通の形（`cd … &&` で始まる複合コマンド、許可していない `ruff`、ヒアドキュメントでの追記など）が中心で、候補ごとの差の原因ではない。

## 結果の制約

- **天井効果**: 6 課題中 4 課題が全員満点で、品質の比較にはほとんど使えない。結論は「同じ品質の中での費用・時間」を主な比較軸にした（PLAN.md §4.4 の 2 本立てと同じ考え方）。
- **試行回数**: 各課題 × 各条件 1 回。B3 の旧環境と新環境の結果の違い（Feature Dev が 10/10 → 8/10）のように、1 回ごとのぶれが品質の差と同じくらい大きい。
- **課題の選び方**: 学習時期より後に本家が直したものを選んだが、B2（最小の再現例付き）や F2・F3（API の仕様付き）のように、課題文に必要な情報がそろっていて素直に解けるものが多かった。
- **モデル**: 子セッションは全条件で同じモデル（`run-trial.sh` の既定）。モデルを変えたときの差は見ていない。

## 判断の記録

- **課題の選定と採点方法は試行前に固定した**（`poc/tasks/wf-W11-design.md`、`poc/answer-key/W11/`）。途中で課題を足したり難しくしたりはしていない（コーディネーター指示）。
- **F2（packaging）の採点の補正**: 本家のテストファイルが新しい API を冒頭で import するため、修正前は既存テストも含めて全件が失敗し、F2P が 1182 件に膨らんだ。準備の段階で「修正前のテストファイルのまま実行した結果」と比べ、新しいテスト（54 件）と、import に巻き込まれた既存テストを分けて数えるようにした（品質点は前者を「新しいテスト」、後者を「既存テスト」として計算）。試行の前に行った補正。
- **費用の上限**: 試行の途中（2026-11-09 15:40 UTC）に、ユーザー指示で上限なしに変えた（このセッションからユーザーに直接確認して承認を得た）。それより前に上限 $10 で始めた B1 の 3 試行は上限に達していないので、そのまま採点に使った。
- **zod の課題での nub の代替（許可リストの変更）**: B3 の初期状態の zod は、`CLAUDE.md` でテストやスクリプトを `nub` で実行するよう指示している。ところが nub はこの環境に無く、許可リストにも無かったため、指示どおりに動いた候補だけがテストを実行できなかった（B3 の baseline は `pnpm install` も試みて拒否され、既存テストを 37 件壊した）。候補の差ではなく環境の差になるため、コーディネーターの承認（CLAUDE.md の例外: 作業用コピーの中でしか効かない許可リストの変更）を得て、次のとおりにした。
  - nub の代替（`poc/scripts/oss/nub-shim`）を zod の課題の作業領域にだけ置き、その試行だけ `PATH` と許可リスト（`Bash(nub:*)`・`Bash(timeout * nub*)`）に入れた。代替は事前に入れた依存だけで動き（`npx --no-install`）、依存の変更（install・add・remove など）と知らないサブコマンドは拒否する。
  - 代替を通しても、隠しテストが修正前に失敗し本家の修正で通ることを、試行の前に確かめた（B3: F2P 10/10、F1: F2P 22/22）。
  - B3・F1 の全 10 試行をこの環境でやり直し、採点に使った。旧環境の B3 の 5 試行と、旧環境で上限 $10 のまま走った F1 の Compound Engineering の 1 試行（新しいテスト 21/22、$10.58。所要時間の記録が残っていない）は参考値として `no-nub/` に残した。F1 の初期状態（8 月の zod）は pnpm の版で nub の指示が無く、実際に影響を受けたのは B3 だけだった。

## 次の対応

1. **差が出る課題を足した検証（提案）**: 今回は 4/6 課題が天井だった。品質で比べるなら、(a) B3・F1 のように「症状を直すだけでは足りず、本家が周辺のケースまで直している」課題、(b) 課題文に再現手順が無い・仕様の制約が細かい課題を、事前に baseline 1 回で試して満点にならないものだけ採用する手順にする。
2. **差が出た 2 課題（B3・F1）の繰り返し**: 1 回ごとのぶれが大きいので、各条件 2〜3 回に増やして、F1 で 4 候補がそろって同じテストを壊した傾向が再現するかを確かめる。
3. **判定への入れ方**: W11 は品質で差が出なかったため、判定会では「効率の比較の参考（同じ品質なら候補なしが最も安く速い）」として扱うのが妥当。
