# W34 レビューの指摘で直させた後の質（作りすぎ・消えた振る舞い・弱いテスト・flaky なテスト） — 結果レポート

- 実施: 2026-11-12。設計: [`poc/tasks/wf-W34-design.md`](../../../tasks/wf-W34-design.md)。判断の記録: [`decisions.md`](decisions.md)。集計表: [`tables.md`](tables.md)（`poc/scripts/report_w34.py`）。
- 目的: これまで（W21〜W33）は「仕込んだ不具合を見つけるか」だけを測り、どの Skill も道具なしと同じだった。Skill の中身（Fable と相談し、実物で確かめた）から、強みは観点の深さ・重さ付け・抑制にあると見て、**レビューの指摘に沿って直させた後のコード**を測った。題材にはユーザーの依頼で「時間がたつと落ちる・flaky なテスト」を足した。
- 題材 4 つ × 設定 7 つ × 2 回 = 56 本（Sonnet）。どの試行も、同じ会話で レビュー → REVIEW.md に書く → 指摘に沿って直す、まで行った。全試行が終わり、介入は 0 回。判定（レビューの段）の一致率は 1.0（2 回判定 14 件）。

## 結論

- **今回も、Skill による差は小さかった。** レビューの段で見つけた数も、直した後の質も、ほとんどの項目で道具なしと同じだった。差が出たのは次の 3 点だけ（各 2 回なので暫定）。
  1. **作りすぎを消すか（f1）**: PR Review Toolkit（既定・明示）・`design-principles-review`・`ce-code-review depth:full` は 2 回とも、1 項目のための汎用の仕組みを消した。道具なし・内蔵 `/code-review high`・`ce-code-review` は 2 回中 1 回だった。設計を見る Skill にわずかな利点がある。
  2. **直すときに正しかった本体を壊す（f4）**: 内蔵 `/code-review high` は 2 回とも、正しかった集計の処理や日数の検証を変えて、振る舞いを壊した（隠しテスト 1/4・3/4）。PR Review Toolkit の専門エージェントを明示した設定も 1 回ずつ（f3・f4）壊した。指摘の数が多い設定ほど、直す必要の無い所まで直す。
  3. **費用**: 専門エージェントを明示した PR Review Toolkit は 1 本 $1.3〜1.6（道具なしの約 4 倍。一部のエージェントは Opus 指定）。`ce-code-review depth:full` は f3 で $1.6。
- **flaky なテスト（f4。ユーザーの依頼）: レビューで直せる型と、直せない型がはっきり分かれた。**
  - 本物の時刻に頼る・UTC と日本時間の取り違え・処理時間の確認は、14 本すべてが見つけて直した。時間がたった状態で落ちる数は 5 → 2 に減った。
  - **初期データの件数の決め打ち（14 本中 2 本しか指摘しない）と、エラーの文言の丸ごとの比較（14 本中 0 本）は、どの設定もほぼ見落とし、直した後も残った。** これは、ユーザーの言う「テストが細かくなりすぎて、しばらくすると落ちる」型そのもの。レビューする側は「確かめ方が細かすぎる」を問題と見なさない。
  - テストを消して落ちなくした試行は無かった。本体を壊したときに落とせる数（変異）は、直す前の 3/6 から 5〜6/6 に上がった。
- **ほかの題材は全員ができた。**
  - f2（ファイル分割で消えた検証 2 つとテスト 1 つ）は、14 本すべてが 3 つとも見つけて戻した。
  - f3（弱いテスト）は、直した後のテストが本体の変異を 8 個中 7 個落とせるようになった（直す前は 0 個）。設定による差は無かった（道具なしの 1 本は、日付の計算を SQL に移して変異の対象が 6 個になり、5 個を落とせた）。
  - f1 の不具合（更新で優先度が保存されない）と書き写しは、14 本すべてが直した。
- 開発フローへの意味（暫定）:
  - レビュー用の Skill を、きれいさ・テストの質のために入れる根拠は弱い。設計を見る Skill（`design-principles-review` など）には、作りすぎを消す方向のわずかな利点がある。
  - **内蔵 `/code-review high` の指摘をそのまま直させるのは危ない。** 指摘が多く検証が無いので、正しかった所まで変える。
  - **flaky を減らすには、レビューより、テストの書き方の決まりを明文化する方が効きそう。** 例: 「初期データの件数や、エラーの文言を丸ごと比べない」「本物の時刻を使わず時刻を渡す」「処理時間を単体テストで確かめない」。今回の結果では、時刻・時差・処理時間の型はレビューで直るが、件数・文言の型はレビューでは直らない。決まりを置く場所は、雛形の規約（`AGENTS.md`）か、テストの方針（`docs/standards/testing-and-ci-policy.md`）。決まりを入れたときに直るかは、次の W で確かめられる。

## 注意（読み方）

- 各組 2 回。作りすぎを消したかの差（2/2 と 1/2）は、本数が少なく揺れの範囲の可能性がある。
- 「初期データを 1 件足す」状態（P3）は、このアプリの既存のテストも初期データの件数を決め打ちにしているので、プロジェクトの流儀として受け入れられている面がある。表では P3 を除いた数も並べた（tables.md）。
- f1 の隠しテスト H3（ライブラリの関数に不正な値を直接渡す）は、作りすぎを消した試行で落ちた。検証を API と画面の入口に移したためで、API と画面での振る舞いは保たれている（壊したのではない）。f1 は H1（不具合を直したか）と、仕組みが残ったかで読む。
- f3 の隠しテストの読み込み方を、試行の後に 1 回直した（関数を消した試行で読み込めなかったため。振る舞いの基準は変えていない）。判断の記録に書いた。
- 再レビューの往復は入れていない（1 回の修正だけ）。
