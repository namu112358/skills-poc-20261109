所見

  • どこで差が出たか: 12 項目のうち 6 項目（別のタスクの申請 H03、本文のなりすまし H04、実在しない日付 H05、壊れた入力 H06、理由の境界 H08、判断済みの再判断 H11）は、全試行が守った。差が出たのは、権限（担当者以外の申請 H01。通過 4/9、本人の承認 H02。通過 6/9）と、期限・日付の意味（H07・H09・H10・H12）だった。
  • 権限（H01）: Feature Dev と gstack は 4 試行とも、担当者でない人の申請を受け付けた（課題文には「タスクの担当者は…延長を申請できます」とある）。Feature Dev #1・gstack #2・Compound Engineering #1 は、申請者本人による承認（H02）も止めていなかった。Superpowers・baseline・Compound Engineering #2 は担当者の確認を入れた。
  • 時差（H10）: 課題文には「利用者は全員日本国内にいます」とだけ書いた。日本時間で「今日」を求めたのは Superpowers #1 だけ（差分に日本時間の扱いが 6 か所）。ほかの 8 試行はそもそも過去の日付を確かめていなかった（H09 も不合格）。Compound Engineering の 2 試行は日本時間に言及したが、過去の日付の判定には使っていなかった。
  • 期限の意味（H07・H12）: 「延長」なのに今の期限と同じ日付を受け付けた試行が 7/9、申請の後に期限がもっと先へ変えられていても承認で期限を短くした試行が 7/9。Superpowers の 2 試行だけが、申請時と承認時の両方で「今の期限より後か」を確かめていた。
  • テストの強さ: 全試行が tests/extensions.test.ts を追加し、壊した版の検出率は 73%〜93%（14.7〜18.7 点）で、隠しテストほどの差は出なかった。gstack #2 は src/lib/ のコードが短く、壊せた版が 45 個（ほかは 60 個）だった。検出率が高くても、落とし穴そのもの（日本時間・権限）を確かめていないテストでは隠しテストの結果は良くならない（Compound Engineering #1 は 53/60（88%）を検出したが、隠しテストは 6/12）。
  • ブラインドレビュー: 7.5〜13.5 点。2 名で同じ観点が 2 点以上ずれたものは無かった。最低は Feature Dev #1（7.5 点。権限の確認が無い、共通の src/lib/api.ts に延長申請の処理を入れた、テーブル名とマイグレーション名の食い違い）。Superpowers は 2 試行とも 12.0 点で、レビューでは 1 位ではない（Feature Dev #2・Compound Engineering #1 が 13.5 点）。コードの見た目の質と、落とし穴への対応は一致しなかった。
  • ツールの工程: Feature Dev は 2 回とも code-explorer・code-architect・code-reviewer のエージェントを動かし、Compound Engineering は計画・作業・レビューで 11 回ずつサブエージェントを起動、gstack は /review を実行した。どの候補も工程は省いていない。それでも、課題文に無い落とし穴（日本時間・期限を短くしない）を設計やレビューで拾えたのは Superpowers（brainstorming が発火）だけだった。
  • Superpowers の 2 回の差: #2 は H09・H10（過去の日付・日本時間）を落とした。brainstorming の出方で、日付の扱いを検討するかどうかが変わる（2 回で品質の差 7.0 点）。

判断の記録

  • 課題の作り直し: 前任の下書き（コミット 01ea514、「作業時間の記録」）は W7b とほぼ同じ機能で、配点・テストの強さの方式も未確定だったため、引き継いだ担当が「期限の延長申請と承認」で作り直し、試行の前に固定した。前任の下書きは poc/answer-key/W10/unused-time-entries-draft/ に残した。時計をずらして時差を確かめる方法、判定を「拒否されたか・状態が変わっていないか」で見る考え方は同じ。
  • 画面を作らない: 品質の差（書かれていない落とし穴）を API で決定的に確かめるため、課題を API だけにした。画面の検査は W6 で行っている。
  • 「公開」の受け入れテストの扱い: 課題文に書かれた範囲を確かめるという意味で、テスト自体は W1〜W8 と同じく候補に見せていない。
  • 隠しテストの判定: 403 と 409 のようなステータスコードの違いは問わず、「拒否されたか（4xx）」と「状態が変わっていないか」で判定した（課題文に書いていないコードを当てさせないため）。入力の誤り（H05〜H10）は 400、不正な ID は 404 を求めた。
  • テストの強さの方式: 候補が src/lib/ に書いた行をわざと壊し、候補自身の npm test で検出できた割合にした。候補ごとに関数の名前・形が違い、参照実装を壊した版に候補のテストを当てることはできないため。API Route は @/ の別名のため node:test から読めず、どの候補も単体テストできないので対象にしなかった。
  • 費用の上限: 規模係数 = baseline $0.7308 ÷ W1 baseline $0.15 = 4.87。上限 = 4.87 × W1 の候補平均 × 5（最大 $10）で、Superpowers $4.13・Feature Dev $4.18・gstack $10（計算値 $11.1）・Compound Engineering $10（計算値 $43.5）。baseline は暫定 $5 で実行した。15:33 UTC にコーディネーターから上限撤廃の連絡があり、ユーザーに直接確認して「上限なしで進めてよい」との回答を得たため、Feature Dev #2・Superpowers #2 は上限なしで行った。上限で止まった試行は無い（最高は Compound Engineering #2 の $6.87）ため、やり直した試行は無い。
  • ターン数・時間の数え直し: Feature Dev #1・#2、Superpowers #2、Compound Engineering #2 は、子セッションが裏で起動した待機用の監視の通知で 1 ステップに結果が複数あり、共通の grade.py（最後の結果だけを数える）ではターン数・実際に動いた時間が少なく出た。W10 では全部の結果を足して数え直した（grade_w10.py --recount。元の値は turns_last_result_only に残した）。費用は累計なので影響なし。効率の時間は壁時計の時間（elapsed_seconds）で計算しており影響なし。
  • 試行間の独立性: isolation_suspects は baseline と Superpowers #1 で 1 件ずつ。どちらも自分の作業用コピーの中で cd ../../../../.. してアプリの直下に戻っただけで、外は参照していない（誤検出と判断）。正解データを読んだ形跡（answer_key_access）は全試行で無し。
  • 総合判定への入れ方: PLAN.md §4 のとおり、W10 の重みは判定会で決める。このレポートでは 2 本立て（品質・効率）を主に示す。総合点は品質の内訳の合計（費用・時間を含まない）なので、品質と同じ値になる。
