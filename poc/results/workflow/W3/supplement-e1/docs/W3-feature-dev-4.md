# 要件: チームの進捗の可視化（「進捗」画面）

## 背景・課題

- 誰がどれくらいタスクを抱えていて、どれが遅れているかが、ひと目で分からない。
- 現状は、毎週月曜朝の定例（15 分）で、リーダーが各自に口頭で状況を聞いている。タスク一覧は全件が並ぶだけで、遅れの発見に向かない。
- 利用者は主にリーダー。メンバーも閲覧してよい（ログイン済みの全ユーザーが見られる）。定例で画面を共有して全員で見る。

## 目的

定例で「遅れているタスク」を早く見つけ、手を打てるようにする。メンバーの入力の手間は増やさず、既存のステータスと期限だけで把握できるようにする。

## 機能要件

### F1. 「進捗」画面（新規）

- 新しいページ（例: `/progress`）を追加する。ログイン必須（`requireUser()`）。
- ヘッダー（`src/app/layout.tsx`）に「進捗」へのリンクを追加する。
- 既存のタスク一覧（`/tasks`）の表示・絞り込みは変更しない。
- 画面の文言は日本語。数字と表のみで構成し、グラフ類は作らない。

### F2. 期限切れタスク（画面でいちばん目立たせる）

- 定義: 期限が今日（JST）より前で、ステータスが完了でないタスク。
- 画面の最上部に件数を大きく表示し、一覧を出す。一覧の項目: タスクのタイトル（詳細へのリンク）、担当者名、期限、「何日過ぎたか」（今日 − 期限の日数）。
- 並び順: 超過日数の多い順（同じなら ID 順）。
- 0 件のときは「期限切れのタスクはありません」と表示する。

### F3. 期限が近いタスク

- 定義: 期限が今日を含めて 7 日以内（今日〜今日+6 日、JST）で、ステータスが完了でないタスク。期限切れは含めない。
- 期限切れとは別のセクションで、タイトル・担当者名・期限・あと何日かを一覧する。期限の近い順に並べる。
- 0 件のときはその旨を表示する。

### F4. 担当者別の件数表

- 担当者（ユーザー全員。タスクが 0 件の担当者も行を出す）ごとに、未着手・進行中・完了の件数を表で示す。
- 担当者は ID ではなく名前（佐藤など）で表示する。
- 合計行を設ける（全体の件数把握のため）。
- 参考として、担当者ごとの期限切れ件数の列を設けてよい（実装時に判断。F2 の定義と一致させる）。

### F5. 今週の完了数（担当者別）

- 今週（月曜〜日曜、JST の日付で判定）に完了にしたタスクの数を、担当者ごとに表示する。完了数が 0 の担当者も行を出す。
- 判定には、ステータスを完了にした日時（下記 F6）を使う。

### F6. 完了日時の記録（データ変更）

- tasks に「完了日時」を保持する列を追加する。`src/lib/db/migrations.ts` の末尾に version 3 として追加し、既存のマイグレーションは書き換えない。
- 日時は ISO 8601（UTC）で保存する（sessions.expires_at と同じ形式）。
- 記録のタイミング（作成と更新の両方、API 経由）:
  - ステータスが完了以外から完了に変わったとき: 現在時刻を記録する。
  - 完了から別のステータスに戻したとき: 記録を消す（NULL）。
  - 完了のまま他の項目だけを更新したとき: 記録は変えない。
  - 完了ステータスで新規作成したとき: 作成時刻を記録する。
- 過去の分の埋め戻しはしない。初期データ（seed）の完了タスクは、画面確認のため完了日時を持たせてよい（今週に入るもの、入らないものを含める）。完了日時が無い完了タスクは、今週の完了数に数えない。
- 完了日時が NULL のまま既に完了になっているタスクがあっても、画面が壊れないこと。

### F7. 日付の扱い（JST）

- 「今日」「今週」「7 日以内」の判定はすべて日本時間（JST, UTC+9）の日付で行う。UTC の保存値は JST の日付に変換して比較する。
- 現在時刻は関数の引数で渡せるようにして、テストで固定できるようにする。

## 非機能・制約（CLAUDE.md の規約に従う）

- 集計・絞り込みのロジックは `src/lib/` に置き（例: `src/lib/progress.ts`）、ページには表示処理だけを書く。
- SQL の値はプレースホルダで渡す。
- 新しい外部ライブラリは追加しない。
- ロジックを追加・変更するので、`tests/` に単体テストを追加する（完了日時の記録・削除、JST の境界、期限切れ・期限間近の判定、今週の判定、担当者別の集計）。
- `npm run typecheck`、`npm test`、`npm run build` が通ること。
- 既存の API の仕様（エラー形式、401/400/404）は変えない。タスクの JSON に完了日時を追加するかどうかは実装時に判断する（追加する場合は後方互換を保つ）。

## 対象外

- 通知（メール、Slack など）。
- 進捗率（%）や工数の入力。
- グラフ、ガントチャート、バーンダウンチャート。
- 過去からの推移、先週との比較。
- 過去分の完了日時の埋め戻し。
- 既存のタスク一覧の表示・絞り込みの変更。
- エクスポート（依頼者からお任せとのことだが、スコープを絞るため今回は作らない。必要なら別途依頼）。

## 受け入れ基準

1. ヘッダーの「進捗」から `/progress` を開ける。未ログインではログイン画面に移る。
2. 画面の最上部に期限切れの件数があり、一覧に担当者名・期限・超過日数が出る。完了済みのタスクは含まれない。
3. 期限が今日のタスクは「期限切れ」ではなく「期限が近い」に出る。今日+6 日は出て、今日+7 日は出ない。
4. 担当者別の表に、全ユーザーの未着手・進行中・完了の件数が名前付きで出る。タスクが 0 件の担当者も出る。
5. 今週（月〜日、JST）に完了にしたタスクだけが、担当者別の完了数に入る。日曜 23:59 JST と月曜 0:00 JST の境界が正しく判定される。
6. タスクを完了にすると完了日時が記録され、完了から戻すと消える。完了のまま他の項目を更新しても変わらない。
7. 既存のタスク一覧、詳細、API の動作が変わらない。既存テストが通る。
8. 追加したロジックの単体テストがあり、`npm run typecheck` / `npm test` / `npm run build` が通る。

## 補足（コードベースの現状）

- tasks は `id, title, status, assignee, due_date` のみ。ユーザー名は `users.name`（`listUsers` / `getUser`）。
- 一覧画面の担当者は現在 ID 表示（今回は変更しない。進捗画面でのみ名前表示）。
- 更新は `createTask` / `updateTask`（`src/lib/tasks.ts`）に集約されているため、完了日時の記録はここで行う。
