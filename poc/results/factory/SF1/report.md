# SF1: GitHub のイベントで起動する Routine で、Issue から PR までを自動で回す（結果）

- 実施: 2026-11-12（設計は [wf-SF1-design.md](../../../tasks/wf-SF1-design.md)）
- 試行の場: [namu112358/poc-software-factory-20261112](https://github.com/namu112358/poc-software-factory-20261112)
- 手順書（Routine が読むもの）: 試行の場の `.claude/routines/`

## 結論

- **Routine の GitHub トリガーで、Issue → 実装 → PR → 独立したレビュー → 修正 → 人のマージ待ち、が人の操作なしに回った。** 人がしたことは、Issue に `ready` を付けることとマージだけ（試行中に見つかった手順書の不具合を直したことを除く）。
- **起動は速く、確実だった。** `ready` を付けてから実装のセッションが起動するまで 1 分以内（付け直した 2 回は 1 秒）。15 回ほどのイベントで、取りこぼし・二重の起動は無かった。
- **品質は、手で起動した試行と同じ範囲だった。** W1 6/6、W2 16/16 は満点。W10 は公開 13/13・隠しテスト 6/12 で、既存の試行（baseline 8、Superpowers 12・10、Feature Dev 6・7）の範囲の下のほう。実装の Routine は Sonnet 5.5（effort 中）で動いた。
- **独立したレビューの役は役に立った。** 手順書の変更の PR では、本物の抜けを 2 回続けて見つけた（巡回が人の PR を切り替えてしまう、など）。一方、受入条件と照合する作りなので、書かれていない落とし穴（W10 の権限・時差・同時更新）は見逃した。これは既存の PoC（W29〜W33）と同じ傾向。
- **安全の決まりは守られた。** Issue に仕込んだ「CI の検査を消す・権限を広げる」は実行せず、断ったことを Issue に書いた。`.claude/` の変更が要る指摘は、修正の役が手を付けずに `needs-human` で止まった。マージ・Approve はしなかった。
- **流れは、ラベルより PR の Ready / draft で組むほうが単純だった**（ユーザーの提案）。レビューは Ready になったときに起動し、指摘があれば draft に戻す。修正は draft に戻されたときに起動し、直して Ready に戻す。起動のためのラベルが 3 つ要らなくなった。

## 見つかった問題と、取った対応

| # | 問題 | 対応 | 状態 |
|---|---|---|---|
| 1 | `ready` を付けた人の権限を確かめる REST の API が、クラウドのプロキシで拒まれた（403）。4 件のうち 1 件だけ止まり、ほかは別の方法で通った。セッションによって結果が分かれる | 確かめ方を GitHub MCP の `list_repository_collaborators` に固定した | 直した |
| 2 | 止まったときに `ready` が付いたまま残り、人が付け直しても「ラベルが付いた」イベントが起きず、実装が起動しなかった | 止まるときは `ready` と `in-progress` を外す決まりにした | 直した |
| 3 | 先にマージした PR と衝突した PR を、直す役がいなかった（衝突は GitHub のイベントにならない） | レビューが衝突を必須の指摘にし、巡回が衝突した PR を draft に戻し、修正が `main` を取り込む | 直した（巡回の動きは未確認） |
| 4 | 閉じた Issue に `in-progress` が残った | 実装が PR を Ready にしたら外す。巡回が残りを外す | 直した（巡回の動きは未確認） |
| 5 | ラベルで次の役を起動する流れは、ラベルが 7 種類になり、付け外しの漏れが起きやすい | PR の Ready / draft で起動する流れに変えた | 直した |
| 6 | 人が手順書を直して Ready に戻すとき、修正の役が付けた `needs-human` を外し忘れると、レビューの役が何もせずに終える | README に再開のしかたを書いた | 直した |
| 7 | Routine のセッションの名前が「Factory 実装」のままで、どの Issue の作業か分からない | 各役が自分の名前を付け直す決まりを入れたが、Routine のセッションには名前を変える道具が無かった | 未解決（下の改善案） |
| 8 | 画面から作った Routine は、エージェントから編集できない。コネクタ（Slack・Supabase・Vercel など）が既定で全部付いた | 人が画面で外す | 未対応 |

## 改善案（必要なものだけ）

1. **流れは今の形（Ready でレビュー、draft で修正）を標準の案にする。** 状態は GitHub の PR と 4 つのラベル（`ready`・`in-progress`・`blocked:question`・`needs-human`）だけにし、新しい仕組みは足さない。
2. **レビューを、受入条件の照合と、書かれていない落とし穴の確認の 2 段にするかは、まだ決めない。** W10 の見逃しは、レビューの頼み方を変えれば減る見込みがある（既存の PoC の W29〜W32）が、費用が 1.2〜1.9 倍になる。Issue に運用の事情を書くほうが効く（W12〜W14）ので、先に Issue の様式で対応する。
3. **セッションの名前は、Routine の中からは変えられない。** 名前を付け直す決まりは手順書から外し、代わりに各役が Issue・PR に書くコメントに、そのセッションの URL を書く（コメントからセッションを開ける）。
4. **Routine の作成は人の作業として手順にする。** 画面から作ると、エージェントは編集できず、コネクタも全部付く。指示文・トリガー・外すコネクタを、そのまま写せる形で雛形に置く。
5. **巡回は、1 時間ごとでは遅い場面がある。** 今回のイベントの取りこぼしは 0 件だったので、頻度は上げず、実績を見て決める。

## まだ確かめていないこと

- 巡回の Routine が、取りこぼし・衝突・残ったラベルを実際に拾うか。
- 新しい流れ（Ready / draft）で、レビューの指摘から修正の往復が回るか（W8 の試行で確かめる）。
- 同じ Issue を 2 回以上流したときのばらつき。各課題 1 回だけで、品質の差は既存の試行のばらつきの範囲で読んでいる。
- GitHub のイベントの 1 時間あたりの上限（数値は非公開）。
