# W19 の設計: 粗悪な既存実装に引っ張られない

- 作成: 2026-11-10（試行の前に固定。試行中・採点中は変えない）
- 採点の詳細: [`poc/answer-key/W19/grading.md`](../answer-key/W19/grading.md)（正解データ。作業用コピーには置かない）
- 試行の仕組み（`run-trial.sh` の分岐、依頼者役 `answer_persona.py`、`run_w14_trials.sh`）は W14・W15 と同じものを使う。W19 で足したのは人間の代理人（下の 4）だけ。

## 1. 目的

ユーザーの実際の開発で、DB をマイグレーションせず、JSON の列に全データを詰め込む問題が起きた。
既存の実装が粗いとき、候補がそれに合わせてしまうか、要件から見たあるべきデータの持ち方を選ぶかを比べる。

1. 要件から見たデータの持ち方を先に考える（担当者は列、点検の記録は専用の表）。既存の `extra`（JSON の列）に合わせて詰め込まない。
2. 構造の変更を避けない。マイグレーションで足し、旧データの点検者・最終点検日を移す。
3. 範囲は広げすぎない。`extra` 全体の作り直しはせず、残した課題を書き残す。
4. データを失わない。既存の利用者（経理が直接読む `extra.dept`）を壊さない。前の版に戻せる。
5. 5 万件の本番データで動く（索引・最初の起動の時間）。

## 2. 題材と初期状態

W12 と同じ計測器の校正台帳。初期状態（`poc/answer-key/W19/base.patch`）は、`poc/app/` に次を足したもの。`poc/app/` 自体は変えず、`run-trial.sh` が作業用コピーにだけ当てる。

- マイグレーション 5: 計測器に「その他の項目」`extra`（TEXT の JSON）を足した。
- 初期データの計測器の `extra` に、担当部署（`dept`）・点検者（`inspector`、「鈴木さん」「外部委託」や在籍していない人の名前）・最終点検日（`last_inspected`、`2026/8/20`・`R8.9.10` など書き方がばらばら）・メモが、決まりなく入っている。
- 担当部署での絞り込みは、全件を読んでから JavaScript で行う。更新（PATCH）は `extra` を重ねる（null を送ったキーは消す）。詳細の画面はキーごとの if が散らばっている。
- 単体テスト 31 件。型チェック・ビルドとも成功。`docs/operations.md` に「本番は計測器 5 万件」。

依頼者だけが知っている事情（質問すれば答える。`persona.md`）: 担当者・点検した人は在籍している人、記録は点検日・点検した人・結果（良好・要修理）・メモで履歴を残す、消さない（訂正は足す）、周期は計測器ごと・既定 3 か月、記録が無ければ未点検、担当者で絞り込み・担当者ごとの遅れの台数、要修理なら使用停止、旧データの点検者・最終点検日を引き継ぐ（分からない名前・読めない日付も捨てない）、本番 5 万件で毎朝一覧を開く、`extra.dept` は経理が直接読むので変えない、前の版に戻せること。

## 3. 課題文（確定。この 1 文だけを依頼として渡す）

課題文の末尾には W12 と同じ定型文（依頼者に `ask-po` とメッセージで質問できる・工程を省かない・コミットする）を付ける（代理人の判断 D6）。

## 4. 依頼者役と、人間の代理人

ユーザーの指示（2026-11-10）: 「基本的に自律型開発をするつもりだから、質問や議論は、人間の代理人を置いて確認してみて。代理人は、どのような決定を下したのか、人間に報告できるようにしておいて。」

- 業務の事実（何を作るか・業務の決まり・運用の事情）は、依頼者の回答シート（`persona.md`）から答える。W14 と同じ。
- 技術的な判断（案の選択・計画の承認・進めてよいか・やり直すか）は、人間の代理人が `poc/proxy/principles.md` の原則（P1〜P8）に沿って決めて答える。「お任せします」とは言わない。
  - 記録は `raw/<試行ID>/po-questions.jsonl` の `kind: decision`（決めたこと・理由・原則の ID・置いた前提）。report の「代理人の判断」にまとめる。
  - 仕組み: `answer_persona.py` の `PROXY_SCENARIOS`（W19 だけ）。`POC_PROXY=0` のときは従来どおり「お任せします」と答える（対照）。
  - コミットせずに止まったときの介入文も「お任せ」を含まない文にする（D7）。代理人なしの試行は従来の文。
- 注意（D3）: 原則 P1（既存の実装に引っ張られない）は、この W の正解と同じ向き。代理人ありの結果は「代理人の誘導込み」として読み、代理人なしの Feature Dev 2 本と比べる。
- 準備の中で担当が人に聞きたくなった判断も代理人に聞いて決めた（`results/workflow/W19/PROXY-DECISIONS.md` の D1〜D7）。
