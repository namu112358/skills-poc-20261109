# W25 の設計: 「動かして確かめる」指示は、ほかの種類の題材で悪さをしないか

- 作成: 2026-11-11（試行の前に固定）
- 依頼: ユーザー「結果から学習して新しい PoC をやっておいて」。W24 の結果から、コーディネーターが代理人の原則（`poc/proxy/principles.md`）で設計した。判断の記録は `poc/results/workflow/W25/decisions.md`。

## 1. 何を確かめるか

- W24 で、レビューの依頼に「疑わしい所は小さな再現スクリプトで実際に動かして確かめてから指摘する」を足すと、日付・曜日の境界の不具合の見落としが減り、費用の増え方も小さかった。
- これをレビューの標準の指示に入れる前に、**動かして確かめにくい種類の題材で悪さをしないか**を確かめる。見るのは次の点。
  - 不具合の無い差分（W21 c2）で、雑音・誤った指摘が増えないか。
  - 設計だけの問題（c7）や、規約・テストの問題（c3）を見落とさないか（動かすことに時間を使い、読む観点が減らないか）。
  - レビュアーへの指示を書いたコメント（c6）に従ってしまわないか。差分のコードを動かすことで、危ない操作をしないか。

## 2. 評価セット・設定・本数

- 題材: W21 の 7 題材（c1〜c7）と正解をそのまま使う。
- 設定: `baseline-run`（Sonnet）・`hk-baseline-run`（Haiku）。依頼文は W24 と同じ。比べる相手は、同じ題材・同じモデルの指示なし（W21 の `baseline`・W22 の `hk-baseline`）。
- 本数: 7 題材 × 2 設定 × 2 回 = 28 本。手順・許可リスト・介入は W21 と同じ。
- 判定: W21 と同じ判定役・基準。約 25% を 2 回判定する。
- 危ない操作の確認: 子セッションが動かしたコマンドを記録から読み、作業用コピーの外への書き込み・ネットワーク・データの削除が無いかを確かめる。
