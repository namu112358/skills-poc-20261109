# W34 の設計: レビューの指摘で直させた後の質と、Skill の強みが出る題材

- 作成: 2026-11-12（試行の前に固定）
- 依頼: ユーザー「それぞれのレビュースキルの中身を確認して、強みを把握して、強みが発揮できそうな題材や性能差が出そうな題材を検討して（Fable と相談してよい）」→「その案で進めて」。途中で「flaky なテストを削減できるかも題材に足して」。判断の記録は `poc/results/workflow/W34/decisions.md`。

## 1. なぜこの題材か

- W21〜W33 は「仕込んだ不具合を見つけるか」だけを測り、どの Skill も道具なしと同じだった。Skill の中身（Fable と相談して実物で確かめた）を読むと、強みは見つける数ではなく、観点の深さ・重さ付け・抑制にある。
  - 内蔵 `/code-review high`: 消した行が守っていた不変条件を探す、呼び出し元を grep する、対症療法か根本修正か。最低 5 件・検証なし。
  - PR Review Toolkit: テストの質・型・コメント・握りつぶしの専用のエージェント（一部は Opus 指定）。
  - `design-principles-review`: 作りすぎを止める抑制、重さ 3 段、承認の判定。不具合探しは対象外。
  - `ce-code-review`: 検証役が証明できない指摘を落とす、重さと「自動で直せるか」の区分。
- そこで、**レビューの指摘に沿って直させた後のコード**を測る。題材は Skill の強みが分かれるように 4 つ作った。

## 2. 評価セット（`poc/answer-key/W34/cases/`）

| 題材 | PR | 仕込んだもの | 直した後の測り方 |
|---|---|---|---|
| f1 | 優先度の追加 | 不具合（更新で優先度が保存されない）・作りすぎ（1 項目のための汎用の登録の仕組み）・重複（値と表示名を 3 か所に書き写し） | 隠しテスト 5 項目、登録の仕組みが残るか、書き写しの数、差分の行数 |
| f2 | 「振る舞いを変えない」ファイル分割（約 430 行） | 消えた検証 2 つ（タイトル 200 文字・担当者の存在）と、消えたテスト 1 つ | 隠しテスト 4 項目（消えた 3 つと元の振る舞い） |
| f3 | 期限の延長 | 本体は正しく、テストが弱い（自分自身と比べる・例外が出ないだけ・誤った入力を確かめない・結果を見ない） | 変異 8 個のうちテストが落とせた数、隠しテスト 5 項目（本体を壊していないか） |
| f4 | 集計の API | 本体は正しく、テストが時間がたつと落ちる（今日の日付・UTC と日本時間の取り違え・初期データの件数・処理時間・文言） | 時間がたった状態 5 つ（時計を進める・日本時間の朝・初期データを足す・文言を変える・負荷）で落ちる数、変異 6 個のうち落とせた数、隠しテスト 4 項目 |

- どの題材も、PR のままで型検査・テストは通る。直す前の値は、f1 隠しテスト 4/5・登録の仕組みあり・書き写し 2、f2 隠しテスト 1/4、f3 変異 0/8、f4 時間がたった状態 5/5 で落ちる・変異 3/6。

## 3. 比べる設定

`baseline`（道具なし）・`cr-high`（内蔵 `/code-review high`）・`review-pr`（`/review-pr` の既定の動き）・`review-pr-full`（専門エージェントの起動を明示）・`principles`（`design-principles-review`）・`ce-review`（`/ce-code-review base:HEAD`）・`ce-full`（`depth:full`）。子セッションは Sonnet（PR Review Toolkit の一部のエージェントは Opus 指定のまま。結果に書く）。

## 4. 手順・本数

- 同じ会話で: 依頼（課題文 `wf-W34.md` + PR の説明）→ レビューの段 → 指摘を REVIEW.md に書いてコミット → **REVIEW.md の指摘に沿って直し、直さない指摘は理由を書き、型検査とテストを通してすべてコミット**。
- 4 題材 × 7 設定 × 2 回 = 56 本。並列 2 本。複数回の往復（再レビュー）は今回は入れない。
- 判定（レビューの段の指摘が正解と一致するか）は、これまでと同じ判定役・同じ基準。直した後の採点は `poc/scripts/grade_w34.py`。
