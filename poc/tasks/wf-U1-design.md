# U1 の設計: UI/UX 系ツールの組み合わせの比較

- 作成: 2026-11-11（試行の前に固定。試行中・採点中は変えない）
- 改訂 2: 2026-11-11（U1a〜c の試行中）。依頼者の指示で、LP・業務アプリ・SaaS・ダッシュボードなど題材を増やすため U1d〜f を足した。U1a〜c の課題・採点は変えない。
- 改訂: 2026-11-11（本番の試行の前）。依頼者と相談し、見た目の主の評価を AI の判定から人の 2 択投票に変え、作る課題の回数を 4 回に増やした（§4・§5）。
- 背景: [docs/tool-candidates/ui-ux-overlap.md](../../docs/tool-candidates/ui-ux-overlap.md) は、UI/UX 系 4 ツール（Frontend Design・Web Design Guidelines・Impeccable・UI/UX Pro Max）の中身を読んで、役割の重なりと矛盾を整理し、整理案（案 A）を出した。ただし、どれも実際に動かして確かめていない。U1 は、その「試行で確かめること」を実際の試行で確かめ、標準の構成を決める根拠にする。
- これまでの試行（W1〜W20）は、4 つすべてが有効な状態で行った。U1 だけは、4 つの出し入れを比べる条件にする。

## 1. 目的

次の問いに、試行の結果で答える。

1. 4 つを同時に有効にした今の標準は、どれか 1 つの作る担当に絞った構成より、画面の出来が良いか・悪いか。費用はどれだけ違うか。
2. 作る担当として、Frontend Design・Impeccable・UI/UX Pro Max のどれが良いか。ツールなし（モデルだけ）とどれだけ差があるか。
3. レビューで、どの構成がどれだけ問題を見つけるか。誤った指摘・重複はどれだけ出るか。
4. 実際にどの Skill が呼ばれるか。UI/UX Pro Max の書体の勧めを Impeccable の自動チェックが指摘する往復は起きるか（ui-ux-overlap.md の「試行で確かめること」1〜4）。

## 2. 比べる構成

レビュー担当の Web Design Guidelines は、ツールなし以外のすべての構成に入れ、作る担当の違いだけを比べる。

|---|:-:|:-:|:-:|:-:|---|
| `ui-none` | | | | | ツールなし（比べる基準） |
| `ui-all` | ○ | ○ | ○ | ○ | 今の標準（W1〜W20 の条件） |
| `ui-a` | | ○ | ○ | | 整理案 A |
| `ui-fd` | ○ | ○ | | | 軽い構成（vendored の Skill だけ） |
| `ui-pm` | | ○ | | ○ | UI/UX Pro Max を作る担当にした構成 |

- ほかの常時有効なもの（security-guidance、TypeScript LSP、Vercel の React 系 Skills、webapp-testing、skill-creator、gh、gh-stack、Playwright MCP・Next.js DevTools MCP）は全構成で同じ。開発ワークフローの候補プラグインは入れない（baseline と同じ）。
- Impeccable のフック（編集のたびのチェック・作業終了時のチェック）は、Impeccable を入れる構成で既定のまま有効にする。
- Web Design Guidelines は実行時にルールを `raw.githubusercontent.com` から取得する。U1 に限り、子セッションの許可リストに `WebFetch(domain:raw.githubusercontent.com)` を足す（CLAUDE.md の例外: 子セッションの許可リストの変更。全構成に同じく足す）。

## 4. 試行

- U1a・U1b は各構成 4 回、U1c は各構成 2 回（5 × 4 × 2 + 5 × 2 = 50 本）。回ごとに実行順を逆にする。並列は 3 本まで。
  - U1d〜f も各構成 4 回（60 本）。U1a〜c の 50 本の後に流す。
  - 作る課題を 4 回にしたのは、見た目は 1 回ごとのぶれが大きく、2 回では構成の差とぶれを見分けにくいため。
- モデル `claude-sonnet-5-5`。権限は W6 以降の許可リスト（開発サーバー・ブラウザを含む）+ 上の WebFetch。
- 費用の上限は付けない。1 試行が $15 を超えたら報告に書く。

## 5. 採点

### U1a・U1b（作る課題）

目的は「人が良いと思える UI を作れるか」なので、**主の評価は人の 2 択投票**にする。機械の検査は足切り、AI の判定は補助にする。

1. **人の 2 択投票（主の評価）**: 同じ課題の 2 案（別の構成の試行）のスクリーンショット（幅 1280px と 375px）を、構成の名前を伏せ、左右をランダムにして並べ、「どちらが良いか（同じくらい、も可）」を選んでもらう。投票用の非公開のページを使う。結果は構成ごとの勝率（同じくらいは 0.5 勝）と、Bradley–Terry の強さで示す。評価者は依頼者 1 名（このチームの標準を決める人）。1 名の好みなので、結果は「依頼者の好みでの順位」として扱い、他の人の評価で補えるようにページは残す。
2. **足切り（合否）**: 下の表の「機能と規約」と「アクセシビリティの自動検査」。満点でない試行も投票には出すが、報告では足切りの結果を並べて書く。
3. **AI の判定（補助）**: 下の表の「見た目と使い勝手（ブラインド判定）」をそのまま行い、人の投票との一致度（同じ組で同じ方を選んだ割合）を測る。一致度が高ければ、次からは AI の判定で回せる根拠にする。

以下は機械の検査と AI の判定の配点（参考の点数。主の評価ではない）。

| 観点 | 配点 | 測り方 |
|---|---:|---|
| 機能と規約 | 30 | 隠しの検査（Playwright）: U1a は「未ログインで `/` に紹介ページ（`h1` とログイン画面へのリンク）が出る」「ログイン済みは `/tasks` へ移動」「ログインできる」、U1b は「全タスクのタイトル・詳細へのリンク・担当者・期限が出る」「`?status=done` で完了だけになる」「画面に絞り込みの操作がある」。両方とも「幅 375px で横スクロールが出ない」。各項目を同じ重みで 20 点。型チェック・単体テスト・ビルドが通る 5 点。新しい外部ライブラリを足していない（`package.json` の依存が同じ）5 点 |
| アクセシビリティの自動検査 | 20 | axe-core（4.10 系、採点側だけで使う）で対象の画面を幅 1280px・375px で検査し、重大（serious・critical）の規則 1 つにつき −4、中（moderate）の規則 1 つにつき −1。0 点が下限 |
| 見た目と使い勝手（ブラインド判定） | 50 | 判定役（`claude-opus-5-5`）に、同じ課題の全試行のスクリーンショット（幅 1280px・375px の全体）を構成の名前を伏せて並べて渡し、5 項目を 0〜4 点で付けさせる: ① 目的が伝わる（紹介ページとして / 毎日使う一覧として）② 情報の階層と読みやすさ ③ 余白・整列・一貫性 ④ 色と書体の使い方（読みやすさ・目的との合い方）⑤ スマートフォンでの見やすさ・操作しやすさ。合計 20 点 × 2.5。U1b は変更前の画面も「参考（採点しない）」として並べる。判定は順番を変えて 2 回行い（判定役 2 名に相当）、平均を使う。2 回の差が 4 点以上の試行は報告に書く |

- 判定役には、どの構成が「良い」と期待されているかを伝えない。判定の基準は「この会社の社員が使う業務アプリとして」で、特定のツールの好み（「ありがちな書体を避ける」など）は基準に入れない。

U1d〜f の隠しの検査（各項目同じ重みで 20 点。ほかの配点は U1a・U1b と同じ）:

- U1d: 未ログインで `/lp` に `h1` が出る、料金（フリー・600 円・ビジネス）が載る、よくある質問がある、申し込みからログイン画面へ行ける、幅 375px で横スクロールが出ない。
- U1e: 未ログインは `/login` へ移動、ログイン後に `h1` が出る、ステータスの名前と件数が出る、全担当者の名前が出る、一覧の画面からダッシュボードへのリンクがある、幅 375px で横スクロールが出ない。
- U1f: 未ログインは `/login` へ移動、一覧から登録画面へのリンクがある、空のまま送ると登録されずエラーが出る、ラベルで入力して登録すると一覧に戻って表示される、幅 375px で横スクロールが出ない。

### U1c（レビュー課題。品質 100 点）

- 判定役（`claude-opus-5-5`）に正解の一覧と `REVIEW.md` を構成の名前を伏せて渡し、指摘 1 件ずつを正解（B1〜B9）・おとり（D1〜D5）・正解外（本当らしい問題 / 誤り / 細かい点 / 判断できない）に振り分けさせる（W20 の `judge_w20.py` と同じ形）。
- 品質 = 見つけた割合 × 80 + 20 −（おとりへの指摘と誤った指摘 1 件につき 5。20 点が下限 0）。
- 「判断できない」は担当が読んで決める。

### 効率

- W6 以降と同じ 2 本立て（`two_axis.py` の考え方）。費用・時間は `ui-none` に対する倍率で測る。品質の差が、比べる 2 構成の 2 回の差の大きい方以下なら「差なし」。

### 観察（点数にしないが報告する）

- 呼ばれた Skill（実行記録の `Skill` ツールの呼び出し）、Impeccable のフックの出力の件数、作られた設計の文書（`DESIGN.md`・`design-system/` など）。
- 使った書体（差分の `font-family`）と、それが Impeccable の「使い古された書体」の一覧に入るか。UI/UX Pro Max の勧め → Impeccable の指摘 → やり直し、の往復があったか。
- トークン（入力・キャッシュの読み込み）と費用、時間。

## 6. 判定の限界（先に書いておく）

- 見た目の判定は 1 つのモデルによるもので、人の好みとは一致しない場合がある。判定の 2 回の一致度を報告し、上位と下位の画面は担当が実際に見て確かめる。
- 各構成 2 回なので、小さな差は「差なし」になりやすい。
- 子セッションのモデルは Sonnet 系。より強いモデルでは、ツールの差が小さくなる可能性がある。
- Web Design Guidelines は `ui-none` 以外のすべての構成に入れているため、単体の効果は切り分けない（依頼者と相談して決めた。作る担当 3 つの比較に絞る）。`ui-none` との差には、作る担当と Web Design Guidelines の両方の効果が混ざる。
