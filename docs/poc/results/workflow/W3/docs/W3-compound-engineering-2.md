# 要件: チームの進捗が見える「進捗」画面

## 背景と目的

- 主な利用者はリーダーの佐藤。チームは佐藤・鈴木・田中の3人で、メンバーも見てよい。
- 毎週月曜朝の定例（15分）で画面を共有し、全員で見る。そこで**遅れているタスクを早く見つけて手を打つ**ことが目的。
- 現状は、定例で各自に口頭で状況を聞いて回っている。タスク一覧は全件が並ぶだけなので、誰がどれだけ抱えているか、どれが遅れているかがひと目で分からない。
- 現状のタスクの項目は、タイトル・ステータス（未着手 / 進行中 / 完了）・担当者・期限の4つ。

## 用語の定義

| 用語 | 定義 |
|---|---|
| 遅れ | 期限の日付が今日より前で、ステータスが「完了」ではないタスク |
| 期限が近い | 期限が今日から7日後まで（今日を含む8日間）で、ステータスが「完了」ではないタスク。遅れには含めない |
| 今日 | 日本時間の日付 |

## 要件

### R1. 「進捗」画面を新設する

1. 新しく「進捗」画面を作り、ヘッダー（既存の「タスク一覧」リンクの隣）にリンクを置く。
2. ログイン済みのユーザーなら誰でも見られる。未ログインのときは、既存の画面と同じくログイン画面へ送る。
3. 画面の文言は日本語にする。

### R2. 遅れているタスクの一覧（画面の最上部・最も目立たせる）

1. 「遅れ」の定義に当てはまるタスクを、期限の古い順に並べる。
2. 各行に、タイトル・担当者（名前）・期限・何日遅れかを出す。
3. タイトルは既存のタスク詳細画面へのリンクにする。
4. 該当が無いときは「遅れているタスクはありません」と出す。
5. 他の部分より目立つ見た目にする（色や見出しなど。具体的な見た目は実装時に決める）。

### R3. 期限が近いタスクの一覧

1. 「期限が近い」の定義に当てはまるタスクを、期限の近い順に並べる。遅れの一覧とは別の見出しにする。
2. 各行の項目は R2 と同じ。ただし日数は「あと何日」（期限が今日なら「今日」）とする。
3. 該当が無いときは「期限が近いタスクはありません」と出す。

### R4. 担当者ごとの件数の表

1. 行は担当者（全ユーザー）、列は「未着手」「進行中」「完了」の件数。担当タスクが0件の担当者も行を出す。
2. あわせて「遅れ」と「期限が近い」の件数の列も出す。
3. 担当者は ID ではなく名前（佐藤など）で表示する。

## 受け入れ例

今日が 2026-11-09 で、初期データ（`src/lib/db/seed.ts`）のままのとき:

- 遅れ: 0件（期限切れの未完了タスクは無い。期限が過ぎている2件は完了済み）。
- 期限が近い（〜11-16）: 「ログイン画面のデザイン」（鈴木・11-12・あと3日）、「API 設計」（佐藤・11-14・あと5日）の2件。
- 件数の表: 佐藤＝未着手1 / 進行中1 / 完了1、鈴木＝未着手1 / 進行中1 / 完了0、田中＝未着手1 / 進行中0 / 完了1。
- 期限が 2026-11-09 の未完了タスクは「期限が近い」に入る（「今日」と表示）。期限が 2026-11-08 の未完了タスクは「遅れ」に入る（1日遅れ）。
- 期限が 2026-11-17 の未完了タスクは、どちらにも入らない。

## 対象外（今回やらないこと）

- タスクの重さの入力や、重さによる負荷の比較。メンバーの入力の手間を増やさないため、既存のステータスと期限だけで判断する。
- 「進行中」のまま長く動いていないタスクの検出。更新日時の記録が必要になるため、必要になったら別の機会に検討する。
- 既存のタスク一覧の表示や絞り込みの変更。
- 通知（メールやチャットへの送信）、期間の指定、グラフ表示。

## 前提

- 「今日」は日本時間で判断する。サーバーの動作環境の時刻設定に左右されないようにする。
- タスクの項目（タイトル・ステータス・担当者・期限）は今のまま。新しい項目は追加しない。

## 実装時の留意点（`CLAUDE.md` の規約より）

- 集計や絞り込みは `src/lib/` の関数に置き、ページには表示の処理だけを書く。
- ロジックを追加したら `tests/` に単体テストを追加する。期限の境界（今日・7日後・8日後・昨日）を必ず含める。
- 新しい外部ライブラリは追加しない。DB のスキーマ変更は不要の見込み。
