# 要件: チーム進捗ダッシュボード

## 1. 背景と目的

- 社内向けの業務改善（売り物ではない）。2 週間以内に最初の版を使い始める。
- 依頼者・主な利用者: 開発チームのリーダー（佐藤）。メンバー（鈴木・田中）も閲覧してよい。チームは 3 人。
- 現状: 毎週月曜朝の定例（15 分）で、各自に口頭で状況を聞いて回っている。タスク一覧は全件が並ぶだけで、誰がどれくらい抱えているか、どれが遅れているかがひと目で分からない。
- 目的: 定例で、遅れているタスクと各自の抱えている量を画面ですぐ把握し、早く手を打てるようにする。
- 成功の目安: 定例で口頭の聞き取りに頼らず、この画面を見ながら進められる。

## 2. スコープ

### 含める

新しい画面「進捗ダッシュボード」（ログイン必須、ログインしたユーザーなら誰でも閲覧可）。次の 4 つを数字と表で表示する。

1. **担当者別の状態別件数の表**
   - 行: 担当者（全ユーザー）。列: 未着手 / 進行中 / 完了 / 合計。
2. **期限切れタスク**
   - 件数と一覧。一覧の項目: タイトル、担当者、期限、期限から何日過ぎたか。
   - 対象: 期限が今日より前で、ステータスが完了でないもの。過ぎた日数の多い順に並べる。
3. **期限が近いタスク**
   - 期限が今日を含めて 7 日以内（今日〜今日+6 日）で、ステータスが完了でないもの。期限の早い順。
   - 期限切れとは別の表にして区別できるようにする。
4. **今週（月〜日）に完了した件数（担当者別）**
   - 今週の月曜 00:00 から日曜 24:00 の間に、ステータスを「完了」にした件数を担当者ごとに表示する。

あわせて、実現に必要な次の変更を含める。

- **完了日時の記録**: ステータスが「完了」に変わった日時を DB に保存する（`tasks` に列を追加。マイグレーションは末尾に新しい番号で追加）。
  - 完了以外から完了に変わったとき: 日時を記録する。
  - 完了から他の状態へ戻したとき: 日時を消す。
  - 完了のまま他の項目だけを変えたとき: 日時は変えない。
  - 作成時から完了のタスクは、作成時刻を完了日時とする。
  - 既存の完了タスク（マイグレーション前に完了していたもの）の完了日時は不明（NULL）とする。今週の完了数には数えない。
- ダッシュボードへの導線（既存のタスク一覧などからリンクする）。

### 含めない（今回やらない）

- 状態変更の履歴（誰がいつ変えたか）
- メール・Slack などの通知、定期レポート
- グラフ、ガントチャート、バーンダウンチャート
- 過去からの推移（先週との比較など）
- 進捗率・工数など、入力項目の追加（判定は今のステータスと期限だけで行う）
- 新しい外部ライブラリの追加

## 3. 仕様の詳細

- **「今日」と「今週」の基準**: 日本時間（Asia/Tokyo）。週は月曜始まり。期限は日付（YYYY-MM-DD）なので、今日の日付との比較で判定する。
- **期限切れ**: 期限 < 今日 かつ ステータス ≠ 完了。期限が今日のものは期限切れに含めない（「期限が近い」に入る）。
- **期限が近い**: 今日 ≤ 期限 ≤ 今日+6 日 かつ ステータス ≠ 完了。
- **過ぎた日数**: 今日 − 期限（日数）。
- **担当者の表示名**: ユーザーの表示名（佐藤など）を使う。
- **0 件のとき**: 「期限切れのタスクはありません」のように日本語で空の状態を表示する。担当者別の表は、タスクが 0 件の担当者も 0 で表示する。
- **URL**: `/dashboard`（仮）。
- **API**: 画面のみ。新しい API は作らない（必要になったら後で足す）。
- **既存機能への影響**: 既存の `/tasks`、`/tasks/:id`、`/api/tasks*` の見た目と仕様は変えない。ただし PATCH／POST で完了日時が記録される副作用がある。

## 4. 実装時の制約（CLAUDE.md の規約に従う）

- 集計・絞り込みは `src/lib/` の関数に置き、ページは表示だけを書く。
- 画面の文言は日本語。新しい外部ライブラリは追加しない。
- スキーマ変更は `src/lib/db/migrations.ts` の末尾に新しい番号で追加する（既存は書き換えない）。
- SQL はプレースホルダを使う。
- ロジックを追加・変更したら `tests/` に単体テストを追加する。特に、境界日（期限が今日、今日+6 日、今日+7 日）、週の境界（月曜 0 時・日曜末）、完了日時の記録・解除を確認する。
- 依頼の範囲にとどめる。

## 5. 受け入れ条件

1. ログインしていないと `/dashboard` を見られない（ログイン画面へ遷移する）。
2. 担当者別の状態別件数が、DB のタスクと一致して表示される（全ユーザー分、0 件も表示）。
3. 期限切れ一覧に、条件を満たすタスクだけが、担当者・期限・過ぎた日数つきで表示され、件数が出る。
4. 期限が近い一覧に、今日を含めて 7 日以内の未完了タスクだけが表示され、期限切れとは別の表になっている。
5. ステータスを完了にすると完了日時が記録され、今週の完了数（担当者別）に反映される。完了から戻すと数えられなくなる。
6. `npm run typecheck`、`npm test`、`npm run build` がすべて通る。

## 6. 前提と未確定の点

依頼者の回答で決まっていること以外は、次の前提を置いた。違えば指摘してほしい。

- 全員が全員のタスクを見られる（権限の区別なし）。
- 完了日時の対象は、今回の変更以降に完了にしたものから。過去分の遡及はしない。
- 「期限が近い」の 7 日は、期限切れを除いた「今日〜今日+6 日」。
- 画面は 1 ページにまとめる（タブ分けや絞り込み機能は付けない）。
- 実現方法は、既存のスキーマに完了日時の列を 1 つ足し、ページ内で集計して表示する最小の構成とする（別画面の集計 API や履歴テーブルは作らない）。

### D3: 運用手順（保存先の指定）

- `DATABASE_PATH` を指定しないと DB は `:memory:` で、サーバーの再起動のたびに初期データへ戻る。完了日時も消え、「今週の完了数」が成り立たない。
- 実運用では必ずファイルを指定して起動する（例: `DATABASE_PATH=/var/lib/poc-app/tasks.db npm start`）。保存先は書き込み可能で、定期的にバックアップされる場所にする。
- 初期データの投入は、ユーザーが 0 人のときだけ行われる。既存のファイルに対して再投入はされない。
- マイグレーションは起動時に自動で適用される。初めて新しい版を起動する前に、DB ファイルをコピーしておく。
- 本番への反映は、実施前にユーザーの承認を得る（プロジェクトの規約）。
- **公開範囲**: 社内ネットワーク内だけで公開し、外部には出さない。初期ユーザー（sato / suzuki / tanaka）の共通パスワードは初期値のままで、変更機能は今回は無い（リスクとして受容。第 2 版の候補）。HTTPS で運用する場合は、Cookie に `secure` 属性を付けることを検討する。
- **権限**: ログインした 3 人は、誰のタスクのステータスも変更できる（リスクとして受容。メンバーが増えたとき、または誤操作が起きたときに見直す）。
