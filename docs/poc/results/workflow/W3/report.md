- 依頼者は人ではなく、定型回答シートだけを根拠に答える回答役（別の `claude -p`）です。候補の質問の聞き方で答えの詳しさが変わる余地があり、回答役が質問をどう数えたか（確認・案の選択も 1 件）も LLM の判定です。回答はすべて `raw/` の `qa-*.json` に残しています。
- 定型回答シートに「実装に進んでよいか」への答え方が無く、3 試行が実装まで進みました。この 3 試行は費用・時間が要件づくりだけの分より大きくなっています。
- 採点者は人ではなくサブエージェント（同じモデル系統）です。2 名の差が大きかった項目（隠れ要件 4 点以上、ほか 3 点以上）はありませんでした。
- 回答のやり取りは試行全体で最大 10 回としましたが、上限に達した試行はありませんでした（最多は gstack の 6 回）。
- 「使われた Skill」の欄は Skill ツールの呼び出しだけを数えています。スラッシュコマンド（`/feature-dev`・`/office-hours`・`/ce-brainstorm` など）で読み込まれた手順は数えていないため「—」になっていますが、生ログでは各コマンドの手順書を読み込んで進めていたことを確認しました。

## 判断の記録

- **定型回答の与え方**: 回答を課題文に連結すると、隠れ要件が最初から全部見えてしまい、W3 の目的（質問で引き出せるか）を測れない。そこで、候補が質問したときだけ、別の回答役（`scripts/poc/answer_w3.py`。ツールなし・設定なし・専用 HOME・作業用コピーの外で動く `claude -p`）がシートから答え、次のメッセージとして同じセッションに返す方式に固定した。全候補で同じ回答役・同じシート・同じルール（聞かれたことだけ答える、シートに無いことは「お任せします」、案の確認には「はい」・複数案なら「推奨の案で」）を使った。
- **質問用のツールを外した**: 無人の `claude -p` では `AskUserQuestion` に答えられないため、W3 では `--disallowedTools AskUserQuestion` で外し、課題文で「質問はメッセージの本文に書く」と指示した。gstack・Compound Engineering の手順書は質問ツールを前提にしているが、どちらも本文での質問に切り替えて進められた。
- **採点する文書**: 候補ごとに要件の置き場所が違う（Superpowers は `docs/superpowers/specs/`、Compound Engineering は `docs/brainstorms/` など）ため、比較できるよう課題文で `REQUIREMENTS.md` へのまとめを指示した。全 9 試行が `REQUIREMENTS.md` をコミットしたので、代わりの文書は使っていない。
- **実装まで進んだ 3 試行の扱い**: 採点手順では「指示に反してアプリのコードを変更した試行はスコープ判断の SC4 を 0 点」と決めていた。Superpowers #1・Feature Dev #2・gstack #2 は、いずれも「実装に進んでよいか」と依頼者に確認し、回答役が「はい」と答えた後に実装している。依頼者が許可した変更は「指示に反した」変更ではないと判断し、SC4 の 0 点は適用しなかった（`score_w3.py` で、確認に「はい」と答えた後の変更を除外）。採点は文書だけで行い、実装の中身は評価していない。W4 以降でシートを作るときは、実装の可否の答え方を決めておく。
- **費用の上限**: W1 の候補ごとの平均費用 × 5 を、1 試行の打ち切り額（`POC_MAX_TRIAL_USD`）にした（baseline $0.77、Superpowers $0.85、Feature Dev $0.86、gstack $2.29、Compound Engineering $8.92）。上限に達した試行は無い。回答役の費用（1 試行あたり $0.05〜$0.18）は候補の費用に含めず、別に記録した。
- **試行の並列度と順番**: 2 本並列で実行した（W4 の試行と並行するため、コーディネーターの指示どおり 1〜2 本に抑えた）。並びは、1 本目のレーンが Superpowers #1 → gstack #1 → Compound Engineering #2 → Feature Dev #2、2 本目のレーンが Feature Dev #1 → Compound Engineering #1 → gstack #2 → Superpowers #2。W3 はサーバーを起動しないので、ポートの取り違えは起きない。
- **試行間の独立性**: `grade.py` の検出（自分の作業用コピーの外への参照）で引っかかったのは gstack #1 の 1 件だけだった。`cat ../../../../docs/github-writing.md`（リポジトリの文書の書き方ルール）を含む連結コマンドで、許可リストにより拒否されており、実行されていない。正解データ（`docs/poc/answer-key/`）・ほかの試行・結果への参照は無かった。なお、これは検出であり、完全な防止ではない（Bash の `cat`・`ls` などは、読むパスを制限できない）。
- **W1・W2 との後方互換**: `run-trial.sh` の変更は、課題文末尾の定型文、手順、質問ツールの除外、回答のやり取り、`REQUIREMENTS.md` を完了の条件に加える処理のすべてが `W3` のときだけ働く。W1・W2 を同じ手順で再実行したときの動きは変わらない。

## 次の対応

- W4 以降で依頼者役を使う場合は、定型回答シートに「実装に進んでよいか」「範囲を広げる案」への答え方を加えてから試行する。
- W3 の結果からは、要件を固める工程は候補なしでも十分にこなせ、候補の主な違いは「最初に幅広く聞くか、1 問ずつ深掘りするか」でした。総合判定（§4.3）では、W3 の重み 10% のとおりに扱う。

### 計算方法と判断の記録

- 品質 = （隠れ要件 40 + 要件文書の質 25 + スコープ判断 20）の得点 ÷ 85 × 100。
- 効率 = 費用 50 + 時間 30 + 介入 20。費用・時間は baseline（$0.1702・78 秒）に対する倍率で、2 倍以下 = 満点、3 倍以下 = 80%、5 倍以下 = 60%、10 倍以下 = 30%、10 倍超 = 0。介入は 0 回 = 20、1 回 = 10、2 回以上 = 0。
- 質問の回数は効率から引かない（参考値）。品質の差が、比べる 2 候補の 2 回の差（ばらつき）の大きい方以下なら「差なし」とする。
- 定義は docs/poc/PLAN.md §4.4。計算は scripts/poc/two_axis.py。従来の総合点・順位はこの節では変えない。
- 「質問の負担」は品質にも効率にも入れない（参考値）。
