## 結論

- **規約として置いても効いた。** 日曜に翌週を指す不具合（d1・d3 の B2）を 6 回中 5 回見つけた。比べる相手（W24 の Sonnet）は、指示なしで 0/6、依頼文に指示を書いて 6/6。見つけた不具合の計は 48 中 47（指示なし 42、依頼文 48）。
- **9 本すべてでコードを動かした**（`node` の呼び出しは計 23 回）。W24 の指示なしの Sonnet は、9 本中 3 本・各 1 回だけだった。
- **費用は依頼文に書いたときとほぼ同じ**（1 本 $0.25。指示なし $0.22、依頼文 $0.28）。
- 開発フローへの意味（提案）: 雛形の `AGENTS.md` の規約（各プロジェクトの `CLAUDE.md` から読み込まれる）に、次の一文を足すことを提案する。W24〜W26 の結果を根拠にでき、配る形で効くことも確かめた。

  > コードをレビューするときは、疑わしい箇所（境界値・日付や時刻・並び順・状態の共有など）を読むだけで判断せず、小さな再現スクリプトを書いて実際に動かし、結果を確かめてから指摘する。
  >
  > 理由: 読むだけでは気づきにくい境界の不具合を、動かすと見落とさなくなり、費用の増え方は小さい（PoC W24〜W26）。

  あわせて、レビューを行うエージェントがコードを動かせる権限と、本番のデータに触れない環境（テスト用の DB など）を用意する必要がある。

  **追記（W27 の後）:** これまでの試行で実際に起きた不具合（W27）では、この一文の効果は無かった（見つけた数は同じで、費用は約 1.4 倍）。実際の変更では指示が無くてもコードを動かしていて、見落としたのは本番の起動でだけ出る不具合と、要件との照合が要る不具合だった。足すかどうかは、「関数を呼べば確かめられる種類の不具合（日付・曜日の境界など）の見落としが減る」効果と、費用の増え方を比べて判断する。
