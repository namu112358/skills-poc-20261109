# W12 短い要件から、運用まで考えて作る — 結果レポート

- **結論（標準なし・Sonnet・きれいな初期状態）: 品質はどの条件も 88〜92 点で、プラグインの上乗せは試行のばらつき（2 回の差 1.5〜4.3 点）の範囲に収まった。** baseline（候補なし）は 90.2 点で、Superpowers 91.6・Feature Dev 91.5・Compound Engineering 90.3・gstack 88.4。全条件が実装の前に依頼者に質問し（ask-po が中心）、マイグレーション 20/20・運用 10/10 を満点にした。差が出たのは隠れ要件の一部（月末の期限・絞り込み・借りている人）と、同じ実行の中での再試行（R01〜R04）。
- **費用対効果**: 同じ品質の中では baseline（$0.85・4.5 分）が最も安く速い。Feature Dev（$2.2・9 分）と Superpowers（$2.0・9 分）は 2〜3 倍、gstack は 5 倍（$4.6・12 分）、Compound Engineering は 20 倍（$17・30 分）。
- **汎用の開発標準（23 項目）を CLAUDE.md に足しても、品質はほとんど変わらなかった**（条件ごとの差 −4.1〜+4.5、5 条件の平均 +0.1）。標準をよく守ったのは gstack（+4.5。外部呼び出しの堅牢さが 1 回で満点）と Feature Dev（+1.2）。Superpowers は −4.1（隠れ要件の取りこぼし）。
- **採点項目をそのまま書いた規約（baseline-conventions、参考値）は、堅牢さを 15/15 に上げた**（baseline 9.6）。規約に答えが書いてある場合の上限の目安で、費用対効果の結論には使わない（ユーザー判断）。
- **Haiku（各 1 回）では baseline が 83.3 点に下がり、プラグインの上乗せが大きくなった**（Feature Dev +8.2、Compound Engineering +5.1、gstack +3.2、Superpowers +2.0）。「モデルが強いと上乗せが効きにくい」という仮説を支持する向きの結果だが、1 回ずつでばらつきを測れていない。
- **乱れた初期状態（各 1 回）では、Feature Dev 以外が 3〜5 点下がった**（baseline −5.2、Superpowers −4.7、Compound Engineering −4.3、gstack −3.2、Feature Dev +1.6）。下がったのは主に隠れ要件（業務）で、引き出した隠れ要件の数が減った（Superpowers 12.5 → 7、gstack 8.5 → 5）。古いログ関数や UTC の日付関数に引きずられた例は無く、全員が logger と日本時間の関数を使った。上乗せは Feature Dev だけが大きい（+8.1）。
- 測り方の感度: 堅牢さのテストを旧版（台本を 1 回の実行にまとめた形）で計算すると、gstack・baseline などが 4〜7 点下がり順位が入れ替わるが、「Sonnet のきれいな初期状態では上乗せがばらつきの範囲」「Haiku では Feature Dev の上乗せが大きい」という結論は変わらない。
- 不正の点検: 正解データ・リポジトリ本体・他の試行・依頼者役の作業場所・/proc への参照と Web の使用は全試行で 0。依頼者役が聞かれていない項目まで明かした質問は 305 問中 39 問（13%）で、特定の条件に偏っていない（baseline は 14 問中 1 問）。
