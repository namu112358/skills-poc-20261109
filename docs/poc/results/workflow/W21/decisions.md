# W21 の判断の記録

- ユーザーの指示（2026-11-11）: 「レビュー系の Skills の PoC を。簡単なタスクではすべて同じ結果が出るので、興味深い結果が出るケースを」。比べる対象は「Claude Code 内蔵（`/code-review`）・PR Review Toolkit・自作の設計の原則のレビュー（`design-principles-review`）・`ce-code-review`・baseline」（ユーザー指定）。
- 続けて「コマンドは一任するので無人で回して」「終わったら、結果から次の PoC を自分で検討して進めて」。
- 進め方の判断は、人間の代理人の原則（`docs/poc/proxy/principles.md`）でコーディネーターが決めた。

## 代理人の原則による判断

| ID | 問い | 決めたこと | 理由（原則） | 置いた前提 |
|---|---|---|---|---|
| R-D1 | 題材の作り方 | W9・W20 の題材は使い回さず、題材ごとに 1 つの力だけを測る作り物を 7 つ作る（差分の外・不具合なし・規約とテスト・日付の計算・紛れた不具合・指示への対応・設計だけ） | P6（何を測っているかを分けないと、差の理由を説明できない）・P5（7 つに絞る） | 作り物なので、実際の障害に当たるかは W20 の結果と合わせて読む |
| R-D2 | 正解の固定 | 題材ごとに、型検査・テストが通ることと、仕込んだ問題が実際に起きることをスクリプトで確かめてから正解を書き、試行の前に固定する | P6（確かめた不具合だけを正解にする） | — |
| R-D3 | 手順 | W20 と同じ 3 段（依頼 → レビューの道具 → 書き写し。新しい指摘は足させない）。`ce-code-review` には `base:HEAD` を渡し、深さの判定は道具に任せる | P5（W20 と比べられる形）・P6 | `depth:full` を付けると「道具の既定の動き」を測れなくなるため付けない |
| R-D4 | 子セッションの許可リスト | W21 だけ、全設定で `node`・`npx tsc`・`npm test` の実行を許可する（依存のインストールは許可しない） | P6（動かして確かめる力を測る題材 c4 がある）。CLAUDE.md の例外（子セッションの許可リストはコーディネーターが判断してよい） | 動作確認の試行で、CE が書いた再現スクリプトの `node` 実行が拒否された |

| R-D7 | 自作 Skill を試行に入れる | `principles` の設定だけ、作業用コピーに `design-principles-review` を入れる（baseline コミットより前に入れ、レビュー対象の差分には出さない）。ほかの設定には入れない | P6（比べる対象そのもの）。AGENTS.md の罠（自作の Skill は試行に入れない）は、条件を揃えるための決まりなので、対象の設定に限って入れる | — |

## 担当の判断・経過

- 作業の途中でユーザーから「無人で回せるように settings.json に必要なコマンドを書いて PR を出して」と指示があり、PoC とは別の PR として出した（[namu112358/skills-poc-20261109#54](https://github.com/namu112358/skills-poc-20261109/pull/54)）。
- 1 本目の動作確認（`ce-review` × c1）は、実行中に `run-trial.sh` を書き換えたため、スクリプトの読み込みが壊れて止まった（スクリプトの不具合ではない）。以後、試行の実行中は `run-trial.sh` を書き換えない。
- `judge_w20.py` の、2 回判定する資料の選び方（設定ごとに同じ数）は、試行 ID の分け方の誤りで全設定を 1 つとして扱っていた（W20 でも同じ）。W21 では直した版を使う。W20 の判定はやり直さない（2 回判定の一致率は 1.0 で、選び方の偏りは結論に影響しない）。
