W5（バグ修正）では、修正の正しさに差は出ませんでした。4 候補と baseline の全 9 試行が、報告された 3 件のバグをすべて根本原因から直し（隠しの E2E 8 件・隠しの単体テスト 3 件がすべて通過）、3 件それぞれに回帰テストを足し、元からある単体テスト 19 件も全部通りました。症状の場所と原因が離れたバグ（B3: 一覧に反映されない。原因は src/lib/ の一覧キャッシュ）でも、画面や Next.js のキャッシュを疑って手当てだけする試行はありませんでした。

採点方法

配点は PLAN.md §5.1 の W5、手順は試行前に固定した docs/poc/answer-key/W5/grading.md のとおり（scripts/poc/grade_w5.py → score_w5.py）。

  • 根本原因を正しく直せた数（50）: バグ 1 件ごとに 50/3 点。隠しの E2E（報告の症状が消えたか）と、src/lib/ の関数を直接呼ぶ隠しの単体テスト（原因の層で直ったか）の両方が通ったら「直せた」。
  • 回帰テストの追加（25）: バグ 1 件ごとに 25/3 点。候補が足したテストを、参照用のコード（仕込みバグ + 正解の修正）と、そこからバグを 1 つだけ戻したコードで実行し、前者で通り後者で落ちるテストがあれば「ある」。
  • 既存テストの維持（10）: 元からある単体テスト 19 件（候補が書き換えていても元の版）を試行のコードで実行した合格率 × 10。
  • 所要時間（15）: 15 ×（W5 の全試行の最短の時間 / 自分の時間）。壁時計の時間（elapsed-seconds）。

この結果の制約

  • バグ 3 件は、どれも原因が 1〜2 行で、コードを読めば一本道で辿れる規模でした。全試行が満点を取ったため、根本原因・回帰テスト・既存テストの 85 点分では差が付かず、点差は所要時間（15 点）だけから来ています。より深い調査が要るバグ（複数の原因が重なる、再現条件が揃いにくいなど）での差は、この結果からは分かりません。
  • 所要時間は 2 本並列で実行したときの壁時計の時間です。並列の相手によって数秒〜十数秒の揺れがあり得ます（Superpowers の 2 回は同じ 60 秒、gstack は 50 秒と 76 秒）。
  • B2（10 分でログインが切れる）は、サーバーの時計を進められないため、隠しの E2E では Cookie の有効期限が変わっていないことだけを確かめ、セッションの期限そのものは隠しの単体テストで確かめました。
  • 子セッションはサーバーのバックグラウンド起動などが許可リストに無く（W6 から許可する予定）、画面での確認は限られた形でしか行えていません。gstack の /qa のブラウザ機能は環境の制約で使えていません。
  • 各試行は 2 回（baseline は 1 回）だけで、ばらつきの評価には足りません。

判断の記録

  • 文言の切り替えによるやり直し: 最初は旧文言（「課題文に書かれていないことはお任せします」）で baseline を 1 回、ほかの 2 試行を途中まで実行した。コーディネーターから W4 以降は新文言（工程を省かずに進める）にすると連絡があったため、それらを止めて破棄し、main（#21）を取り込んでから 9 試行すべてを新文言でやり直した。全試行の raw/<ID>/task-suffix が new であることを確認した。旧文言の baseline の結果（55 秒・$0.17、3 件とも修正）はレポートに使っていない。
  • 費用の上限: 試行は W3 と同じ「W1 の候補ごとの平均費用 × 5」（baseline $0.77、Superpowers $0.85、Feature Dev $0.86、gstack $2.29、Compound Engineering $8.92）を打ち切り額にして実行した。途中でコーディネーターから、規模係数を使う上限（規模係数 × W1 平均 × 5、最大 $10）を使ってよいと連絡があった。W5 の規模係数は W5 baseline の実額 ÷ W1 baseline = $0.1675 ÷ $0.15 = 1.12 で、上限は baseline $0.84、Superpowers $0.95、Feature Dev $0.95、gstack $2.57、Compound Engineering $9.97 になる。実行時の打ち切り額はこれより低いが、打ち切られた試行は無く（最高額は Compound Engineering #2 の $0.66）、新しい上限でやり直す必要は無かった。
  • バグの決め方: 3 件とも「元からある単体テストでは見つからない」「再現手順だけで症状を確かめられる」ものにした。B3 は、最初に作った案（一覧キャッシュをモジュールの変数に持つ）だと、Next.js が画面と API Route で別々にモジュールを読み込むため、正しく直しても画面だけ古いままになることが試行前の確認で分かった。原因が 2 つ重なる状態は採点がぶれるので、キャッシュを DB の接続と同じく globalThis に持たせ、原因を 1 つにした。課題文の「新しく登録したときはすぐ出てくる」もこの形で正しいことを確かめた。
  • 課題文で指示しないこと: 利用者からの報告という形にしたので、原因の場所と、テストを足すことは課題文で指示していない。テストについては、全候補が読む poc-app/CLAUDE.md の規約 5（ロジックを変えたらテストを足す）に任せた。

  • 回帰テストの判定: 候補のテストを候補自身のコードでなく参照用のコードで動かすのは、候補が直した後のコードにバグを戻すパッチは当てられない（同じ行を書き換えている）ため。候補が新しく作った関数を import していて参照用のコードで動かない場合は採点者が読んで判断する手順にしていたが、今回は該当なし（ref_failures は全試行で 0）。

計算方法と判断の記録

  • 品質 = （根本原因 50 + 回帰テスト 25 + 既存テストの維持 10）の得点 ÷ 85 × 100。
  • 効率 = 費用 50 + 時間 30 + 介入 20。費用・時間は baseline（$0.1675・45 秒）に対する倍率で、2 倍以下 = 満点、3 倍以下 = 80%、5 倍以下 = 60%、10 倍以下 = 30%、10 倍超 = 0。介入は 0 回 = 20、1 回 = 10、2 回以上 = 0。
  • 質問の回数は効率から引かない（参考値）。品質の差が、比べる 2 候補の 2 回の差（ばらつき）の大きい方以下なら「差なし」とする。
