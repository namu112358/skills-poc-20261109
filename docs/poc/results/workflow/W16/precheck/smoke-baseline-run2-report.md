二重通知の原因を 2 つ見つけて直し、コミットしました（`0931786`）。typecheck とテスト 54 件はすべて通っています。実際の通知サービスや本番に対する確認はしていません。

## 原因
1. **ジョブの同時実行（ログで確認できた原因）**
   - 11/8 の朝、通知サービスの応答が遅くなり、ジョブが 1 分以上かかりました（73 秒、65 秒）。
   - 開始の約 1 分後に 2 回目の呼び出しが来て、前の実行が終わる前に同じ対象へ送っていました。
   - 11/8 の MI-0030 の takahashi 宛てが、約 0.16 秒の間に 2 通送られています。
   - 旧コードは「送信済み」の記録しか見ておらず、別の実行が送信中でも通ってしまいました。
2. **再試行時の Idempotency-Key**
   - 通知クライアントが、再試行のたびにキーを変えていました。
   - タイムアウトで応答が返らなくても、通知サービスが受け付けていることがあります。その場合、再試行が別の通知として二重に届きます。
   - 通知サービスの仕様では、断られた要求は記録されません。そのため、同じキーで再試行しても安全です。
   - 11/8 の matsumoto 宛てや yamada 宛てのようにタイムアウト後に再送した分は、ログだけでは二重かどうか判定できません。

## 修正
- `src/lib/calibration-reminders.ts`
  - 送信済みの確認と送信中記録の作成を 1 つの SQL 文にしました。別の実行が送信中の間は送らず、スキップします。
  - 途中で止まった送信中の記録は、30 分後に送り直します。
- `src/lib/notify-client.ts`: 再試行でも同じ Idempotency-Key を使います。
- テスト
  - 実行が重なる場合と、古い送信中記録を送り直す場合のテストを追加しました。
  - `tests/notify-client.test.ts` のキーの期待値を、新しい仕様に合わせて変えました（`k1-1` を `k1` に、`["k2-1", "k2-2", "k2-3"]` を `["k2", "k2", "k2"]` に）。
- `docs/operations.md`: cron の再呼び出しに関する注意を追記しました。

## 残っている課題
- **2 回目の呼び出しの出どころ**
  - 毎回、開始のちょうど約 61 秒後に来ています。cron のタイムアウト後のリトライか、前段のプロキシのようです。
  - アプリ側では二重に送らなくなりましたが、運用チームに確認をお願いします。
- **shimizu 宛ての失敗**
  - MI-0030 の宛先 shimizu は、毎日「recipient not found」（400）で失敗しています。
  - 二重通知とは別の問題です。通知サービス側に shimizu が登録されていないか、利用者 ID が違っている可能性があります。
- **すでに届いた二重通知**
  - 取り消しはできません。
  - 修正は次回の実行から効きます。リリース前に DB のバックアップを取り、再起動して反映してください。
