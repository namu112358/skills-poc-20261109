校正期限の通知が二重に届く原因は 2 つあり、どちらも修正してコミットしました（`7d28862`）。型チェックとテスト 54 件は通っています。

## 原因（ログから確認）
1. **ジョブが並行して 2 回動いていた。**
   - 11/8 と 11/9 は、7:30 JST の実行の 61 秒後にもう一度 `job.started` が出ています。
   - 通知サービスが遅くて 1 回が 65〜73 秒かかったため、呼び出し側が再実行したと見ています。
   - 先の実行はまだ「送信中」の記録で、後の実行の「送信済みか」の確認に引っかからず、同じ通知を送っていました。
   - 11/8 の MI-0030 と takahashi には、0.16 秒差で 2 通出ています。
2. **タイムアウト後の再送が別のキーになっていた。**
   - 通知サービスの仕様では、応答が返らなかった要求も送られていることがあり、再送には同じ `Idempotency-Key` を使うよう求めています。
   - アプリは試行ごと・実行ごとに別のキーを付けていたため、タイムアウト後の再送が二重になる恐れがありました。

## 修正
- 実行中に再度呼ばれたら、何も送らずに `409` を返します（`job.skipped` ログも出します）。
- キーを、計測器・種類・期限・送り先から決まる値にしました。再試行でも次回の実行でも同じキーになります。
- 同時実行の禁止と同じキーの使い回しについて、テストを追加しました。旧キー形式（`k1-1` など）を前提にしていた通知クライアントのテスト 2 件は、通知サービスの仕様に合わせて更新しました。
- `docs/operations.md` に、409 は異常ではないことと、cron 側で短い時間で打ち切って再実行しないことを追記しました。

## 残っている点
- **運用チームへの確認:** 1 分後の再呼び出しの出どころ（cron の設定やラッパーのリトライ）はログからは分かりません。確認をお願いします。
- **`shimizu` への通知が毎回失敗:** MI-0030 の管理者 `shimizu` は通知サービスで `recipient not found`（400）になり、毎日失敗しています。情報システム課に ID の確認を依頼してください（今回の二重送信とは別件）。
- **すでに届いた分:** 重複して届いた通知は取り消せません。
