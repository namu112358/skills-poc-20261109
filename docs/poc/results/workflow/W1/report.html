所見

  • 全候補が同じ構成で実装しました。変更は src/lib/tasks.ts（listAssignees / isAssignee / 絞り込み条件）、src/app/tasks/page.tsx（選択欄）、tests/tasks.test.ts の 3 ファイルで、コードの追加は 29〜38 行でした。CLAUDE.md の規約（lib に処理を置く、型ガードで検証、テストを追加、ライブラリを足さない）も全試行で守られています。
  • Superpowers は 2 回とも test-driven-development Skill が自動で発火し、テストを先に書いて失敗を確認してから実装しました。結果は baseline と同じでしたが、費用の増加は約 1 割にとどまりました。brainstorming は発火しませんでした（課題が明確なため）。
  • Feature Dev は /feature-dev:feature-dev が動きましたが、「無人のため確認・設計案の比較・レビューのフェーズを省略」と判断し、サブエージェント（code-explorer / code-architect）を一度も使いませんでした。W1 では実質的に baseline と同じ動きで、特長は出ていません。
  • Compound Engineering は /ce-plan の中で計画書を作り、ce-doc-review（サブエージェント）で計画をレビューしたうえで、そのまま実装・コミットまで進めました。そのため続く /ce-work は「作業なし」で終わりました。作業ブランチも自分で作ります。/ce-code-review は、範囲判定のスクリプトが権限で拒否されたため簡易レビューに切り替え、指摘はありませんでした。
  • gstack は 50 以上の Skill が読み込まれましたが、実装の段階ではどの Skill も自動で発火せず、通常の実装と同じ内容になりました（gstack の初期設定では、自動で発火するのは /office-hours・/review・/qa・/ship だけ）。読み込まれる Skill が多い分、実装段階だけで baseline の約 2 倍の費用（約 $0.32）がかかりました。続く /review は、作業ブランチが無く master に直接コミットされていたため、スキルの規定どおり「レビュー対象なし」で停止しました（1 回目は代わりに差分を自分で読み直し）。外部送信の記録（gstack-egress list）は 2 回とも「no receipts」でした。
  • 拒否された操作は、baseline・Superpowers・Feature Dev が 1〜2 件（Bash でのファイル書き換え。Edit ツールで代替）だったのに対し、Compound Engineering は 7〜10 件でした。内訳は、プラグイン自身のスクリプトの実行と、動作確認のための開発サーバー起動です。対話で使う場合は人が承認する操作で、無人実行では不利に働きます。

採点方法

100 点満点（計画書 §5.1 の W1）。

  • 受け入れ 50: 隠しの E2E 6 件 × 5 点、型チェック・単体テスト・ビルド 10 点、規約（テスト追加 5 点・ライブラリを足さない 5 点）
  • 時間・費用 30: 費用 15 × 最安 / 自分、時間 15 × 最速 / 自分（W1 の全試行で比較）
  • 過剰さ 20: コード追加 41〜80 行 −4・81 行以上 −8、テスト以外の新規ファイル 1 つ −2（最大 −4）、計画書などの文書・管理ファイルをコミット −4、依頼範囲外の変更 −4

採点スクリプト: scripts/poc/grade.py、scripts/poc/score_w1.py。受け入れテスト: docs/poc/answer-key/W1/acceptance.cjs。

この結果の制約

  • 無人（ヘッドレス）実行です。確認の質問に答えられないため、対話を前提にしたフェーズ（Feature Dev の確認・設計比較、Superpowers の brainstorming など）は評価できていません。
  • 権限を絞っています。全許可での子セッション起動は安全判定で止められたため、編集と決まったコマンドだけを許可しました。プラグイン自身のスクリプトや開発サーバーの起動が拒否されることがあり、Compound Engineering に不利に働いた可能性があります。
  • gstack はブラウザなしで入れています。setup 中の Chrome for Testing のダウンロード（cdn.playwright.dev）が環境のネットワーク制限で失敗するため --no-browser を付けました。W1 では使いませんが、ブラウザを使う W6 の前にこのホストの許可が必要です。
  • 試行はデフォルトブランチ（master）上で始めています。作業ブランチを前提にする gstack の /review が「レビュー対象なし」になりました（Compound Engineering は自分でブランチを作成）。W2 以降は全候補とも作業ブランチの上で始めます。
  • 採点は自動テストと Claude（このセッション）による差分の確認です。人のブラインドレビューは未実施です（W1 の配点には含まれません）。
  • 試行回数は候補ごとに 2 回、baseline は 1 回です。
  • モデルは claude-sonnet-5-5 に固定しています。この実行環境に元からあるプラグイン・Skill（cc-plugin-* など）も全試行で読み込まれています（条件は全試行で同じ）。GitHub MCP は認証情報がないため外しています（W1 では不要）。
  • 最初の実行で、ハーネスに 3 つの不具合（プラグインの参照ファイルを読めない、Feature Dev のコマンド名の誤り、費用の二重計上）が見つかりました。修正後に全試行をやり直した結果だけを載せています。

計算方法と判断の記録

  • 品質 = （受け入れ 50 + 過剰さ 20）の得点 ÷ 70 × 100。
  • 効率 = 費用 60 + 時間 40（この W には介入の仕組みが無い）。費用・時間は baseline（$0.1548・42 秒）に対する倍率で、2 倍以下 = 満点、3 倍以下 = 80%、5 倍以下 = 60%、10 倍以下 = 30%、10 倍超 = 0。
  • 質問の回数は効率から引かない（参考値）。品質の差が、比べる 2 候補の 2 回の差（ばらつき）の大きい方以下なら「差なし」とする。
  • 定義は docs/poc/PLAN.md §4.4。計算は scripts/poc/two_axis.py。従来の総合点・順位はこの節では変えない。
