# レビュー用 Skill の比較のまとめ（W9・W20〜W34）

- 最終更新: 2026-11-12。個々の結果は各 W の `report.md`（`docs/poc/results/workflow/W<番号>/`）にある。
- **ここに書く答えは暫定**。各組 1〜4 回、題材は poc-app（Next.js + TypeScript + SQLite）の上の作り物 14 個と、これまでの試行で実際に起きた変更 4 つ。子セッションのモデルは主に Sonnet。

## 結論

- **レビュー用の Skill を足しても、見つかる不具合はほとんど増えない。** 道具なしと Skill は、ほぼ同じ数を見つけた（W9・W20〜W23・W34）。弱いモデル（Haiku）の道具なしでも同じだった（W22・W23）。
- **Skill で変わるのは、雑音・費用・直した後の振る舞い・指摘の書き方。** 設計を見る Skill は作りすぎを消す方向にわずかな利点があり、内蔵 `/code-review high` は雑音が最も多く、指摘どおりに直させると正しかった本体まで壊した（W34）。
- **見落としを減らしたのは、Skill ではなく、依頼の中で「何を確かめ、確かめた結果をどう書くか」を具体的に頼むこと**（W24〜W32）。ただし、今のモデルが合意した要件のとおりに作った変更では、そもそも要件に反する不具合はまれだった（W33）。残る問題の多くは「誰も聞かなかった隠れ要件」で、レビューでは見つけようがない。
- **細かすぎて時間がたつと落ちるテスト（初期データの件数・文言の決め打ち）は、どの設定のレビューでもほぼ直らない**（W34）。テストの書き方の決まりを明文化する方が効きそう（未決定の提案）。

## Skill ごとの強み・弱み

| 設定 | 強み | 弱み | 根拠 |
|---|---|---|---|
| 道具なし（Sonnet。Haiku でもよい） | 見つける数は Skill と同じ。最も安く速い（1 本 $0.2〜0.4。Haiku は $0.02〜0.03） | 重さ・出力の形が毎回変わる。作りすぎを消すのは 2 回中 1 回 | W21〜W23・W34 |
| 内蔵 `/code-review high` | 導入が要らない。ほかに無い観点（消した行が守っていた決まり、呼び出し元の grep、対症療法か根本修正か）。時刻・時差・処理時間に頼るテストを最も頑丈にした | **雑音が最も多い**（「最低 5 件を目標、検証しない」手順。不具合の無い差分でも 9〜10 件）。要件の抜けに弱い（実際の不具合で 9 件中 1〜3 件）。**指摘どおりに直させると、正しかった本体まで変えて壊した**（2 回とも） | W20・W21・W34 |
| PR Review Toolkit `/review-pr` | 実際の不具合で見つけた数が最多の組（9 件中 8 件）。作りすぎを 2 回とも消した。既定では費用が道具なしに近い（$0.3〜0.5） | Sonnet は専門エージェントの起動を省く（14 本中 13 本）。起動を明示しても見つける数は同じで、細かい指摘と費用（約 3.5〜4 倍。一部のエージェントは Opus 指定）が増え、本体を壊すこともあった | W20・W21・W22・W34 |
| `design-principles-review`（自作） | 作りすぎを 2 回とも消した。指摘に重さが付き、書き方がそろう。指摘どおりに直させても壊さなかった | 不具合探しは対象外。設計の問題を見つける数は道具なしと同じ。時間は約 1.5 倍 | W21・W34・Skill の評価ケース |
| Compound Engineering `ce-code-review` | **最も静か**（誤った指摘が最少。`depth:full` は 0）。直させても壊さなかった | **最も高い**（$0.37〜0.6、`depth:full` は $0.8〜1.6）。小さい差分では軽い型になり、実質は道具なし。`depth:full` を渡しても 14 本中 10 本で全員を起動しなかった | W21・W22・W23・W34 |
| （参考）Superpowers `requesting-code-review` | 実際の不具合で `/review-pr` と同じく 9 件中 8 件 | 比べたのは W20 の 1 回だけ | W20 |

## 使うタイミング（提案。標準の手順にするかは未決定）

| タイミング | 使うもの |
|---|---|
| 実装中のセルフレビュー（毎回） | 道具なし（安く済ませるなら Haiku）。日付・境界を扱う変更では「疑わしい所は関数を動かして確かめる」を依頼に入れる（W24） |
| 設計を変える変更（新しい抽象・ファイル構成の変更） | 上に `design-principles-review` を足す |
| PR を出す前 | 道具なしのレビューを 2 段に分ける。1 段目は「合意した要件を 1 つずつ照らす」（W29）、2 段目は「本番ビルドして起動し、変更した画面・API を開いて、状態コードとエラーを結果として書く」（W32）。2 つを 1 つの依頼に詰めると片方が手薄になる（W30・W31） |
| 重要・危険度の高い変更（認可・課金・データ移行など） | `ce-code-review` を足し、静かで確かな指摘を得る |
| 指摘を自動で直させる | `ce-code-review` か `design-principles-review` の指摘に限る。内蔵 `/code-review high` の指摘は、人が取捨してから直す（`--fix` は使わない） |

- **内蔵 `/code-review` は、既定では使わない。** 使うなら、指摘を人が取捨する前提の「見落としの洗い出し」として使い、自動で直させない。`max`（検証つきの最も重い段階）はまだ測っていない。
- 頼み方を足すと、費用は 1.2〜1.9 倍になる。不具合が入っていない変更では、そのまま上乗せになる（W33）。

## レビューでは見つからないもの

| 種類 | 効いた手段 | 根拠 |
|---|---|---|
| 本番でだけ出る不具合 | 依頼に「本番で起動して確かめ、状態コードとエラーを書く」 | W28・W32（0/47 → 4/4） |
| 合意した要件への違反 | 依頼に「合意した要件を 1 つずつ照らす」 | W29（0/6 → 2/2） |
| 日付・曜日の境界 | 依頼に「関数を動かして確かめる」（作り物の題材でだけ効いた） | W24〜W27 |
| 細かすぎて時間がたつと落ちるテスト（初期データの件数・文言の決め打ち） | レビューではほぼ直らない。テストの書き方の決まりを明文化する（提案） | W34 |
| 誰も聞かなかった隠れ要件 | レビューでは見つけようがない。実装の前に聞き出す | W33 |

| [W27](workflow/W27/report.md) | 同じ指示を実際の不具合で | 効果なし（実際の変更では指示が無くても動かしていた） |

| [W34](workflow/W34/report.md) | 指摘に沿って直させた後の質（作りすぎ・消えた振る舞い・弱いテスト・flaky なテスト。7 設定） | 差は小さい。設計を見る Skill は作りすぎを消し、`/code-review high` は直すときに壊した。件数・文言の決め打ちの flaky はどの設定も直せなかった |

## まだ測っていないこと

- 公式プラグインの Code Review（`code-review@claude-plugins-official`。GitHub の PR を読む前提）と、内蔵 `/code-review` の `max`。
- 再レビューの往復（2 回目以降のレビュー）。前回のレビューコメントの対応確認（`ce-code-review` だけが持つ機能）。
- テストの書き方の決まりを明文化したときに、細かすぎる flaky なテストが減るか。
- ほかの言語・フレームワーク。
