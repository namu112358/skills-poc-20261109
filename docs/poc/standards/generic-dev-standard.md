## 開発標準（全プロジェクト共通）

### 設計・コード

1. 既存のコードの書き方・構成・命名に合わせる。新しい書き方を持ち込むときは、理由を PR に書く。
2. 1 つの関数・モジュールには 1 つの責務を持たせる。業務の判断（ルール）と、入出力（DB・HTTP・画面）を分ける。
3. 同じ処理を複製しない。既存の部品で足りるときは、それを使う。
4. 名前は業務の言葉で付ける。略語は、プロジェクトの用語集や既存のコードにあるものだけを使う。
5. 日時は保存と内部処理で扱いを統一し、利用者に見せるときの時刻帯を明確にする。

### 入力・セキュリティ

6. 外部からの入力（画面・API・ファイル）は、受け取った場所で検証する。エラーは、利用者が直せる言葉で返す。
7. 認可は API ごとに確認する。画面に出さないことを、アクセスの制限の代わりにしない。
8. 秘密情報（トークン・パスワード・鍵）はコードやリポジトリに書かず、環境変数などの設定から読む。ログやエラー応答にも出さない。
9. SQL はプレースホルダーで組み立てる。文字列をつなげて組み立てない。

### データベース

10. スキーマの変更はマイグレーションで行い、本番のデータを失わないようにする。出荷済みの変更は書き換えない。
11. 既存の API の応答や項目を変えるときは、既存の利用者（画面・他システム）への影響を確かめ、互換性を保つか、移行の手順を書く。

### 外部連携・定期処理

12. 外部サービスの呼び出しは、失敗や遅延が起きる前提で設計する（相手の仕様書に従い、待ち時間の上限や失敗したときの扱いを決める）。
13. 定期的に動く処理は、何度動いても結果が同じになるようにし、途中で失敗しても次の回で回復できるようにする。

### エラー処理・ログ

14. エラーを握りつぶさない。処理を続けられる失敗と、止めるべき失敗を分けて扱う。
15. ログはプロジェクトの決まった仕組みで出す。運用で調べられるよう、何が・どの対象で・どうなったかが分かる形にする。

### テスト

16. 変更した振る舞いにはテストを書く。境界の値と、失敗するときの動きも確かめる。
17. 時刻・乱数・外部サービスに依存する処理は、テストで差し替えられるようにする。
18. 既存のテストを消したり弱めたりして通さない。

### UI・アクセシビリティ

19. 画面の文言は利用者の業務の言葉にする。操作の結果（成功・失敗）を画面で分かるようにする。
20. フォームには見出し（label）を付け、キーボードだけでも操作できるようにする。

### 進め方・レビュー

21. 要件があいまいなときは、依頼者に確認する。確認できないときは、置いた仮定を PR に書く。
22. PR には、何を・なぜ変えたか、どう確かめたか、残っている課題を書く。1 つの PR には 1 つの目的の変更だけを入れる。
23. 依存パッケージを足すときは、必要性・ライセンス・保守の状況を確かめ、PR に理由を書く。
