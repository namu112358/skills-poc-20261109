## ねらい

人は Issue に計画を書いてレビューを回すことに集中する。Ready になった Issue は、Claude が計画を基に実装して PR を出す。

## 状態（ラベル）

| ラベル | 意味 | 動く人 |
|---|---|---|
| `plan:draft` | 計画を書いている途中 | 人（Claude に下書きを頼んでもよい） |
| `plan:review` | 計画のレビュー中 | 人と AI のレビュー |
| `ready` | 実装してよい（これを付けることが承認） | 人だけが付ける |
| `in-progress` | 実装中 | Claude |
| `blocked:question` | 実装中に確認事項が出た | Claude がコメントして止まり、人が答える |
| PR が開く → マージで閉じる | `Closes #番号` | — |

- 実装を始めるきっかけは、書き込み権限のある人が付けた `ready` だけにする（Issue の本文は誰でも書ける入力として扱う）。Claude は `ready` を付けず、マージもしない。
- 起動の仕組みは 2 つの候補がある。① 公式の Claude Code GitHub Actions（Issue のラベルなどで起動）、② Claude Code のクラウドのセッションと定期実行の予定（`ready` の Issue を古い順に拾う。同時に動かす数を決めやすい）。`.github/workflows` を足すときはユーザーの承認が要る。

## Issue の様式に足す欄

- 計画: 手順・影響範囲・検証方法・やらないこと。小〜中は Issue の本文、大きな計画は `docs/plans/` への PR（行ごとにレビューできる）にして Issue からリンクする。
- **運用・互換の事情**: 他システム・端末・集計が読むもの、前の版に戻すことがあるか、止められる時間など。PoC（W14・W15）で多くの試行が落とした隠れ要件は、ほぼすべて「聞かれなかった運用の事情」だった。人が計画の段階で埋める。
- 大きさ（分割するか）と難しさ（どの道具を使うか）の判定。

## 大きさ: 小さな PR と Issue の分割

- PR の目安: 1 つの目的、変更はおよそ 300 行以内（テスト・生成物・ロックファイル・データは数えない）。
- 緩い制限: 同時にやったほうが効率が良いときは超えてよい。その場合は PR の本文の「まとめた理由」の欄に書く（片方だけでは動かない、分けると同じ変更を 2 回レビューすることになる、など）。CI では落とさず、超えたら `size:large` を付けて見える化するだけ。
- Issue の目安: 1 つの PR で終わる大きさ（多くても 2〜3 個）。大きければ、計画の時点で Claude が分割案を出し、親の Issue（目的と進み具合）と子の Issue（GitHub の sub-issues。1 つずつレビューして `ready` にする）に分ける。順番は本文に「#12 の後」と書く。
- 分け方の型:
  - 移行（W14）: 足す → 両方に書く → 既存のデータを埋める → 読む側を切り替える → 古いものを消す、の各段階を 1 つずつの PR にする。段階ごとにリリースでき、戻すこともできる。
  - 古いコードの改修（W15）: 今の振る舞いを固定するテストを先に 1 つの PR にし、改修をその後の PR にする。

## 難しさ: どの道具を使うか（大きさとは別の軸）

計画のときの判定の観点（1 つでも当てはまれば level 2 の候補）:

- 元に戻しにくい（本番のデータの書き換え・削除・外部への送信）
- 外部の利用者がいる（他システム・端末・集計が読む API や列）
- 触る場所にテストが無く、理由の書かれていない分岐がある
- 大量のデータ・同時更新・止められない処理が絡む
- 認証・権限・お金が絡む
- 要件に未決の点が多く、依頼者の事情を聞かないと決められない

| 段階 | 道具 | 使うとき | 上げ方 |
|---|---|---|---|
| level 0 | 標準のまま（プラグインなし） | 既定。仕様が明確・範囲が狭いもの（大きくても） | 実装中に難しさが分かったら、Claude が level 1 に上げてよい |
| level 1 | Feature Dev か Superpowers（計画の工程あり） | 要件があいまい・書かれていない落とし穴がありそうなもの | level 2 へは、Claude が止まってコメントし、人が承認する |
| level 2 | Compound Engineering（計画 → 実装 → レビュー） | 上の観点に当てはまり、人が計画のレビューで確定したもの | — |

- 根拠: 易しい課題（W1・W2・W5〜W9・W11）は、候補なしが品質で 1 位か差なしで、最も安い。あいまいな要件（W3）は Feature Dev と候補なしが同点 1 位、書かれていない落とし穴（W10）は Superpowers が 1 位。設計・移行・古いコード（W4・W14・W15）は Compound Engineering が 1 位だが、費用は候補なしの 4〜15 倍（1 本 $5〜14）。
- 「小さいが難しい」（本番のデータの列の型を 1 つ変える）は分割せずに level 2、「大きいが簡単」（画面の文言をまとめて直す）は分割して level 0。
- level 2 だけ人の承認を挟むのは費用のため。同時に回す本数の上限も決める。
- 段階の境目は各条件 2 回の試行からの目安で、ぶれも大きい。最初は level 2 を広めに取り、実績を見て絞る。

## 実装中に止まるきっかけ（`blocked:question` を付けてコメントし、止まる）

- 計画に無い DB の構造の変更や、外部の利用者への影響が必要になった
- 変更が目安を大きく超えそうで、分割したほうがよい
- テストが何度直しても通らない

## 既存の道具（2026-11-10 時点で確かめた範囲）

| 範囲 | 公式機能 | PoC の候補 | Anthropic のディレクトリ（未検証） |
|---|---|---|---|
| 計画を Issue にする | — | Compound Engineering `/ce-plan`（「Issue を作る」）、gstack `/spec` | IDD（`plan-to-issues`・`issue-creator`） |
| 計画のレビュー | — | Compound Engineering `ce-doc-review`、gstack `plan-*-review` | plan-review-skill |
| Ready の Issue を実装して PR にする | Claude Code GitHub Actions、クラウドのセッションと定期実行の予定 | Compound Engineering `lfg`（Issue の参照を受け取り PR まで） | IDD（`issue-resolver`・`auto-pilot`） |
| PR のレビュー | Claude Code の `/code-review`、Code Review（GitHub の PR で動く） | `/ce-code-review`、gstack `/review` | IDD（`issue-pr-review`） |

- 部品はそろっているが、ラベルの状態の流れ・Ready での起動・難しさによる道具の切り替えをまとめる公式の機能は無い。リポジトリの決まり（Issue の様式・ラベル・ワークフロー・CLAUDE.md）として組む。
