# W20 の設計: レビューの組み合わせの評価（E2）

- 作成: 2026-11-10（試行の前に固定）
- 目的: 開発フロー（Issue 駆動）のレビューの段で、どの道具・組み合わせを使うかを決める。記事「How the Claude Code team does code review」の「障害を評価の題材に」と、「Automating eval design and hillclimbing」の「採点を信じる前に確かめる（同じ出力を 2 回採点しても同じか）」に沿う。
- 進め方の判断は人間の代理人が決めた（`docs/poc/results/workflow/W20/decisions.md`）。

## 1. 評価セット（`docs/poc/answer-key/W20/cases/`）

PoC の試行で、採点とコードの確認で確かめた不具合を「障害」として集めた。正解は試行の前に固定し、結果を見てから変えない。

| 題材 | 差分 | 正解 | 種類 |
|---|---|---|---|
| c1 | W9 の差分（仕込み） | B1〜B10・おとり D1〜D5 | 作り物（比べる基準） |
| c2 | W19 superpowers 1 | B1（本番で詳細の画面が 500）・G1・G2（要件の抜け） | 実際の試行 |
| c3 | W14 superpowers 2 | B1（場所の ID で登録すると 500）・B2（自由入力を受け付ける）・B3・B4（古い列に場所の名前が入らない） | 実際の試行 |
| c4 | W15 gstack 2 | B1（ファイル内の重複の判定）・B2（BOM 付きを見分けない） | 実際の試行 |
| c5 | W15 compound-engineering 2 | なし（隠しテスト・黄金テストを全部通過） | 誤検出を測る |

- PR の説明（`pr.md`）は、依頼文・依頼者と合意した要件・候補のコミットメッセージ（署名の行は除く）から作った。要件の抜け・違反は、合意した要件に照らせば分かるようにした。
- 読み方の分かれるもの（依頼者役が「お任せします」と答えた扱いなど）は正解に入れない。

## 2. 比べる設定（候補）

| 設定 | 手順（同じ会話で順に） |
|---|---|
| `cr-low` | 依頼（PR の説明）を渡す → `/code-review low` → 出た指摘を REVIEW.md に書き写す |
| `cr-high` | 同じく `/code-review high` |
| `review-pr` | 同じく `/pr-review-toolkit:review-pr all` |
| `combo` | `/code-review high` → `/pr-review-toolkit:review-pr all` → 2 つの指摘を書き写す |
| `sp-review` | 同じく `/superpowers:requesting-code-review` |

- 書き写しの段では、新しい指摘を足させない（道具ごとの差を測るため）。
- レビュー対象は未コミットの差分として置く（`/code-review` の今の差分と、PR Review Toolkit の `git diff` の両方に出るよう、新しいファイルも登録する）。
- 5 題材 × 5 設定 × 2 回 = 50 本。モデル・許可リストは W9 と同じ。介入は最大 1 回。

## 3. 測るもの

| 指標 | 測り方 |
|---|---|
| 見つけた割合 | 一致した正解の数 / 正解の数（題材ごと・全体） |
| 誤った指摘 | おとりへの指摘 + 判定役が「事実と違う・直すと害がある」とした指摘 |
| 雑音 | c5 の指摘の数と、重要度「高」の好み・細かい点 |
| 費用・時間 | 1 回のレビューの実額 |

- 通るまでの往復の回数は、今回は測らない（上位の設定で次に測る）。

## 4. 判定

- 判定役（別のモデル）に、正解の一覧と REVIEW.md を、設定の名前を伏せて渡す（`judge_w20.py prepare`）。
- 全体の約 25% を 2 回判定させ、正解との一致が同じかを比べる（一致率が 8 割未満なら、判定の基準文を直して判定し直す）。
- 正解外の指摘で「本当らしい問題」「判断できない」は担当が読んで決める（`judge/manual.json`）。
