# 開発ワークフロー PoC — W13〜W17 の計画（コーディネーター）

2026-11-10 ユーザー承認（「◎・○ の案を計画して順次対応」）。W1〜W11 の結果から、候補（Skills・プラグイン）は「小さく仕様がはっきりした仕事」では素の状態（baseline）に費用で負け、「大きい・落とし穴がある仕事」（W4・W10）では品質で勝つ傾向が見えた。W13〜W17 は、候補が強みを出せそうな「途中で変わる・壊れやすい・調査が要る・横断する」仕事で比べる。

## 共通の条件

- 題材: W12 の「計測器の校正台帳」（`docs/poc/answer-key/W12/base.patch`。学習データに多い ToDo を避ける）。各 W は W12 の初期状態を土台に、その W に必要なものだけ足した初期状態を `docs/poc/answer-key/W1x/` に置く。W12 の PR がマージされる前に始める場合は、`origin/agent/poc-w12` から base.patch などを写して使い、出どころ（コミット）を設計書に書く。
- 条件: 5 条件 × 2 回 = 10 本（superpowers・feature-dev・gstack・compound-engineering・baseline）。全条件の作業用コピーで、アプリの CLAUDE.md の末尾に汎用の開発標準（`docs/poc/standards/generic-dev-standard.md` の区切りより下、全 W 同じ文面）を足す（2026-11-10 ユーザー承認。W12 の baseline-conventions は課題に合わせた答えを含んでいたため、W13 以降は使わない）。
- ペルソナ（依頼者役）: W12 の `ask-po` と回答シートの仕組みを使う。質問の回数・的中・聞き直し・実装前かを記録する。
- 試行の前に、参照実装・最短で動くだけの実装・半分だけの実装の 3 つで採点がはっきり分かれることを確かめ、コーディネーターの確認を受けてから試行を始める。
- 品質と効率の 2 本立て。効率は費用・時間の実額を主に示す（baseline 2 回の平均を基準にした点数は補助）。
- 費用の上限なし（1 試行 $30 超はコーディネーターに報告）。使用量の上限で失敗した試行は、リセット後にやり直して判断の記録に書く。
- 判断の経路・削除の運用・ask に当たる操作の回避・PR の決まりは `docs/poc/results/workflow/RESUME.md` のとおり。
- 並行: 試行を流す担当セッションは同時に 2 つまで（W12 を含む）。準備（設計・正解データ）は重ねてよい。

## 各 W

### W13 途中で要件が変わる

- 依頼（短い）: 「計測器の貸出を予約できるようにしてほしい。」
- 変更依頼: 候補の手順が終わって実装がコミットされた後に、ペルソナから次のステップとして送る。例:「最初の版は昨日本番に出しました。やっぱり予約は管理者の承認制にしてほしい（承認されるまで仮予約）。予約できる期間は最大 14 日にしてください。」本番に出た前提なので、スキーマの変更は新しいマイグレーションで行う必要がある。
- 測ること: 変更後の受け入れ（隠しテスト）、変わっていない部分の後退が無いか、古い前提のコード・状態値が残っていないか、出荷済みのマイグレーションを書き換えていないか、変更のステップの費用・時間（手戻りの大きさ）。

### W14 安全な DB 移行（止めずに切り替える）

- 依頼（短い）: 「計測器の『設置場所』を自由入力ではなく、場所マスタから選ぶ形にしたい。」
- 隠れ要件の例: 既存の自由入力の値は表記ゆれが多い（全角半角・「第1工場」「第一工場」など）。現場のハンディ端末アプリは来月まで古い版のままで、自由入力で送ってくる（古い API を当面受け付ける）。移行中も台帳は止められない。
- 初期状態: 大量の既存データ（例: 計測器 5 万件、表記ゆれを含む）。
- 測ること: 段階的な移行（新しい列・表を足す → 両方に書く → 埋める → 切り替える → 古い列は後で消す）になっているか、表記ゆれの寄せ方と寄せられない値の扱い、古い API の互換、大量データでの所要時間・一括処理の分割、戻し方の記述。

### W15 テストの無い古いコードの改修

- 依頼（短い）: 「校正機関 B 社の新しい CSV 形式でも、校正記録を取り込めるようにしてほしい。」
- 初期状態: テストの無い古い取込処理（1 つの長い関数、Shift_JIS、和暦の日付、合否の表記ゆれ、重複行の読み飛ばしなど、理由の書かれていない分岐を含む）。
- 測ること: 変更の前に今の振る舞いを固定するテスト（特性テスト）を書いたか、隠しの黄金テスト（既存の形式の取込結果）で後退が無いか、新形式の受け入れ、直し方（既存の分岐を壊さず拡張したか）。

### W16 ログから障害の原因を探す

- 依頼（短い）: 「昨日から、一部の管理者に校正期限の通知が二重に届いていると苦情が来ている。直してほしい。」
- 初期状態: 不具合を仕込んだ校正台帳（例: 定期ジョブの多重起動を防いでいない + タイムアウト時の再送で冪等性キーを変えている）と、本番相当の JSON ログ（原因の手がかりと、関係の無いおとりのエラーを含む）。
- 測ること: 原因の特定が正しいか（報告に書いた原因を正解と突き合わせる）、原因に効く修正か（表示側で重複を隠すなどの対症療法でないか。隠しテストで多重起動・再送を再現）、再発防止のテスト、ログ・監視の改善。

### W17 依存ライブラリの大きな更新

- 依頼（短い）: 「<ライブラリ> を最新のメジャー版に上げてほしい。」（ライブラリは、校正台帳の 10 箇所以上で使われ、互換性の無い変更を含むものを設計書で選ぶ。例: 入力検証や日付のライブラリ）
- 測ること: 全体に漏れなく反映したか（古い API の残り）、振る舞いの維持（隠しテスト: エラー応答の形・日付の扱い）、互換用の抜け道（古い版の併用・型の無視）で逃げていないか、ロックファイルの更新、変更の説明。

## 進める順番

2. W12 の初期状態（base.patch）が固まったら W13 の準備を始める。W12 の試行が終わったら W13 の試行。
3. W14・W15 は別アカウントの担当が実施する（2026-11-10 ユーザー指示。使用量の上限がアカウントごとのため）。判断のやり取りは git で行う（`docs/poc/coordination/answers.md`）。

## W18 長期品質（積み重ね開発と引き継ぎ）— 2026-11-10 ユーザー承認

単発の課題では測れない「保守しやすさ」「技術的負債のたまり方」を測る。市場の報告（GitClear の重複・リファクタリング減少、DORA の安定性低下、EvoClaw / SWE-Milestone・SWE-CI・SWE-STEPS の継続開発ベンチマーク、AI との共同開発の保守性を測る比較実験）に沿った設計。

- 条件: 5 条件（superpowers・feature-dev・gstack・compound-engineering・baseline）× 2 回 = 10 本の「系列」。全条件に汎用の開発標準。モデルは Sonnet。
- ① 積み重ね: 同じ校正台帳（W12 の初期状態）に、6 つの機能を順番に足す。各回は短い依頼 + 依頼者役（ask-po）。機能は、後の回ほど前の回の設計に乗る・横断的な変更を要するものにする（例: 重要度と期限の通知 → 貸出の予約 → 設置場所のマスタ化 → 外部の校正機関への発注連携 → 変更履歴（監査ログ）→ 部署ごとの権限）。各回は同じセッションを続けず、新しいセッションで始める（実務で日をまたぐ形。候補の記憶の仕組みは使えるままにする）。
- ② 劣化の追跡: 各回の後に、それまでの全機能の隠しテスト（後退の検出）、コードの指標（関数の複雑さ・重複・ファイルの大きさ・lint の警告）、テストの強さ（ミューテーション）、費用・時間を記録し、回を追った推移を見る。
- ③ 引き継ぎテスト: 6 回の後の各系列のコードに、どの系列にも同じ固定のエージェント（Sonnet・プラグインなし・汎用の開発標準あり）で、共通の改修課題 2 つ（横断的な仕様変更 1 つ、不具合の修正 1 つ）を行わせ、成功・費用・時間・後退を「保守しやすさ」とする。あわせて、最終のコードをブラインドレビュー（2 名）する。
- 試行前の確認: 参照の系列（参照実装を積み重ねたもの）と、最短で動くだけの系列（各回を最短でつないだもの）で、②の指標と③の引き継ぎの結果がはっきり分かれることを確かめる。
- 順番（2026-11-10 ユーザー判断）: W18 の試行は W16・W17 の後に回す（W12 → W13 → W16 → W17 → W18）。準備は先に済ませて待機する。
- 見込み: 1 系列で 6 回 + 引き継ぎ。Compound Engineering は 1 回 $15〜20 程度のため 1 系列 $100 前後、全体で $300〜400 程度。時間が長いので、W12・W13 の試行が終わってから、試行を流す担当が同時に 2 つまでになるように流す。準備は先に始めてよい。
