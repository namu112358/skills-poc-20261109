# W12 の設計: 短い要件から、運用まで考えて作る

- 作成: 2026-11-10（試行の前に固定。試行中・採点中は変えない）

## 1. 目的

人が短くしか要件を伝えなくても、候補が次のことをするかを比べる。

1. 隠れた業務の振る舞いに、質問で気づくか（依頼者役に聞ける）。
2. DB の設計変更から逃げずに、本番のデータを残すマイグレーションをするか。
3. 人の開発者なら自然に意識する運用の品質（構造化ログ、外部呼び出しのリトライ・指数バックオフ・タイムアウト・冪等性、設定の環境変数化）を実現するか。
4. 最短で動くものではなく、既存の構造に沿った本質的な設計で進めるか。

あわせて、候補のプラグインを使わずに **開発規約を 5 行足しただけ**（baseline-conventions）で、プラグインと比べてどこまで届くか（費用対効果）を見る。

## 2. 題材: 計測器の校正台帳（社内向け）

当初はタスク管理アプリ（`poc-app`）にタスクの優先度と期限通知を足す案だったが、**ToDo・タスク管理は学習データに多く、候補が「よくある実装」をなぞるだけで済んでしまうおそれがある**ため（ユーザーの指摘、2026-11-10）、学習データに少ない業務の題材に変えた。

- 製造・電気工事の会社が、計測器（テスター・絶縁抵抗計・トルクレンチなど）を台帳で管理し、外部の校正機関で定期的に校正する。
- 初期状態（`docs/poc/answer-key/W12/base.patch`）は、`poc-app` の基盤（Next.js・SQLite・ログイン・API の書き方・`node:test`）を使い、タスクの機能を置き換えて作った。`poc-app/` 自体は変えず、`run-trial.sh` が作業用コピーにだけ当てる。
- 既存の機能: 計測器の一覧（状態で絞り込み）・詳細・登録・編集（管理番号・名称・型式・設置場所・管理者・校正周期（月）・前回校正日・状態（使用中・貸出中・校正中・使用停止・廃棄）・備考）、貸出と返却、校正記録の登録（合格なら前回校正日を更新、**不合格なら使用停止**）、利用者（部署・在籍／無効）と部署（代表者）、返却予定日を過ぎた貸出を集計する定期実行のジョブ（`POST /api/jobs/overdue-loans`）。初期データ（利用者 18 人・計測器 10 台など）と単体テスト 27 件。
- 校正期限の計算・重要度・通知は、既存のコードに無い。
- 人の開発者なら読む位置に、次を置いた（`CLAUDE.md` には書かない。気づけるかを見る）:
  - `src/lib/logger.ts`: 1 行 1 JSON の構造化ログ。ログイン失敗・不合格・既存のジョブの 3 か所でだけ使う。
  - `docs/notify-api.md`: 社内通知サービスの API。URL・トークンは環境変数（`NOTIFY_API_URL`・`NOTIFY_API_TOKEN`）、送り先は社員 ID、`429`（`Retry-After`）・`503` が返る、`Idempotency-Key` に対応、応答が遅いことがある。
  - `docs/operations.md`: 本番は SQLite のファイル（2024 年からのデータ）で起動時にマイグレーションが当たる。定期実行はアプリの中で行わず、運用の cron が `POST /api/jobs/<ジョブ名>` を `JOBS_TOKEN` で呼ぶ（`requireJobAuth()`）。
  - `src/lib/db/migrations.ts` の冒頭のコメント: 既存のマイグレーションは書き換えず、末尾に足す（`CLAUDE.md` の規約からは外した）。
  - `src/lib/dates.ts`: 日本時間の今日（`todayJst()`）と、実在する日付の検証。

## 3. 課題文（確定。この 1 文だけを依頼として渡す）

> 計測器に重要度を付けられるようにして、重要度が高い計測器の校正期限が近づいたら、管理者に社内の通知サービスで知らせてほしい。

課題文の末尾には、無人実行であることと、依頼者に質問できることを伝える定型文を付ける（`run-trial.sh` の `POC_TASK_SUFFIX=w12`。W12 の既定）:

> この作業は無人で実行しています。依頼者（品質保証部の担当者）に確認したいことがあれば、作業中いつでも ask-po "<質問>" コマンドで質問できます（依頼者が答えます。決まっていないことは「お任せします」と返ります）。作業の区切りで、最後のメッセージに依頼者への質問を書いても答えます。ツールの手順にある工程（調査・設計・レビューなど）は省かずに進めてください。作業が終わったら、変更内容を git にコミットしてください。

## 4. 依頼者役（ペルソナ）と質問の経路

- 回答シート: `docs/poc/answer-key/W12/persona.md`（業務の決まり Q1〜Q13、運用の事情 O1〜O6、文書に既に書いてあること D1〜D5、範囲の外）。作業用コピーには置かない。
- 決まり: 聞かれたことにだけ答え、隠れ要件を自分から言わない。運用の話は聞かれたら業務の言葉で答える（例「通知サービスはたまに落ちる」「運用チームはログを JSON のまま集計している」）。シートに無いことは「お任せします」。文書にあることは「〜に書いてあるとおりです」と短く答え、聞き直しとして数える。
- 依頼者役は候補とは別の `claude -p`（ツールなし・設定なし・専用 HOME・作業用コピーの外、モデルは試行と同じ）。費用は候補の費用に含めず別に記録する。
- 経路は 2 つで、両方を数える（`scripts/poc/answer_w12.py`）:
  - (a) `ask-po "<質問>"`: 作業中いつでも使えるコマンド。`run-trial.sh` が作業用コピーの外（`$WORK/bin`）に置いて子セッションの `PATH` に入れ、許可リストに `Bash(ask-po:*)` を足す（W12 だけ）。`ask-po` は UNIX ソケットで裏の依頼者役に質問を送るだけで、回答シートの場所は書かれていない。
  - (b) メッセージ: W3 と同じく、ステップの最後のメッセージに依頼者への質問があれば、回答を次のステップとして同じセッションに送る（試行全体で最大 10 回）。`AskUserQuestion` は外す（W3 と同じ）。
- 記録（`raw/<試行ID>/po-questions.jsonl`）: 経路・時刻・実装前か後か（その時点で `src/`・`tests/` に baseline からの変更が無いか）・質問ごとの分類とシートの ID（隠れ要件に当たったか、聞き直しか）・回答・依頼者役の費用。

- 6 条件 × 2 回 = 12 本。前半（各条件の 1 回目）と後半（2 回目）で実行順を逆にする。並列は 1〜2 本。
- 介入は W2 以降の定型の「お任せします」（最大 2 回、`POC_MAX_NUDGES=2`）。費用の上限は付けない（`POC_MAX_TRIAL_USD` を渡さない。歯止めは 1 ステップ 40 分の `POC_STEP_TIMEOUT`）。1 試行が $30 を超えたら、続ける前にコーディネーターに報告する。
- モデル・Claude Code: 既存の W と同じ（`claude-sonnet-5-5`、Claude Code 2.1.321）。
- 子セッションの許可リストは W6 以降のもの（開発サーバー・ブラウザを含む）+ `ask-po`。
- `run-trial.sh` の変更は W12（と新しい候補名 `baseline-conventions`）のときだけ働き、W1〜W11 の既定の動作は変えない。

### baseline-conventions の開発規約（固定の文言。`docs/poc/tasks/wf-W12-conventions.md`）

```markdown
## 開発規約（チームの決まり）

- ログは `src/lib/logger.ts` の構造化ログ（JSON）で出す。`console.log` は使わない。トークンなどの秘密はログに出さない。
- 外部サービスの呼び出しには、タイムアウトを付け、失敗したら指数バックオフ（ジッター付き）で回数を決めて再試行する。429 の `Retry-After` を守り、400 など再試行しても直らない誤りは再試行しない。冪等性キーを付けて二重送信を防ぐ。
- スキーマの変更は `src/lib/db/migrations.ts` の末尾に新しいマイグレーションを足して行い、既存のマイグレーションは書き換えない。本番のデータが残ることを前提にする。
- 接続先・トークンなどの設定と秘密は環境変数から読み、コードに書かない。
- 依頼に書かれていない仮定を置いたら、コミットメッセージ（PR があれば PR の説明）に書く。
```

業務の隠れ要件（Q）は規約に入れない（規約で運用の品質がどこまで上がるかと、質問の行動が変わるかを見る）。

## 6. 採点（品質 100 点。詳細は grading.md）

| 観点 | 配点 | 主な測り方 |
|---|---:|---|
| 業務の受け入れ | 30 | 公開 8（課題文の範囲 4 項目 + 型チェック・単体テスト・ビルド）+ 隠し 22（隠れ要件 13 項目） |
| DB マイグレーション | 20 | 旧スキーマ + データ入りの DB で起動。データが消えない・新しい列が埋まる・2 回起動しても壊れない・既存のマイグレーションを書き換えない |
| 外部呼び出しの堅牢さ | 15 | 失敗を混ぜる偽の通知サービスで、再試行・指数バックオフ・Retry-After・上限・400 を再試行しない・タイムアウト・二重送信なし・次の実行で送り直す・1 件の失敗で止まらない・保存を壊さない・冪等性キー（11 項目） |
| 運用 | 10 | 既存の logger を使う・JSON のログ（失敗は warn / error）・秘密をログに出さない・文書どおりの環境変数 |
| 設計の筋 | 15 | ブラインドレビュー 2 名（層の分け方・既存の抽象の再利用・定期実行の作り方・テストのしやすさ・仮定の明示・後方互換） |
| テストの強さ | 10 | ミューテーション（候補が `src/lib/` に足した行を壊した版を、候補のテストが検出した割合） |

- 質問は品質に入れず、別の指標（回数・的中率・聞き直し・実装前の割合・引き出した隠れ要件の数）として報告する。
- 効率は費用・時間の実額を主に示し、点数は補助（PLAN.md §4.4。基準は baseline 2 回の平均。baseline-conventions は基準に入れない）。`two_axis.py` に W12 を足す。
- 候補ごとに違う名前（重要度の項目名・値、ジョブの API）は、採点用のアダプター（`adapt.cjs`）で吸収する。自動で決められないときは採点者がコードを読んで補正し、report の「判断の記録」に書く。
- 公開の受け入れテストは「課題文に書かれた範囲」の意味で、テスト自体は試行中は候補に見せない（W10 と同じ）。
