# W23 の設計: 画面を作った後の「仕上げの工程」の効果

- 作成: 2026-11-11（W22 の結果を見た後、試行の前に固定）
- 依頼者の指示（不在の間、検証結果から新たな PoC を検討して進める）を受けて、コーディネーターが W21・W22 の結果から立てた。
- 題材・機械の検査は W21 と同じ（[wf-W21-design.md](wf-W21-design.md)）。試行 ID は `W21<課題>-<構成>-<回>` の形。

## 1. きっかけ

- W21: レビュー担当の Web Design Guidelines は、作る課題では一度も呼ばれなかった。入れていても使われていない。
- W21: Impeccable は評価が高い題材もあるが、費用と時間がほかの 2〜3 倍かかる。仕上げにだけ使えば安く済む可能性がある。
- W22（AI の判定。暫定）: Frontend Design を `CLAUDE.md` で指定した構成（`ui-fd-md`）が、安くて評価も高かった。
- W22 の途中で、AI の判定は「同じ画面でも、一緒に並べる画面が変わると点が動く」ことが分かった（SaaS の LP で、1 回目と 2 回目の判定の相関 r = 0.48）。構成ごとに点を付けて比べる方法では、小さな差を判断できない。

## 2. 問い

1. Frontend Design で作った画面に、仕上げの工程（作った画面をレビューして直す）を足すと、見た目は良くなるか。
2. 仕上げに使う道具は、Web Design Guidelines（ルールに沿ったレビュー）と Impeccable の `polish`（デザインの仕上げ）のどちらが良いか。
3. 足した分の費用・時間はどれくらいか。

## 3. 比べ方（対の比較）

各試行で、同じ画面の「仕上げの前」と「仕上げの後」を比べる。作る段階は同じ（`ui-fd-md` と同じ道具と指示）なので、差は仕上げの工程だけから来る。

| 構成 | 道具 | 手順 |
|---|---|---|
| `ui-fd-md-wdg` | Frontend Design + Web Design Guidelines、`CLAUDE.md` の指示は `ui-fd-md` と同じ | ① 課題文 → ② 仕上げ: 「`web-design-guidelines` Skill を使って、今回作った画面をレビューし、直すべき問題を直す。ブラウザで確かめてからコミットする」 |
| `ui-fd-md-imp` | 上に Impeccable を足す。`CLAUDE.md` の指示は同じ（作るのは Frontend Design） | ① 課題文 → ② 仕上げ: 「`/impeccable:impeccable polish` で今回作った画面を仕上げる。ブラウザで確かめてからコミットする」 |

- ① が終わってコミットがそろった時点のコミットを「仕上げの前」として記録する（`raw/<試行ID>/pre-polish-commit`）。採点では、前と後の両方をビルドして、スクリーンショット（幅 1280px）と機械の検査を取る。
- 課題: W21d（SaaS の LP）・W21e（ダッシュボード）・W21f（登録フォーム）。2 構成 × 3 課題 × 3 回 = 18 本。

## 4. 測るもの

| 指標 | 測り方 |
|---|---|
| 仕上げで良くなったか（主） | 対の比較の AI 判定: 判定役（`claude-opus-5-5`）に、同じ試行の前と後の画面を A・B として並べ（左右はランダム、どちらが後かは伏せる）、「どちらが良いか（同じくらい、も可）」を選ばせる。左右を入れ替えて 2 回行い、2 回とも同じ方を選んだときだけ「良い」と数える。人の順位付けのページにも、前と後の両方を名前を伏せて載せる |
| 壊していないか | 機械の検査（機能・axe・幅 375px）を前と後で比べる |
| 費用・時間 | ② の分の費用・時間（ステップごとの記録） |

判定: 仕上げの後が良いとされた試行が 9 本中 6 本以上で、悪くなった試行が 1 本以下、機械の検査を落としていなければ、その仕上げの工程を「推奨」として標準の手順に入れる候補にする。

## 5. 限界

- 仕上げの指示は 1 つの書き方だけを試す。
- 仕上げの前と後は同じ試行の中の比較なので、「最初から仕上げを意識して作る」場合との比較にはならない。
- 人の評価が無い間は、AI の判定で暫定とする。
