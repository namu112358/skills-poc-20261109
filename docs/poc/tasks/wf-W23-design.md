# W23 の設計: 要件の書かれていない PR・大きな PR でのレビューの比較

- 作成: 2026-11-11（試行の前に固定）
- 依頼: ユーザー「結果から学習して新しい PoC をやっておいて」。W21・W22 の結果から、コーディネーターが代理人の原則（`docs/poc/proxy/principles.md`）で設計した。判断の記録は `docs/poc/results/workflow/W23/decisions.md`。

## 1. W21・W22 から分かったことと、次に確かめること

- W21・W22 の題材は、PR の説明に要件がはっきり書いてあり、説明と照らせば見つかる不具合が多かった。Haiku の道具なしでも満点だった。
- W23 は、**PR の説明を 1〜2 行だけ**にし、要件と照らすのではなく、コードから誤りを見つける必要がある題材にする。あわせて、**同じ不具合を小さな PR 2 つに分けたときと、大きな PR 1 つにまとめたとき**で、見つかる数が変わるかを見る。

## 2. 評価セット（`docs/poc/answer-key/W23/cases/`）

| 題材 | PR | 差分 | 正解 |
|---|---|---|---|
| d1 | ダッシュボード（説明 1 行） | 6 ファイル・約 240 行 | B1 利用者をまたぐキャッシュ・B2 日曜に翌週を指す・B3 0 件で完了率が NaN・B4 共有の定数を `reverse()` で書き換え・B5 SQL に ID を埋め込む（規約 8）。おとり D1・D2 |
| d2 | タスクのコメント（説明 1 行） | 6 ファイル・約 180 行 | B6 リンクの URL の種類を確かめない（XSS）・B7 編集だけ投稿者を確かめない・B8 存在しないタスクへの追加で 500・B9 日時を表示用の文字列で保存して並べる。おとり D3・D4 |
| d3 | d1 と d2 を 1 つにまとめた PR | 12 ファイル・約 430 行 | B1〜B9（d1 と d2 の和）。おとり D1〜D4 |

- どれも型検査・テストは通る。どの不具合も、PR の説明が無くても誤りと言えるものだけを正解にし、担当がスクリプトで実際に起きることを確かめた。

## 3. 比べる設定

| 設定 | モデル | レビューの段で送るもの |
|---|---|---|
| `baseline` | Sonnet | 道具の指定なし |
| `hk-baseline` | Haiku | 道具の指定なし（W22 で最も費用対効果が高かった） |
| `cr-high` | Sonnet | `/code-review high` |
| `review-pr` | Sonnet | `/pr-review-toolkit:review-pr all`（既定の動き） |
| `ce-review` | Sonnet | `/ce-code-review base:HEAD`（既定の動き） |

- 設計だけの問題を含まないので、`design-principles-review` は入れない。手順を最後まで踏ませる設定は、W22 で見つける数が増えず費用だけ増えたため入れない。
- 手順・許可リスト・介入（最大 1 回）は W21 と同じ。試行 ID は `W23-<設定>-<題材>-<回>`。

## 4. 本数・判定

- 3 題材 × 5 設定 × 2 回 = 30 本。並列 2 本。
- 判定は W21 と同じ判定役（Opus）・同じ指示文・設定を伏せた資料。約 25% を 2 回判定する。
- 見るもの: 見つけた数（題材ごと・不具合ごと）、d1 + d2（分けたとき）と d3（まとめたとき）の見つけた数の差、誤った指摘、費用・時間。
