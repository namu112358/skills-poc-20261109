## 1. 目的

本番のデータが入った台帳の構造を変えるときに、候補が次のことをするかを比べる。

1. いきなり置き換えずに、段階を分けて移す（新しい表・列を足す → 両方に書く → 既存のデータを埋める → 読む側を切り替える → 古いものは後で消す）。
2. 古い利用者（現場のハンディ端末アプリ・古い列を読む経理の集計・前の版のアプリ）を壊さない。
3. 大量データ（5 万件）でも、起動やほかの書き込みを長く止めない。
4. 表記ゆれの多い自由入力の値を、正しく寄せる。寄せられない値を勝手に決めず、元の文字を残して確認できるようにする。
5. 移行の手順と戻し方を残す。

## 2. 題材と初期状態

W12 と同じ計測器の校正台帳（`poc-app` の基盤の上に作った社内アプリ）。初期状態（`docs/poc/answer-key/W14/base.patch`）は、W12 の初期状態に次を足したもの。`poc-app/` 自体は変えず、`run-trial.sh` が作業用コピーにだけ当てる。

- 現場のハンディ端末アプリ（棚卸し）の API: `POST /api/handheld/inventory`（管理番号と、作業者が書いた場所の文字を送る。トークン `HANDHELD_TOKEN`）。仕様は `docs/handheld-api.md`。
- `docs/operations.md`: 本番の計測器は約 5 万件。設置場所の値の抽出（件数つき）が `docs/data/location-values.csv` にある（170 行。正式名称・表記ゆれ・あいまいな値・空欄を含む）。
- 既存の決まり（W12 から）: マイグレーションは末尾に足す（`migrations.ts` の冒頭のコメント）、定期実行は cron が `POST /api/jobs/<ジョブ名>` を `JOBS_TOKEN` で呼ぶ、構造化ログ `src/lib/logger.ts`。

- 単体テスト 29 件。型チェック・ビルドとも成功。

人の開発者なら読む位置に置いた事情（`CLAUDE.md` には書かない。気づけるかを見る）: 端末の API と仕様書、5 万件という件数、値の抽出ファイル、マイグレーションの決まり。

依頼者だけが知っている事情（質問すれば答える。`persona.md`）: 正式な場所の一覧（16 か所）、寄せてよい表記ゆれの範囲、寄せられない値の扱い（確認中として残し、一覧で探せるように）、空欄は未設定のまま、場所は消さず使用終了にする、名前を変えたら表示も変わる、端末の新しい版は来月（それまで自由入力を受け付ける）、経理が古い列を来期まで読む、再起動 1 回で何分も止められない、前の版に戻すことがある（DB はそのまま）、移行の件数を記録したい。
