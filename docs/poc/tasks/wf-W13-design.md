## 1. 目的

最初の版を作って本番に出した後に、依頼者が仕様を変える。そのとき候補が次のことをするかを比べる。

1. 変更後の仕様を満たす（承認制・期間の上限と、それに伴う隠れた決まり）。
2. 変わっていない部分（最初の版の決まり・既存の貸出などの機能）を壊さない。
3. 本番に出したマイグレーションを書き換えず、本番に残っている予約を新しい仕様に移す。
4. 古い前提のコード・状態の値を残さない。
5. 変更のステップの費用・時間（手戻りの大きさ）。

W1〜W11 では、候補（Skills・プラグイン）は「小さく仕様がはっきりした仕事」では素の状態に費用で負け、「大きい・落とし穴がある仕事」で品質で勝つ傾向が見えた。W13 は、計画・設計の工程を持つ候補が、途中の変更に強いかを見る。

### 変更依頼を送るタイミング（全候補で同じ）

候補ごとに手順のステップ数が違うため、**候補の手順のステップ・依頼者への質問への回答・介入（「お任せします」最大 2 回）がすべて終わった時点**を「最初の版（v1）」とし、その直後に同じセッション（`--resume`）へ変更依頼を送る。

- その時点で未コミットの変更が残っていれば、ハーネスがコミットして v1 に含める（`raw/<ID>/v1-leftovers` に記録）。v1 のコミット・それまでの費用・時間を `v1-commit`・`v1-cost`・`v1-seconds` に記録する。
- 変更依頼にも、各候補の手順を同じように使う（下の表）。その後の質問への回答と介入（最大 2 回。定型文「お任せします。確認は不要なので、変更依頼を最後まで実装し、変更を git にコミットしてください。」、v1 からのコミットの有無で判定）も同じ。
- 依頼者役は段階（v1 / v2）を知っていて、v1 の間は承認・期間の上限を「今は要らない・決めていない」と答え、変更依頼の内容を先に言わない。
