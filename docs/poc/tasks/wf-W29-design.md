# W29 の設計: 合意した要件を 1 つずつ照らすと、要件違反を見つけられるか

- 作成: 2026-11-11（試行の前に固定）
- 依頼: ユーザー「結果から学習して新しい PoC をやっておいて」。W27・W28 の結果から、コーディネーターが代理人の原則（`docs/poc/proxy/principles.md`）で設計した。判断の記録は `docs/poc/results/workflow/W29/decisions.md`。

## 1. 何を確かめるか

- W27・W28 で、W20 c3 の B2（場所マスタから選ぶ形にする要件に反し、新しい API が自由入力の場所を受け付ける）は、関数を動かしても本番で起動しても、誰も見つけなかった（W27・W28 の計 6 本で 0）。PR の説明には「台帳での登録・編集は一覧から選ぶ形にし、自由に書けるのはやめる」（要件 3）と「ハンディ端末からは自由入力の文字を受け付ける」（要件 6）の両方があり、紛らわしい。
- W29 は、レビューの依頼に「合意した要件を 1 つずつ書き出し、実装の該当箇所と照らして、満たしているかを確かめてから指摘する（似た要件どうしの違いに注意する）」を足すと、要件違反を見つけられるかを確かめる。

## 2. 評価セット・設定・本数

- 題材: W20 の実際の題材 c2・c3・c4（正解は W20 のまま）。
- 設定: `baseline-req`（Sonnet）。比べる相手は W27・W28 の Sonnet。
- 本数: 3 題材 × 2 回 = 6 本。手順・許可リストは W27 と同じ。判定は W20 と同じ基準・同じ判定役。
