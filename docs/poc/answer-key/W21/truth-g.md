# W21g（W24）の正解: 見つけにくい問題を仕込んだ UI レビュー

review-g.patch は W6 の参照実装（`docs/poc/answer-key/W6/reference.patch`）の「マイタスク」画面に、コードを読むだけでは見落としやすい問題を仕込んだもの。場所はすべて `src/app/my-tasks/MyTasks.tsx`。W21c（簡単な問題）とは違い、ラベルの欠落やコントラストのような一目で分かる問題は入れていない。

### 仕込んだ問題（8 件）

| 番号 | 種類 | 場所 | 問題（誰が・どういう状況で困るか） | 正しい直し方 |
|---|---|---|---|---|
| B1 | キーボード・読み上げで開けない | 各タスクの `<li onClick={() => (window.location.href = …)}>`（タイトルはリンクでなく `<span>`） | 詳細画面へ行く手段が `li` のクリックだけ。キーボードでは移動・実行できず、スクリーンリーダーでもリンクとして読まれない。マウスが使えない人は詳細を開けない。前の版ではタイトルがリンクだった | タイトルを `<a href={"/tasks/" + id}>` に戻す（行全体を押せるようにするなら、リンクを広げる形にする） |
| B2 | 状態の取り違え（連続した変更） | `changeStatus` の失敗時の戻し（`previous` を呼び出し時に覚えて、失敗したらそれに戻す） | 同じタスクのステータスを素早く 2 回変えて（例: 未着手 → 進行中 → 完了）、1 回目の保存だけが遅れて失敗すると、2 回目（完了）の保存は成功しているのに、画面は「未着手」に戻る。画面とサーバーの値が食い違う | 失敗時は、そのときの最新の要求かどうかを確かめてから戻す（要求ごとの番号を持つ、またはサーバーの値を取り直す）。保存中は同じ行の変更を止める方法もある |
| B3 | タブ順の乱れ | 「追加する」ボタンの `tabIndex={1}` | 正の `tabIndex` で、ページを開いて最初の Tab で、一覧やヘッダーより先に「追加する」ボタンへ飛ぶ。見た目の順番とキーボードの順番がずれ、キーボードで操作する人が迷う | `tabIndex` を外す（文書の順番に任せる） |
| B4 | 動きを減らす設定を無視 | `@keyframes my-task-added`（背景の点滅と横へのずれ、0.9 秒） | OS で「視差効果を減らす／動きを減らす」を設定している人（前庭障害など）にも、横に動くアニメーションが出る | `@media (prefers-reduced-motion: reduce)` でアニメーションを止める（色の変化だけにする） |
| B5 | 追加の成功が伝わらない | 追加の成功時（`setJustAdded` だけで、知らせが無い） | 追加に成功しても、画面上の変化は一覧のどこか（期限順の位置）が一瞬光るだけ。スクリーンリーダーでは何も読まれず、成功したか分からない。一覧の外にスクロールしている人も気づかない | 成功の知らせを `role="status"`（`aria-live="polite"`）で出す（例: 「『〇〇』を追加しました」） |
| B6 | フォーカスが失われる | 送信中に「追加する」ボタンを `disabled` にしている | キーボードで送信すると、押したボタンが無効になってフォーカスが文書の先頭（`body`）へ失われる。送信後に続けて入力したいキーボードの人は、最初から Tab でたどり直すことになる | 成功したらタイトル欄にフォーカスを戻す。送信中は `aria-disabled` と処理中の表示にして、フォーカスを保つ |
| B7 | 見出しの階層が飛ぶ | 「タスクを追加」の `<h3>`（ページの見出しは `h1`） | `h1` の次が `h3` で、見出しで移動するスクリーンリーダーの利用者が、間の階層があると誤解する | `<h2>` にする |
| B8 | 選択欄の名前が全部同じ | 各行の `<label>ステータス <select>` | 全行の選択欄の名前が「ステータス」で、スクリーンリーダーや音声操作では、どのタスクの欄か区別できない | 名前にタスクを含める（例: `aria-label={"「" + title + "」のステータス"}`） |

### おとり（問題ではない点。問題だと指摘したら誤った指摘）

| 番号 | 場所 | 見た目 | 正しい理由 |
|---|---|---|---|
| D1 | インラインの `style` | CSS ファイル・クラスを使っていない | 既存の画面と同じ書き方。新しいライブラリを足さない規約もある |
| D2 | 期限の表示形式 `2026-11-14` | 日本語の日付でない | 既存の一覧と同じ形式で、仕様どおり |
| D3 | ステータスを先に画面に反映し、失敗したら戻す（楽観的な更新そのもの） | 保存前に表示が変わる | 意図した動き。問題は連続した変更のときの戻し方（B2）で、楽観的な更新そのものではない |
| D4 | `<form aria-label="タスクの追加">` と見出し | 名前が重複 | フォームの名前と見出しは役割が違う |
| D5 | 送信中の文言「追加中…」 | ボタンの文言が変わる | 送信中であることを伝える、正しい表示 |

`D1`〜`D5` を「問題がある」と指摘した場合は誤った指摘に数える。B2 は「連続した変更で、失敗した古い要求が新しい値を上書きする」ことを述べていれば一致とする（楽観的な更新一般への指摘は D3）。
