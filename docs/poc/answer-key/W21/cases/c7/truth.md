# C7 の正解（不具合は無いが、設計に問題がある差分）

担当者が変わったときだけログに 1 行を出す、という振る舞いは正しく動く（同じ担当者での更新・ステータスだけの更新では出ない）。仕込んだのは設計の問題（P）だけ。

| ID | 種類 | 場所 | 仕組み（核心） | 正しい直し方 |
|---|---|---|---|---|
| P1 | 作りすぎ（YAGNI・KISS） | `src/lib/notify/`（`EventBus`・`Notifier`・`NotifierFactory`・`SlackNotifier`・`EmailNotifier`・使われないイベントの種類） | 「ログに 1 行」の要件に対し、汎用のイベントバス、送り先の差し替え、未実装の Slack・メールの送り先、使われないイベント（`task.status_changed`・`task.created`）を作っている。PR の説明でも、ほかの記録先の予定は無い。読む量・保守する量が増える | `updateTask`（か API Route）で、担当者が変わったときに `console.log` で 1 行を出すだけにする。送り先が増えたときに抽象を作る |
| P2 | 責務の混在・隠れた副作用 | `src/lib/tasks.ts` の `updateTask` から `eventBus.emit`、`src/lib/notify/index.ts` の読み込み時の購読の登録 | DB を更新する関数が、モジュール全体で 1 つのイベントバスを通じて通知という副作用を持つ。購読は `import` した時点で登録されるため、`updateTask` を使うだけで（テストでも）通知が動き、どこで何が起きるかがコードから追えない | 通知（監査ログ）は、呼び出し側（API Route）で明示的に行うか、`updateTask` の引数で記録の関数を受け取る。読み込みの副作用での登録をやめる |
| P3 | 早く失敗しない・驚き | `NotifierFactory.create`（知らない `NOTIFIER_KIND` は黙って console）と、`SlackNotifier`・`EmailNotifier`（選べるのに未実装で例外） | 設定の書き間違いに気づけない。逆に `slack` を選ぶと、DB を更新した後に例外が出て API は 500 になる（更新は済んでいる）。選べる値が実際には使えない | 送り先を作らない（P1）。作るなら、知らない値・未実装の値は起動時に誤りにする |
| P4 | テストが要件を確かめていない | `tests/notify.test.ts` | 追加したテストは汎用のイベントバスとファクトリの動作だけで、要件（担当者が変わったときだけログに出る・変わらないときは出ない）を確かめていない | `updateTask` で担当者を変えたとき・変えないときのログの出力を確かめるテストにする |

- P1〜P4 は設計の指摘。場所と核心（P1 は「要件に対して作りすぎ・使われない拡張」、P2 は「データの更新に通知の副作用が混ざる／グローバルなバス・読み込み時の登録」、P3 は「設定の誤り・未実装の送り先に早く気づけない」、P4 は「テストが要件の振る舞いを確かめていない」）を述べていれば一致。
- 一般論（「設計を見直すべき」だけ）は一致にしない。
