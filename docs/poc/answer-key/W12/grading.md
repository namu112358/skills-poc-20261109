## アダプター（候補ごとの名前の違いを吸収する）

課題文は 1 文だけなので、重要度の項目名や値（`importance` / `priority`、`A/B/C` / `high/medium/low` など）、ジョブの API は候補が決める。
`adapt.cjs` が次の手順で見つけ、テストはこれを通して操作する。

1. 初期データの計測器の API の応答に増えた項目を探し、値の組（A/B/C・high/medium/low・高/中/低・真偽値・数値など）を PATCH で順に送って、受け付けられた値を段階として並べる（先頭が最も高い）。
2. 登録（POST）で重要度を受け付けるか、一覧の API・画面で絞り込めるかを確かめる。
3. 候補が足した API Route のうち、`JOBS_TOKEN` の Bearer トークンで 2xx を返すもの（`/api/jobs/` を優先）をジョブとし、トークンなしの応答も記録する。

自動で決められないとき（値が数値で高い方が分からない、任意の値を受け付ける、項目やジョブが見つからない）は `needs_review` を立てる。
採点者はその試行のコードを読んで `results/workflow/W12/adapters/<試行ID>.json` に補正を書き、採点をやり直す。補正したことと理由は report の「判断の記録」に書く。
採点者が補正してよいのは「候補の実装が実際に持っている名前・値・API を指す」ことだけで、候補に無い機能を足す補正はしない。

環境変数: テストのサーバーには文書どおりの `NOTIFY_API_URL`・`NOTIFY_API_TOKEN`・`JOBS_TOKEN` を渡す。候補が別の名前（`NOTIF` を含む URL・トークン、`CRON`・`JOB` を含むトークン）で読む場合も同じ値を渡して動かし、運用の O4 で減点する。

## 受け入れテスト（`public.cjs`。課題文に書かれた範囲）

| 項目 | 確かめること |
|---|---|
| P01 | 重要度を付けられ、付けた重要度が API で読める |
| P02 | 最も高い重要度の計測器の校正期限が数日後に迫ると、ジョブの実行で管理者に通知サービスのお知らせが届く |
| P03 | 既存の API の応答の形（初期データの計測器の各項目、詳細の `currentLoan`）が変わらず、重要度を送らない登録も受け付ける（後方互換） |

## 隠しテスト（`hidden.cjs`。persona.md の Q と対応）

お知らせは、偽の通知サービスに届いたもののうち、件名・本文に計測器の管理番号（または管理番号を含む名称）があるもので数える。日付はすべて日本時間で、時計は `fake-clock.cjs` で動かす。

| 項目 | 確かめること | Q |
|---|---|---|
| H01 | 重要度は 3 段階で、既存の計測器は真ん中（B）になる | Q1 |
| H02 | 一覧を重要度で絞り込める（API か画面） | Q2 |
| H03 | 期限は「前回校正日 + 周期」の月の末日（前回 2026-02-10 → 2027-02-28。01-15 には届かず、02-20 には届き、02-10 を期限と書かない） | Q3 |
| H04 | 期限の 30 日前から知らせ、31 日前には知らせない | Q4 |
| H05 | 「今日」は日本時間（日本時間 03-01 00:30 = UTC 02-28 に、期限 03-31 の 30 日前として届く） | Q3 |
| H06 | B・C は知らせない（A は届く） | Q5 |
| H07 | 校正中・使用停止・廃棄・不合格で使用停止になったものには知らせない | Q6 |
| H08 | 貸出中なら、管理者と借りている人の両方に届く | Q7 |
| H09 | 同じ期限の「期限が近い」お知らせは、ジョブを何度実行しても 1 回 | Q8 |
| H10 | 校正記録で期限が変わったら、新しい期限について改めて知らせる（校正の直後には送らない） | Q9 |
| H11 | 期限を過ぎたら「期限切れ」を 1 回だけ（件数の推移が 1→2→2→2） | Q10 |
| H12 | 管理者が無効なら部署の代表者に届き、無効な管理者には送らない | Q11 |
| H13 | ジョブは `JOBS_TOKEN` で認証する API で、アプリの中で定期実行しない（`setInterval`・cron のライブラリ・`instrumentation.ts` が無い） | Q12 |

## 外部呼び出しの堅牢さ（`robust.cjs`）

1 回目のジョブの実行で、送り先ごとに台本を仕込んだ偽の通知サービスに対して、次をまとめて確かめる（2 回目は翌日）。

| 項目 | 台本 | 合格の条件 |
|---|---|---|
| R01 | 503 → 503 → 202 | 3 回以上要求し、1 件だけ届く |
| R02 | 503 × 4 → 202 | 再試行の間隔が 2 つ以上あり、最初の間隔が 100ms 以上、最後の間隔が最初の 1.5 倍以上（ジッター可） |
| R03 | 429（Retry-After: 3）→ 202 | 2 回目の要求が 2.9 秒以上あと |
| R04 | 503 が続く | 1 回の実行での要求が 2〜10 回で、ジョブが終わる |
| R05 | 400 | 1 回の実行での要求が 1 回 |
| R06 | 応答しない → 202 | 60 秒以内に自分で打ち切り、再試行で届く（偽のサービスは 90 秒で 504 を返す）。打ち切りの検出の遅れとして 2 秒を見込む（2026-11-10、最初の試行で 60 秒のタイムアウトが 60.001 秒と計測されたための補正） |
| R07 | 受け付けてから応答しない → 202 | 再試行しても届いたのは 1 件（同じ Idempotency-Key） |
| R08 | R04 の送り先を 2 回目の実行では成功させる | 2 回目の実行で届く（失敗を「送信済み」にしない） |
| R09 | （ほかの送り先の失敗と同じ実行） | 失敗と関係ない送り先に届く |
| R10 | すべて 503 | 台帳の更新・校正記録の登録が 2xx（通知の失敗で保存が壊れない） |
| R11 | — | すべての要求に Idempotency-Key があり、再試行で同じキーを使う |

## DB マイグレーション（`old-db.sql`）

旧スキーマの DB（version 4。2024〜2026 年のデータ）をファイルに戻し、その DB で候補のサーバーを 2 回起動する。

| 項目 | 配点 | 合格の条件 |
|---|---:|---|
| M1 | 4 | 新しい番号のマイグレーションを末尾に足し、適用後に `user_version` が上がる |
| M2 | 4 | 既存のマイグレーション（version 1〜4）の SQL を書き換えていない |
| M3 | 4 | 旧 DB で起動・ログインでき、既存の行（部署・利用者・計測器・貸出・校正記録）が 1 件も消えず、値も変わらない |
| M4 | 3 | 既存の計測器すべてに重要度が入り、その値が真ん中の段階（B）（2 段階以下の実装は、段階のどれかが入っていればよい） |
| M5 | 3 | 既存の計測器の重要度を変えると、再起動後も残り、既存の列（備考など）は変わらない |
| M6 | 2 | 2 回目の起動（マイグレーションの 2 回目）でも壊れず、`user_version` が変わらない |

逃げ方の検出（report に書く）: 既存のマイグレーションの書き換え（M2）、DB の作り直し・データの消失（M3）、既存の列への詰め込み（M5 の「既存の列が変わった」）、メモリ保持（M5 の「再起動で消えた」）。

| 項目 | 配点 | 測り方 |
|---|---:|---|
| O1 | 3 | 追加したコードが既存の `logger`（`src/lib/logger.ts`）を使う: 使っていて `console.*` を足していない 3、両方 1.5、logger を使わない 0 |
| O2 | 3 | ジョブの実行中のサーバーのログに、既存以外の事象の JSON の行がある 1.5、失敗（R04・R05 など）で warn / error の JSON の行がある 1.5 |

## 設計の筋（ブラインドレビュー、15 点）

- 資料（`blind_w12.py prepare`）: 各試行のコミットメッセージ・文書（.md）の差分・コードの差分（`package-lock.json` とツールの管理用ファイルを除く）。候補名・ツール名・「baseline」は `[redacted]`。記号の順番は乱数（種 20261110）。共通の資料は課題文と、初期状態の `CLAUDE.md`・`docs/operations.md`・`docs/notify-api.md`・`logger.ts`・`api.ts`・`migrations.ts`。テストの結果・費用・質問の記録は渡さない。
- レビュー担当: 独立した新しいサブエージェント 2 名。互いの結果を見せず、資料を読む順番を変える（1 人目は記号の昇順、2 人目は降順）。
- 観点（各 0〜3 点、18 点満点）:
  - a. 層の分け方（期限の計算・送り先の決定・通知サービスの呼び出し・ジョブの入口・記録が分かれ、既存の `src/lib/` と API Route の分担に沿っているか）
  - b. 既存の抽象の再利用（`logger`・`requireJobAuth`・`todayJst`・`isValidDate`・`transaction`・検証関数・既存のテストの書き方を使い、同じものを作り直していないか）
  - c. 定期実行の作り方 = 既存のジョブの決まりに沿ったか（`docs/operations.md` の `POST /api/jobs/<ジョブ名>`・`requireJobAuth()`・`JOBS_TOKEN` に合わせたか。サーバーの中に `setInterval` などを置いていないか。二重実行・途中で止まったときの扱い）。初期状態に既存のジョブの決まりを置いたため、この観点は「定期実行の仕組みを一から考えたか」ではなく「既存の決まりに気づいて従ったか」を見る
  - d. テストのしやすさ（時刻・HTTP・待ち時間を差し替えられる形か。テストがそれを使って振る舞いを確かめているか）
  - e. 仮定の明示（依頼者に質問しなかった・決めなかった点を、コミットメッセージ・README・設計メモに書いているか）
  - f. 後方互換（既存の API の応答の形・既存の動き・既存のデータを壊していないか。マイグレーションの書き方）
- 2 名の合計の平均 × 15/18 を点にする。同じ観点で 2 点以上ずれたものは report に書く。

## 質問の指標（品質・効率に入れない）

依頼者役の記録（`raw/<試行ID>/po-questions.jsonl`）から、試行ごとに次を数える。

- 質問の数（経路別: `ask-po` / メッセージ）。1 回の問い合わせに複数の質問があれば、依頼者役が分けた項目ごとに数える。
- 的中: 回答に Q または O の項目を使った質問の数と割合。引き出した隠れ要件の数（Q の種類）と運用の事情の数（O の種類）。
- 聞き直し: 文書に既に書いてあること（D）を聞いた質問の数。
- 実装前: 質問した時点で `src/`・`tests/` に変更が無かった質問の数と割合。
- 依頼者役の費用（候補の費用には含めない）。
