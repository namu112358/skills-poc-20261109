### 業務: 公開（課題文の範囲）

| ID | 内容 |
|---|---|
| P1 | 計測器に点検の担当者を付けられる（担当者を `extra` に入れる作りでも、付けられれば通す。持ち方は S で見る） |

### 業務: 隠し（回答シートとの対応）

| ID | 内容 | シート |

| H06 | 点検の記録が無い計測器は「未点検」と分かる | Q4 |
| H07 | 担当者で絞り込める | Q5 |
| H08 | 担当者ごとに、点検が遅れている台数が分かる（加藤さんの担当 3 台のうち、遅れている 2 台。遅れていない 1 台を混ぜて、絞り込みを無視する作りを通さない） | Q5 |
| H09 | 要修理なら計測器を使用停止にする | Q6 |
| H10 | 担当部署での絞り込み・その他の項目の重ね方・計測器の応答の項目が今までどおり（互換） | O2 |

### データの持ち方（API で使った DB と、候補のコードを見る）

| ID | 内容 |
|---|---|
| S1 | 点検の記録の専用の表がある（計測器への外部キーと、記録した点検日がある） |
| S2 | 担当者が `extra` の外（列か、計測器を参照する表）にある |
| S3 | 点検の記録が `extra` に入っていない |
| S4 | 新しいコードが、点検の情報（inspector・inspection・last_inspected）を `extra` で読み書きしていない。移し替えの処理・テスト・コメントは数えない。元の書き方を画面に出すために古いキーを読むことはありうるので、2 か所まで認める |
| S5 | 担当者の列と、記録の計測器の列に索引がある（5 万件・毎朝開く一覧のため。O1） |

### 移行（本番相当の旧 DB 5 万件を、候補のアプリで起動する）

| ID | 内容 | シート |
|---|---|---|
| M1 | 計測器が 1 件も消えず、元の列の値が変わっていない | O3 |
| M2 | 既存のマイグレーションを書き換えていない（新しい版で足す） | O3 |
| M3 | 2 回目の起動で壊れない（版と件数が変わらない） | O3 |
| M4 | 担当部署（`extra.dept`）が 1 件も変わっていない（経理が直接読んでいる） | O2 |
| M5 | 旧データの点検者の名前（「さん」「様」・前後の空白つき）を利用者に寄せた割合が 95% 以上 | Q7 |
| M6 | 分からない名前（外部委託など）・読めない日付（先月・2026-02-30 など）の元の書き方が DB のどこかに残っている（各 300 件を調べて 99% 以上） | Q7 |
| M7 | 最初の応答（ログインと担当部署での絞り込み）が 30 秒以内 | O1 |
| M8 | 移行後の DB で、前の版（初期状態）のアプリが動く（一覧・1 件・更新・詳細の画面） | O3 |

- 試行前の確認で直した: M5 未満の扱い。当初は全部を数えていたが、移行をしない半分の実装と最短の実装が「何も動かしていないので失っていない」だけで 17 点になった。移していないときは M1・M4（壊していない）だけを数える。
- 試行前の確認で見つけた: 参照実装は、訂正された記録を除く副問い合わせに索引が無く、5 万件で一覧が 73 秒かかった（M7 で落ちた）。参照実装に索引を足して 0.5 秒にした。M7 は実際の性能の問題を見つけられる。

## 設計の筋（ブラインドレビュー。各 0〜3 点）

| 記号 | 観点 |
|---|---|
| a | 要件から見たデータの持ち方（担当者・記録を専用の列・表にしたか。既存の `extra` に合わせて詰め込んでいないか） |
| b | 既存の粗い部分との付き合い方（今回要る分だけ直し、残りを理由と一緒に書き残したか。全部を書き直していないか） |

| f | 置いた仮定の明示と、依頼者に確かめたこと |
