# W18 第 4 回「外部の校正機関への発注連携」の回答シート

依頼文（`docs/poc/tasks/wf-W18r4.md`）:

> 計測器を校正に出すときに、校正機関の受付システムに発注を送れるようにしてほしい。受付システムの API の資料は docs/agency-api.md に置きました。

この回の始めに、ハーネスが `docs/agency-api.md`（正解データの `agency-api.md` の写し）を「依頼者が置いた資料」としてコミットする。隠しテストは `f4.cjs`（O01〜O08）。

## 業務の決まり（Q。隠れ要件）

| ID | 内容 | 隠しテスト |
|---|---|---|
| Q1 | 発注できるのは、使用中の計測器と、使用停止の計測器（不合格のあと修理して再校正するため）。貸出中・校正中・廃棄の計測器は発注できない。 | O02 |
| Q2 | 発注したら、計測器は「校正中」にしてほしい（今ある状態の「校正中」を使う）。校正機関から戻って校正記録を登録すれば、今までどおり使用中に戻る。 | O01・O07 |
| Q3 | 発注するのはログインしている本人（発注した人として受付システムに送る）。誰が発注できるかは、今はお任せします。 | O01 |
| Q4 | 受付システムには、管理番号・名称・型式と、発注した人を送る。 | O01 |
| Q5 | 受付システムが受け付けたら、受付番号と返却予定日を台帳で見られるようにしてほしい。 | O01 |
| Q6 | 受付システムは夜間や朝に止まっていることがある。止まっていても、台帳での発注の操作はできるようにして（発注は「未送信」として残す）、毎朝のジョブで送り直してほしい（運用の cron から呼ぶ。8:30 ごろ）。 | O03 |
| Q7 | 同じ発注が受付システムに二重に登録されると、校正機関が 2 回引き取りに来て困る。 | O04 |
| Q8 | 受付システムが「内容の誤り」で断ってきた発注は、何度送っても同じなので送り直さないでほしい（品質保証部が確認する）。 | O08 |
| Q9 | 発注したら、校正から戻るまで使えないので、その計測器のこれからの予約（終了日が今日以降）は取り消して、予約した人に社内の通知サービスで知らせてほしい。 | O05 |
| Q10 | 1 台の計測器に、進行中（未送信・受付済み）の発注は 1 件だけ。 | O06 |
| Q11 | 校正記録（合格・不合格）を登録したら、その計測器の進行中の発注は完了にしてほしい。 | O07 |
| Q12 | 計測器の詳細で、発注の状況（未送信・受付済み・完了など）を見たい。 | O01 |

## 運用の事情（O）

| ID | 内容 |
|---|---|
| O1 | 受付システムの応答はとても遅いことがある（数十秒）。そのせいで画面や朝のジョブが止まったままになるのは困る。 |
| O2 | 運用チームはサーバーのログを JSON のまま集計している。いつ・どの計測器の発注を送ったか、失敗したかを後から追えるようにしてほしい。API キーなどの秘密がログに出るのは困る。 |
| O3 | 本番の DB には 2024 年からのデータが入っている。リリースでデータが消えたり変わったりしないようにしてほしい。 |

## 文書・既存の仕組みに既に書いてあること（D）

| ID | 内容 | 場所 |
|---|---|---|
| D1 | 受付システムの使い方（URL・API キーは環境変数、clientReference、Idempotency-Key、409・429・503、応答が遅い、夜間は止まる） | `docs/agency-api.md` |
| D2 | 定期実行は運用の cron から `POST /api/jobs/<ジョブ名>` を `JOBS_TOKEN` で呼ぶ | `docs/operations.md` |
| D3 | 社内の通知サービスの使い方 | `docs/notify-api.md` |

## 範囲の外・決めていないこと（「お任せします」）

- 発注の取消（今回は要らない）、受付システムからの状況の取り込み（引き取り・校正中・返送）。
- 発注の画面のデザイン、備考の欄。
- 誰が発注できるか（今はお任せします）。
- 予約を取り消したお知らせの文面（管理番号と、予約の期間が分かればよい）。
