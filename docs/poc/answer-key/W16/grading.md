## 仕込んだ不具合（正解）

| | 原因 | 場所 | 単独で二重送信になる理由 |
|---|---|---|---|
| A | ジョブの多重起動を防いでいない | `src/lib/calibration-reminders.ts`（`alreadySent()` が `status = 'sent'` だけを見る。ロック・取り合いなし）、`src/app/api/jobs/calibration-reminders/route.ts` | 前の実行が送信中（`pending`）のお知らせを、後から始まった実行が「未送信」とみなして送る。送信記録は実行ごとに別の行になり、キー（`calibration-notification-<行>`）も別なので、通知サービスでも弾かれない |
| B | タイムアウトの再試行で冪等性キーを変えている | `src/lib/notify-client.ts`（`Idempotency-Key` を「<キー>-<試行回数>」にする。コメントは誤った理由「同じキーだと最初の結果（503 など）が返る」）、`idempotencyKey(行の id)` | 通知サービスが遅いとき、タイムアウトした要求もサービス側では送られている。別のキーで送り直した 2 回目も送られる。失敗として残ったものを次の実行で送り直すときも、新しい行・新しいキーになる |

- きっかけ（障害の原因ではない）: 11-09 の朝から通知サービスが遅い（5〜20 秒）。ジョブが cron の待ち時間（60 秒）を超え、cron が呼び直した（`curl --max-time 60 --retry 1`。回答シートの O1）。
- 本番のログ（`incident/2026-11-10/app.log`、52 行）にある手がかり: 11-09・11-10 の 7:30 に `job.started` が 2 回（約 61 秒差）・`job.completed` が 2 回、11-09 の MI-0030（高橋）の `calibration_reminder.sent` が 2 回（別の `notificationId`）、`notify.retry`（`タイムアウト（10000ms）`）の直後の `sent`（`attempts: 2`）が苦情の松本・山田の分と一致する。
- おとり: 清水への 400（`recipient not found`。2 つの実行で 2 回ずつ）、`auth.login_failed`、11-09 10:05 の `job.unauthorized`、429 の `notify.retry`（断られた要求は送られていない。この再試行では二重にならなかった）、11-09 2:00 の再起動（JSON でない行）、MI-0037 の `calibration.failed`、返却遅れのジョブ。

## 原因の特定（20 点。`judge_w16.py`）

候補が書いた文章（各ステップの最後のメッセージ、コミットメッセージ、候補が足した・変えた `*.md`）だけを、別の `claude -p`（ツールなし。コードは見せない）が 2 回独立に判定する。2 回が食い違った項目は採点者が資料を読んで決め、理由を report の判断の記録に書く（`judge/<試行ID>.override.json`）。

| 項目 | full | partial | none / blamed |
|---|---|---|---|
| A | (a) ジョブが重なって複数回動いた（cron の呼び直しなど）こと と (b) 排他が無い・送信済みの確認と送信の間の競合（送信中を見ていない）で両方が送ったこと の両方 | 片方だけ | 書いていない |
| B | (a) 再試行（タイムアウトの後）で Idempotency-Key が変わる（試行ごと・行ごと）こと と (b) タイムアウトした要求もサービス側では送られていたこと の両方 | 片方だけ | 書いていない |
| おとり | おとりを二重送信の原因として書いていない（clean） | — | おとりのどれかを原因として書いた（blamed） |

通知サービスが遅いこと・cron の呼び直しを「きっかけ」として書くのは、おとりではない。判定の文面は `judge_w16.py` の `RUBRIC`（試行前に固定）。

## 原因に効く修正（30 点。`incident.cjs`）

新しい DB で起動したサーバー（`NOTIFY_API_TIMEOUT_MS=2000`、偽の時計）と偽の通知サービスで確かめる。「要求」は通知サービスに届いた POST（失敗・タイムアウトを含む）、「届いた」はサービスが実際に送ったもの。

| 項目 | 確かめること | 対症療法で落ちる例 |
|---|---|---|
| I1 | ジョブを同時に 2 回呼んでも、同じお知らせの要求は 1 回・届くのは 1 回（3 回目の実行でも送らない） | キーをお知らせごとに固定しただけ（通知サービスの重複排除に頼る）→ 要求が 2 回 |
| I2 | 前の実行の途中（1.2 秒後）に 2 回目が始まっても、要求は 1 回 | 同上 |
| I3 | 受け付けられたのに応答が返らない（タイムアウト）お知らせを、再試行で二重に届けない | 待ち時間を延ばしただけ（`NOTIFY_API_TIMEOUT_MS` を読む限りタイムアウトは起きる） |
| I4 | 何度送ってもタイムアウトしたお知らせ（実は 1 回目で送られている）を、次の実行で送り直しても二重に届けない | 再試行のキーだけ揃え、行ごと（実行ごと）のキーのまま |
| I5 | 本番の状況（遅い応答・一部タイムアウト・途中で 2 回目の実行）で、全員にちょうど 1 回届く | 片方の原因だけを直した |
| I6a | ジョブの途中（送信中の要求は通知サービスで送られた後）でサーバーを強制終了 → 起動し直し → 3 時間後・翌朝の実行で、全員にちょうど 1 回届く（2.5 点） | 実行ごと・行ごとのキーのまま（送り直しが別のキーになる） |
| I6b | 同じく、送信中の要求が通知サービスに届いていなかった場合に、あとの実行で送る（2.5 点） | 期限の無いロック（ずっと残る）、送信中を「送信済み」とみなす（送信中のまま残ったものを二度と送らない） |

- 名前（ジョブの API・重要度の項目）は出荷済みの版のもの（`ADAPTER`）を使う。候補が変えた場合は、採点者が `results/workflow/W16/adapters/<試行ID>.json` で補正する（W12 と同じ。候補に無い機能を足す補正はしない）。
- 2 回目の実行の応答（200・409 など）は問わない。
- I6a・I6b は同じサーバー・同じ DB で a → b の順に行う（b の送り先は a と変え、通知サービスの台本が混ざらないようにした）。

## 後退なし（20 点）

- W12 のテスト（`public.cjs` P01〜P04、`hidden.cjs` H01〜H13、`robust.cjs` R01〜R11）を、出荷済みの名前のアダプターで、新しい DB・既定のタイムアウトで実行する。出荷済みの版で合格する項目（`baseline-pass.json`）のうち、候補のコードでも合格する割合 × 10。
  - 出荷済みの版で落ちる R07（受け付けられて応答が返らないお知らせを二重に届けない）・R11（再試行で同じキー）は B の症状なので分母に入れない（I3・I4 で見る）。
  - 対症療法の「再試行をやめる」は R01（503 のあとに再試行）・R03（429 の Retry-After）などで落ちる。
  - H13（定期実行は cron から API を呼ぶ形）のうち、W12 でコードから調べた「アプリの中の定期実行」は W16 では調べない（空として渡す）。ジョブの API とトークンなしの 401 だけを見る。
- 本番の DB（`old-db.sql` に出荷済みのコードで version 5 を当て、`data_w16.py` で 11-10 朝の状態を書いた DB。重要度 A の 14 台、送信記録 19 行（二重の `sent` を含む）、清水の `failed`）で、11-11 7:30 の時刻で起動する。
  - M1（2 点）: 起動し、ログインして一覧の API が 60 台を返す（既存の重複した行に一意の制約を付けて起動が止まる、などを落とす）。
  - M2（1 点）: 計測器・校正記録の件数と、既存の送信記録の行（id）が残る。
  - M3（3 点）: ジョブを 1 回実行し、11-09・11-10 に送信済みのお知らせを、もう一度送らない（直したものを出した翌朝に、全員に送り直す、などを落とす。回答シートの O8）。
- M4（1 点）: 出荷済みのマイグレーション（version 1〜5）の SQL を書き換えていない。

## 再発防止のテスト（10 点。`reinject_w16.py`）

候補の修正後のコードに、原因を 1 つずつ戻した版（再注入）を作り、候補の `npm test` で検出できるかを見る（原因ごとに 5 点）。

1. 候補のコードがその原因を直していなければ（A は I1・I2、B は I3・I4 がどちらも不合格）、0 点（再注入しない）。
2. 再注入の書き換えは、別の `claude -p` が候補の差分から作る（A: 候補が足した排他・取り合いだけを働かなくする。B: 再試行・送り直しのキーだけを試行ごとに変わる形に戻す）。
3. 書き換えた版で隠しテストを実行し、その原因の項目（A は I1・I2、B は I3・I4）のどちらかが不合格になることを確かめる（戻せていなければ 1 回だけ作り直す。それでも駄目なら採点者が `reinject/<試行ID>.override.json` に書き換えを書く）。
4. 書き換えた版で候補の `npm test` を実行し、失敗が増えれば（書き換える前に全部通っていたなら、失敗すれば）「検出した」。

## ログ・監視（10 点）

I1〜I5 のサーバーのログ（1 行 1 JSON）と、偽の通知サービスが受けた要求から判定する。

| 項目 | 配点 | 合格の条件 |
|---|---:|---|
| L1 | 4 | 実行が重なったこと（2 回目を止めた・待たせた・送らなかった）が、ログに出る（出荷済みの版に無い event、または既存の event の新しい項目に、lock・already・running・skip・concurrent・in progress・duplicate・claim・多重・実行中 などの語がある） |
| L2 | 3 | 通知サービスに送った Idempotency-Key が、アプリのログに出る（通知サービス側の記録と突き合わせられる。回答シートの O9） |
| L3 | 3 | ジョブの実行ごとの識別子（`runId` など）がジョブ・お知らせのログに付き、重なった実行を区別できる（2 種類以上の値が出る） |

## 設計の筋（ブラインドレビュー 10 点）

2 名のレビュー担当（別の `claude -p`）が、候補名を伏せた差分（コード・文書・コミットメッセージ）と共通の資料（課題文・本番のログ・初期状態の関係ファイル）を読み、6 項目を 0〜3 点で付ける。

| 項目 | 観点 |
|---|---|
| a | 原因の層で直しているか（ジョブの排他・キーの作り方。通知サービス側の重複排除や画面・文面の手当てだけに頼っていない） |
| b | 既存の設計・書き方との整合（既存の送信記録・ロガー・ジョブの決まりを使う、変更が目的に絞られている） |
| c | 本番への出し方（出荷済みのマイグレーションを書き換えない、本番に残っている二重の記録・送信中の記録への影響、出した翌朝に送り直さない） |
| d | 障害時の回復（途中で止まってもロックや送信中の記録が残り続けない、失敗を握りつぶさない） |
| e | テスト（多重起動・タイムアウトの再現、時刻・外部サービスの差し替え） |
| f | 説明（原因・直したこと・運用への提案（cron の設定など）・残った課題） |
