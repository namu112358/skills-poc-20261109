# W2（仕様が明確な機能追加）の採点手順

試行を始める前（2026-11-09）に固定した。試行中・採点中は変えない。課題文は [`docs/poc/tasks/wf-W2.md`](../../tasks/wf-W2.md)。

## 配点（100 点。PLAN.md §5.1）

| 観点 | 配点 | 測り方 |
|---|---|---|
| 受け入れテスト | 40 | 隠しの E2E（`acceptance.cjs`、16 件）× 1.875 点 = 30 点 + 型チェック・単体テスト・ビルド 各 10/3 点 = 10 点 |
| 介入回数 | 20 | 20 − 5 ×（介入回数 + 質問回数）。0 点未満にはしない。最後までコミットが無い（未完了）なら 0 点 |
| 設計・テストの質 | 25 | ブラインドレビュー（下記）。採点者 2 名の合計点（25 点満点）の平均 |
| 費用 | 15 | 15 ×（W2 の全試行の最安費用 / 自分の費用） |

- **介入回数**: `run-trial.sh` は手順のステップを終えた時点で「コミットが無い」または「未コミットの変更が残る」とき、定型の「お任せします。確認は不要なので、課題を最後まで実装し、変更を git にコミットしてください。」で続けさせる（最大 2 回、`POC_MAX_NUDGES=2`）。その回数を数える。
- **質問回数**: `AskUserQuestion` の呼び出し回数（無人なので答えられず、人の介入が必要になる操作として数える）。
- 権限の拒否（`permission_denials`）は介入には数えず、レポートに記録だけする。
- 正解データ（`docs/poc/answer-key/`）を読んだ形跡がある試行は、受け入れテストを 0 点にする（`grade.py` の `answer_key_access`）。

## 受け入れテスト（`acceptance.cjs`）

API 9 件・画面 6 件・既存の動作 1 件。仕様書の各項目に 1 対 1 で対応する。参照実装（`reference.patch`）で 16/16 通過し、変更なしの poc-app では既存の動作の 1 件だけが通る（機能の 15 件はすべて失敗する）ことを確認してから試行を始めた。

## ブラインドレビュー（設計・テストの質 25 点）

### 手順

1. 全試行の採点（`grade.py`）が終わってから、`scripts/poc/blind_w2.py` でレビュー用の資料を作る。
   - 各試行の差分から、候補が作る管理用ファイル（`docs/plans/` など `grade.py` の `TOOL_ARTIFACT`）と文書（`*.md`）、`package-lock.json` を除く。コミットメッセージは含めない。
   - 差分の中の候補名（superpowers / feature-dev / gstack / compound など）は `[redacted]` に置き換える。
   - 試行に `R01`〜`R09` のランダムな記号を振る（乱数の種は固定）。対応表は `review/mapping.json` に書き、レビューが終わるまでレビュー担当に渡さない。
2. 採点者 2 名（互いに独立した新しいサブエージェント。候補名・受け入れテストの結果・費用を知らない）に、資料を **採点者ごとに異なる順番** で渡し、下の基準で全試行を採点させる。全試行を見比べてから点を付けるよう指示する（基準の揃え）。
3. 採点者ごとの 5 項目の合計（0〜25）を平均して点数にする。同じ試行・同じ項目で 2 名の差が 3 点以上あれば、レポートに記録する（点数は平均のまま）。

### 基準（各 0〜5 点）

| 項目 | 見るところ |
|---|---|
| 1. 規約の遵守 | `poc-app/CLAUDE.md` の規約: 処理を `src/lib/` に置く、マイグレーションは末尾に追加、プレースホルダ、API はログイン確認 → `src/lib/` の検証関数 → 400 / 401 / 404、画面の文言は日本語、外部ライブラリを足さない |
| 2. 設計の分かりやすさ | 責務の分け方、既存コード（`tasks.ts`・既存の API Route）との一貫性（命名・エラー形式・型）、読みやすさ |
| 3. 認可と入力の安全性 | 投稿者をセッションから決める、本人だけが削除できる、別タスクのコメントを扱わない、ID・本文の検証、HTML を解釈しない表示 |
| 4. テストの質 | 追加したロジックの単体テストの網羅（本文の境界値、削除の権限、存在しない対象、並び順）、テストの独立性・読みやすさ |
| 5. 過不足のなさ | 依頼範囲外の変更・不要な抽象化・使われないコードが無いか。仕様の取りこぼしが無いか |

点の目安: 5 = 指摘なし、4 = 軽微な指摘が 1〜2 点、3 = 明確な問題が 1 つ、2 = 明確な問題が複数、1 = 重大な問題（セキュリティ上の欠陥・仕様の大きな欠落など）、0 = 該当する実装やテストが無い。
