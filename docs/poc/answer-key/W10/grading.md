## 公開の受け入れテスト（`acceptance.cjs`、13 件）

P01 未ログインは 401 / P02 空の一覧 / P03 申請の形（申請者・保留中・判断は null・申請日時は UTC）/ P04 一覧は古い順 / P05 タスクが無いと 404 / P06 形式の誤り・項目の欠落は 400（`details` あり）/ P07 理由が長すぎると 400 / P08 保留中があると 409 / P09 承認で期限が変わる / P10 却下で期限は変わらない / P11 判断の後は再申請できる / P12 存在しない申請は 404 / P13 既存の API が従来どおり動く。

日付は 2027 年にして、過去の日付・時差の扱いに左右されないようにしている。

## 隠しテスト（`hidden.cjs`、12 項目）

サーバーは `fake-clock.cjs` を読み込んで起動し、時計を 2026-11-09T15:30:00Z（日本時間では 2026-11-10 00:30。UTC と日本時間で日付が違う時刻）から進める。課題文には「利用者は全員日本国内にいます」とだけ書いてある。判定は「拒否されたか（4xx）」と「状態が変わっていないか」で見て、ステータスコードの細かい違い（403 と 409 など）は問わない（H05〜H10 は入力誤りなので 400、H06 の不正な ID は 404 を求める）。

| 項目 | 分類 | 確かめること |
|---|---|---|
| H01 | 権限 | 担当者でない人は延長を申請できない |
| H02 | 権限 | 申請者本人は自分の申請を承認できない |
| H03 | 権限 | URL のタスクに属さない申請は承認・却下できない（別のタスクの ID を使った操作） |
| H04 | 権限・入力 | 本文の申請者・状態・判断した人・ID を使わない（使わない、または 400 で拒否） |
| H05 | 入力検証 | 実在しない日付（2027-02-29・2027-04-31・2027-13-01）は 400（`Date.parse` は前の 2 つを受け付ける） |
| H06 | エラー時の振る舞い | 壊れた JSON・配列・`null`・型の違う値は 400、不正な申請 ID（`abc`・`0`・`1.5`・`-1`・桁あふれ）は 404。500 にならない |
| H07 | 境界値 | 新しい期限が今の期限と同じ・より前なら 400、1 日後は受け付ける |
| H08 | 境界値 | 理由は前後の空白を除いて 1〜500 文字（空白だけ 400、500 文字 201、501 文字 400） |
| H09 | 入力検証 | 今日より前の日付への延長は 400（今の期限より後でも） |
| H10 | 時差 | 「今日」は日本時間で判断する（上の時刻に 11-09 は 400、11-10 は 201） |
| H11 | 二重処理 | 判断済みの申請は承認・却下し直せず、状態と期限が変わらない |
| H12 | 同時更新 | 申請の後に期限がもっと先へ変えられていたら、承認しても期限を短くしない |

## テストの強さ（ミューテーション）

- 対象: 初期状態からの差分で、候補が `src/lib/` の `.ts`（テストを除く）に追加・変更した行。ページ・API Route は対象にしない（`@/` の別名を使うため `node:test` から直接読み込めず、どの候補も単体テストで確かめられないため。規約 1 で、ロジックは `src/lib/` に置くことになっている）。
- 壊し方: コードの部分（文字列・コメントの外）の `===`↔`!==`、`<`↔`<=`、`>`↔`>=`、`&&`↔`||`、`true`↔`false`、`.trim()` の削除、`!` の削除、数値 +1。SQL の文字列の中の ` AND `→` OR `、`'pending'`→`'approved'`。重複を除き、60 個を超えるときは全体から等間隔に 60 個を選ぶ（決定的）。
- 検出: 壊した版で候補の作業用コピーの `npm test` が失敗したら検出（壊す前から失敗しているときは、失敗の数が増えたら検出。120 秒の時間切れも検出）。
- 壊しても振る舞いが変わらない版（同値なミューテーション）は除かない。どの候補にも同じ割合で混ざると見なす。
- `src/lib/` に変更が無い試行は 0 点。壊せた数が 10 未満のときはレポートに注記する。

## ブラインドレビュー（15 点）

- 資料: 各試行の差分（`package-lock.json` と、候補のツールが作る管理用の文書（`docs/plans/` など）を除く）。候補名・ツール名は `[redacted]` に置き換え、記号（R01〜）の順番は乱数（種 20261109）で決める。E2E・隠しテストの結果・費用は載せない。
- レビュー担当: 独立したサブエージェント 2 名。互いの結果を見せない。隠しテストの項目一覧は渡さない（「仕様に書かれていないが当然守るべきこと」に気づけているかを、レビュー担当がコードから判断する）。
- 観点（各 0〜3 点、合計 15 点）:
  - a. 規約の遵守（`poc-app/CLAUDE.md` のコーディング規約: ロジックは `src/lib/`、検証関数を通す、プレースホルダ、マイグレーションの追加の仕方、400 / 401 / 404 の使い分け）
  - b. 堅牢さ（仕様に書かれていない入力・状態・権限・時刻の扱いへの配慮が、コードから読み取れるか）
  - c. 設計の分かりやすさと変更範囲の適切さ（責務の分け方、不要な変更・過剰な抽象化が無いか）
  - d. テストの質（振る舞いを確かめているか、境界・異常系を含むか、読みやすいか）
  - e. 保守性（重複・不要なコード・誤解を招く名前やコメントが無いか）
- 2 名の合計の平均を点にする（15 点満点）。同じ観点で 2 点以上ずれたものはレポートに書く。
