## 段階

- **v1（最初の版）**: 候補の手順・依頼者への質問への回答・介入がすべて終わった時点のコミット（`raw/<試行ID>/v1-commit`）。
- **v2（変更後）**: 変更依頼（`docs/poc/tasks/wf-W13-change.md`）の手順・回答・介入が終わった時点（試行の最後のコミット）。
- 採点は v1 のコミットを取り出したアプリと、v2 のアプリの両方で行う。

## アダプター（候補ごとの名前の違いを吸収する）

予約の API（パス・本文の項目名・状態の値）は候補が決めるため、テストはアダプター（JSON）を通して呼ぶ。形は `adapters/reference-v2.json`。

1. `scripts/poc/adapt_w13.py` が、候補が足した・変えたファイル（API Route と予約に関係するもの）を別の `claude -p`（ツールなし）に読ませて下書きを作る（`results/workflow/W13/adapters/<試行ID>-<v1|v2>.draft.json`）。
2. 採点者が下書きとコードを見比べて確かめ、`<試行ID>-<v1|v2>.json` として確定してから採点する。
3. アダプターが指してよいのは「候補の実装が実際に持っている名前・値・API」だけ。候補に無い操作（例: 却下）は書かず、そのテストは不合格になる。状態の対応（例: 候補の `confirmed` を共通名 `approved` に）は、候補のコード・画面の表示名から決める。補正したことと理由は report の「判断の記録」に書く。

テストが使う利用者: 予約する人 suzuki・tanaka、計測器の管理者 kato（テストで作る計測器の既定の管理者）、無効な管理者 inoue（製造部。代表者は yamada、同じ部署の ito）、貸出の操作は sato。予約する人はログイン中の本人（本文に利用者の項目が必要な実装は、アダプターの `{user}` で本人を入れる）。

## 隠しテスト K（最初の依頼の隠れ要件。v1 と v2 の両方で行う）

v2 では、「有効な予約」が要る項目（K05・K08）は管理者の承認まで行う。

| 項目 | 確かめること | Q |
|---|---|---|
| K01 | 過去の日からは予約できず、今日からはできる。終了日が開始日より前は不可 | Q2 |
| K02 | 期間が 1 日でも重なる予約はできない（前の終了日と次の開始日が同じ日も）。隣り合う期間はできる | Q1・Q3 |
| K03 | 取り消した予約は枠を空ける | Q3 |
| K04 | 貸出中は、返却予定日までと重なる予約はできず、翌日からはできる | Q4 |
| K05 | 他人の予約の期間にかかる貸出はしない（返却予定日が予約の開始日でも）。予約の前日までの貸出はできる。予約した本人には予約の期間に貸し出せる | Q5 |
| K06 | 使用停止・廃棄の計測器は予約できない（使用中の対照はできる） | Q6 |
| K07 | 取り消せるのは予約した本人と計測器の管理者で、ほかの人はできない | Q7 |
| K08 | 校正で不合格になり使用停止になったら、これからの予約は取り消しになる | Q8 |

## マイグレーション（本番の DB）

1. `old-db.sql`（version 4。2024〜2026 年のデータ）を SQLite のファイルに戻し、**v1 のアプリ**をその DB で起動する（日本時間 2026-11-10）。v1 のマイグレーションが当たる。
2. v1 のアダプターで予約を入れる（`prod.cjs make`）: A（MI-0001、suzuki、11-20〜11-22）、B（MI-0014、suzuki、12-01〜12-20 の 20 日。v1 で断られたら 12-01〜12-07。当初は MI-0003 だったが、校正期限が 12-03 で、期間中に校正期限が来る予約を断る実装で入れられなかったため試行の途中で変えた）、D（MI-0009、sato、11-16〜11-18）、C（MI-0006、tanaka、11-25〜11-26 を入れて本人が取り消す）。これを「本番の DB」とする。
3. **変更後のアプリ**を同じ DB で 2 回起動する（日本時間 2026-11-15）。

| 項目 | 配点 | 合格の条件 |
|---|---:|---|
| N1 | 3 | v1 の後に新しい番号のマイグレーションを末尾に足し、本番の DB の `user_version` が上がる |
| N2 | 5 | 出荷済みのマイグレーション（v1 のコミットにあったもの。version 1〜4 と v1 で足したもの）の SQL を書き換えていない（v1 で 1〜4 を書き換えた場合も不合格） |
| N3 | 4 | 本番の DB で起動・ログインでき、既存の表（部署・利用者・計測器・貸出・校正記録）が 1 行も変わらず、予約 A・B・D が同じ期間・同じ人のまま一覧にある |
| N4 | 3 | 予約 A・B・D（14 日を超える B を含む）が確定、取り消した C は取消のまま（一覧に出なくてもよい） |
| N5 | 3 | 本番の DB で、A と重なる予約は断り、新しい予約（MI-0010）は仮予約として作れて、管理者 ito が承認すると確定になる |
| N6 | 2 | 2 回目の起動でも壊れず、`user_version` が変わらず、既存の表と予約 A・B・D が残る |

本番の DB に予約を 3 件以上入れられなかった（v1 の予約が動かない）ときは、N3 の予約の部分・N4・N5 は不合格になる。

## 設計の筋（ブラインドレビュー、15 点）

- 資料（`blind_w13.py prepare`）: 各試行の、最初の版までの差分と、変更のステップの差分（v1 → v2）を分けて渡す。コミットメッセージ・文書（.md）を含む（`package-lock.json` とツールの管理用ファイルを除く）。候補名・ツール名・「baseline」は `[redacted]`。記号の順番は乱数（種 20261113）。共通の資料は課題文・変更依頼の文言と、初期状態の `CLAUDE.md`・`docs/operations.md`・`migrations.ts`・`loans.ts`。テストの結果・費用・質問の記録は渡さない。
- レビュー担当: 独立した新しいサブエージェント 2 名。互いの結果を見せず、資料を読む順番を変える（1 人目は記号の昇順、2 人目は降順）。
- 観点（各 0〜3 点、18 点満点）:
  - a. 層の分け方と既存の抽象の再利用（`src/lib/` と API Route の分担、`transaction`・`todayJst`・`isValidDate`・検証関数・既存のテストの書き方）
  - b. 変更の入れ方（承認制を、既存の予約の作り方・状態の持ち方に自然に組み込んだか。場当たりの分岐の継ぎ足しでないか）
  - c. 状態と遷移の扱い（取りうる状態と遷移が一か所で分かり、許されない遷移を拒否するか。期限切れの扱い）
  - d. マイグレーションと既存のデータ（出荷済みのマイグレーションを書き換えず、本番の予約を移す方法が妥当か）
  - e. 古い前提の掃除とテストの更新（古い状態の値・使われなくなったコード・古いテスト・文書を残していないか。変更点をテストに書いたか）
  - f. 仮定の明示と後方互換（依頼者に聞かなかった・決めなかった点をコミットメッセージ・文書に書いたか。既存の API・貸出の振る舞いを壊していないか）
- 2 名の合計の平均 × 15/18 を点にする。同じ観点で 2 点以上ずれたものは report に書く。

## 質問の指標（品質・効率に入れない）

依頼者役の記録（`raw/<試行ID>/po-questions.jsonl`）から、試行ごとに次を数える。

- 質問の数（経路別: `ask-po` / メッセージ。段階別: v1 / v2）。1 回の問い合わせに複数の質問があれば、依頼者役が分けた項目ごとに数える。
- 的中: 回答に Q・C の項目を使った質問の数と割合。引き出した隠れ要件の数（Q の種類・C の種類）。特に C11（本番の予約の扱い）・C2/C3（承認する人）・C6（期限切れ）を聞いたか。
- 聞き直し: 文書に既に書いてあること（D）を聞いた質問の数。
- 実装前: 質問した時点で、その段階の基準（v1 は初期状態、v2 は v1 のコミット）から `src/`・`tests/` に変更が無かった質問の数と割合。
- 依頼者役の費用（候補の費用には含めない）。

## 手戻りの大きさ（効率の補足）

- 変更のステップの費用（`total_cost_usd` − `v1-cost`）・時間（`elapsed-seconds` − `v1-seconds`）・介入の回数。
- 変更の行数（v1 → v2 の `src/`・`tests/` の追加・削除の行数）と、最初の版の行数との比。
