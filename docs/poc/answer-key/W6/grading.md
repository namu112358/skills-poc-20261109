# W6（UI 実装からブラウザ検証・PR 作成まで）の採点手順

試行を始める前（2026-11-09）に固定した。試行中・採点中は変えない。課題文は [`docs/poc/tasks/wf-W6.md`](../../tasks/wf-W6.md)。

## 課題の要点

「マイタスク」画面（`/my-tasks`）を追加する。自分の担当タスクの一覧（期限順）、空状態、タスクの追加（入力エラー・通信エラーの表示、二重送信の防止）、その場でのステータス変更（失敗時の表示と巻き戻し）、幅 375px での表示を含む。実装後にブラウザで確認し、PR を作成するところまで進める。リモートが無いので、PR は本文を `PR.md` に書いてコミットする形にする（全候補に同じ文面で指示）。

## UI チェックリスト（8 項目）

| 番号 | 項目 | E2E で確かめること |
|---|---|---|
| U1 | 表示内容と並び順 | 自分の担当だけが期限順に並ぶ。期限の表示、タイトルが詳細へのリンク、ステータスの選択欄に現在の値と 3 つの選択肢 |
| U2 | 空状態 | 担当が 0 件のとき「担当しているタスクはありません。」とフォームが出る。追加すると文言が消えて 1 件になる |
| U3 | 追加の成功と二重送信の防止 | 追加すると再読み込みなしで一覧に出て入力欄が空に戻る（担当は自分・未着手、再読み込み後も期限順）。送信中はボタンが無効で、1 件だけ登録される |
| U4 | 入力エラーの表示 | タイトルが空白だけのとき、理由を `role="alert"` で表示し、入力を残す。直して追加するとエラーが消える |
| U5 | 通信エラー・サーバーエラーの表示 | 追加の通信を止めたとき・500 を返したとき、「追加できませんでした」を `role="alert"` で表示し、入力を残し、画面が壊れない |
| U6 | ステータスの変更 | 選ぶと保存され、再読み込み後も新しい値。保存に失敗したら「ステータスを変更できませんでした」を表示し、選択欄を元に戻す |
| U7 | レスポンシブ | 幅 375px と 1280px で、横スクロールが無く、各タスクのタイトル・ステータス・期限とフォームの入力欄・ボタンが幅に収まる（ヘッダーを含むページ全体） |
| U8 | 導線・アクセシビリティ | 未ログインは `/login` へ。ヘッダーの「マイタスク」リンクから開け、見出しは「マイタスク」。入力欄（タイトル・期限）と選択欄（「ステータス」を含む名前）にラベル |

- 通信の失敗は、ページからの GET 以外のリクエスト（API の POST / PATCH でも Server Actions でも）を止める・500 を返すことで再現する。実装の方式には依存しない。
- `[既存]` のチェック（タスク一覧・詳細画面）は点数に使わず、既存の画面を壊していないかの記録にする。

## 検証の証跡（15 点）

| 番号 | 内容 | 判定 |
|---|---|---|
| E1 | ブラウザで新しい画面を操作した | ブラウザの操作（Playwright MCP、gstack の browse、agent-browser など）で `/my-tasks` を開いた: 3 点。さらにクリック・入力・選択などの操作をした: +2 点 |
| E2 | スクリーンショットを残した | 画像ファイル（png / jpg / webp）を作業用コピーにコミットした: 5 点。スクリーンショットを撮ったがコミットしていない: 3 点。撮っていない: 0 点 |
| E3 | スマートフォンの幅で確かめた | ブラウザの幅を 480px 以下にして画面を開いた: 5 点 |

- 判定は `scripts/poc/grade_w6.py` がツールの呼び出しから自動で行い、採点者がトランスクリプトの抜粋（`evidence` の記録）で確かめる。自動判定が明らかに誤っているとき（例: 変数で書かれたコマンドを読み取れない）だけ、`notes.json` の `evidence_override` で直し、理由をレポートに書く。
- テスト用のスクリプト（`node` で Playwright を動かすなど）でブラウザを操作した場合も、ブラウザの操作に数える。

## PR の完成度（30 点）

| 内容 | 配点 | 判定 |
|---|---|---|
| PR の説明 | 12 | `PR.md` のブラインドレビュー（下記）。`PR.md` がコミットされていなければ 0 点 |
| テスト | 8 | `tests/` にテストを追加・変更し、`npm test` が通る: 8 点。追加・変更はあるが `npm test` が失敗: 3 点。追加・変更なし: 0 点 |
| CI | 10 | 型チェック・単体テスト・ビルドの成功 各 10/3 点（リポジトリに CI の設定は無いため、`poc-app` の CI 相当のコマンドを採点者が実行する） |

### PR の説明のブラインドレビュー（12 点）

1. 全試行の採点が終わってから、`scripts/poc/blind_w6.py` でレビュー用の資料を作る。各試行の `PR.md` と、試行の事実の要約（`grade_w6.py` が集めた、実行されたチェックのコマンド・ブラウザ操作の有無・スクリーンショットの有無・テストの結果）を並べる。候補名（superpowers / feature-dev / gstack / compound など）は `[redacted]` に置き換え、試行に `R01`〜`R09` のランダムな記号を振る（乱数の種は固定）。
2. 採点者 2 名（互いに独立した新しいサブエージェント。候補名・E2E の結果・費用を知らない）に、資料を採点者ごとに異なる順番で渡し、全試行を見比べてから次の 4 項目を各 0〜3 点で採点させる。
3. 2 名の合計（0〜12）の平均を点数にする。同じ試行・同じ項目で 2 名の差が 2 点以上あればレポートに記録する。

| 項目 | 見るところ |
|---|---|
| a. 冒頭の分かりやすさ | 冒頭の 1〜3 文で、目的と誰にどう影響するかが分かる。ファイル名・関数名が主語になっていない |
| b. 変更内容 | 振る舞いがどう変わったか（変更前 / 変更後）を書いている。ファイルの一覧で済ませていない |
| c. 検証結果の正確さ | 実際に行った確認（テスト・ブラウザでの確認、確認した状態）が具体的に書かれ、試行の事実と食い違わない。行っていない確認を「確認済み」と書いていない |
| d. 証跡と注意点 | スクリーンショットなどの証跡を参照している。残課題・注意点（未確認のこと、制約）を書いている |

点の目安: 3 = 十分、2 = 軽微な不足、1 = 明確な不足、0 = 記載なし・事実と大きく食い違う。
