# W4（既存コードを横断する大きな変更）の採点手順

試行を始める前（2026-11-09）に固定した。試行中・採点中は変えない。課題文は [`docs/poc/tasks/wf-W4.md`](../../tasks/wf-W4.md)（チーム共有機能。タスクの閲覧・編集の権限を「全員」から「個人タスクの作成者／チームのメンバー」に変える）。

| 観点 | 配点 | 測り方 |

## 受け入れテスト（`acceptance.cjs`、26 件）

API 17 件・画面 8 件・既存の動作 1 件。前半は初期データを変えないチェック、後半は自分で作ったタスク・チームだけを使うチェック。参照実装（`reference.patch`）で 26/26 通過し、変更なしの poc-app では既存の動作の 1 件だけが通ることを確認してから試行を始めた。

## 認可プローブ（`authz.cjs`、9 件）

受け入れテストとは別に起動したサーバーで実行する。仕様から導けるが受け入れテストでは直接試していない、攻撃者の視点の入力を試す（所属外のチーム ID を文字列で送る、所属外のチームでの絞り込み（API・画面）、閲覧できないタスクの詳細画面への内容の漏えい、作成者でないメンバーによる別チームへの付け替え、メンバーによる自分の管理者への昇格・管理者の削除、他チームの管理者による操作、外された管理者の操作）。参照実装で 9/9、変更なしの poc-app で 0/9。

## 影響箇所リスト（正解。採点者だけが見る）

変更が必要な箇所。項目ごとに、差分で **正しく** 対応できていれば 1、一部だけ（経路の一部が抜けている・不具合がある）なら 0.5、対応していなければ 0。

## ブラインドレビュー

### 資料の作り方（`scripts/poc/blind_w4.py`）

1. 全試行の `grade.py` が終わってから作る。試行に `R01`〜`R09` のランダムな記号を振る（乱数の種は固定）。対応表は `review/mapping.json` に書き、レビューが終わるまで採点者に渡さない。
2. **コードの資料**（影響箇所・認可のレビュー用）: 差分から `package-lock.json` と候補の管理用ファイル（`docs/plans/` など）を除く。`poc-app/CLAUDE.md` の変更は影響箇所 16 の判定に使うので含める。
3. **設計の資料**（設計案の比較の採点用）: トランスクリプトから、候補（親セッション）が書いた文章、サブエージェントの報告、候補が作った計画書・設計書（`docs/plans/` など）を順に並べる。コードの中身・ツールの生の出力は含めない。長すぎる場合は 1 試行 6 万字で打ち切る。
4. どちらの資料も、候補名・コマンド名（superpowers / feature-dev / gstack / compound / `ce-*` / `/autoplan` など）を `[redacted]` に置き換える。

### 採点者

互いに独立した新しいサブエージェント 2 名（候補名・受け入れテストの結果・費用を知らない）。資料を **採点者ごとに異なる順番** で渡し、全試行を見比べてから点を付けるよう指示する。同じ試行・同じ項目で 2 名の差が大きい（影響箇所は 1 項目で 1 の差、ほかは 3 点以上）ものはレポートに記録する（点数は平均のまま）。

### 認可のコードレビュー（各 0〜5 点）

| 項目 | 見るところ |
|---|---|
| A. 権限確認の一貫性 | 閲覧範囲の絞り込みが一覧・1 件取得・更新・画面のすべての経路で同じ規則になっているか（抜け道・二重定義の食い違いが無いか）。閲覧できない対象を 404 にして存在を漏らさないか。役割の確認がメンバー管理の全操作にあるか |
| B. 入力と境界の扱い | 作成者・所属・役割・ユーザー ID を本文から信用せずに検証しているか（型の違う値を含む）。最後の管理者・所属の変更後の担当者などの境界。SQL のプレースホルダ |

点の目安: 5 = 指摘なし、4 = 軽微な指摘、3 = 実害は小さいが明確な問題が 1 つ、2 = 権限の抜けが 1 つ、1 = 権限の抜けが複数・重大、0 = 権限の確認がほぼ無い。

### 設計案の比較の採点（各 0〜5 点）

| 項目 | 見るところ |
|---|---|
| D1. 比較の有無 | 0 = 設計案の比較が無い（1 案を説明するだけ、または設計の記述が無い）、3 = 1 つの論点で 2 案以上を比べた、5 = 複数の論点（所属・役割のデータの持ち方、認可の確認を置く場所、既存の関数の署名を変えるか、既存データの移行の仕方など）で比べた |
| D2. 選択肢の妥当性 | 比べた案が、このコードベース（SQLite・`src/lib/` に処理を置く規約・既存 API）で現実的な選択肢か |
| D3. トレードオフの具体性 | 長所・短所が、このコードの事実（影響する関数・画面・テスト、権限の抜けの危険）に基づいて書かれているか |
| D4. 決定と理由、実装との一致 | 採用した案と理由が明示され、実装がその案に沿っているか |

D1 が 0 のときは D2・D3 も 0 にする。D4 は、比較が無くても、採用した設計と理由が書かれていれば点を付けてよい。
