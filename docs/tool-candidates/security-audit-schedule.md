# セキュリティ監査の定期実行（案）

コードのセキュリティ監査を、人が思い出したときだけでなく決まった頻度で回すための方針の案です（検討日: 2026-11-11）。
`poc-app` で 3 つのツールを測った結果（[docs/poc/results/security/README.md](../poc/results/security/README.md)）に合わせて、ツールの選び方を見直しました。

## 結論（案）

- **毎日は、LLM を使わない検査に任せる。** CodeQL・Dependabot・Secret Scanning は決まった規則で安く安定して回るため、毎日回す役に向いています。
- **PR ごとに、`/security-review`（Claude Code に最初から入っているコマンド）で差分を監査する。** 1 回 $1 前後・2 分で、差分の中で完結する脆弱性はすべて見つけました。
- **認証・セッション・権限に触れる PR は、Claude Security の差分スキャン（medium）で監査する。** 既存のコードと合わせて初めて分かる脆弱性では、`/security-review` は 3 件中 1〜2 件しか見つけず、Claude Security は 3 件すべてを見つけました（1 回 $2.7 前後・5 分）。
- **週 1 回、前回の監査から変わったところを、Claude Security の差分スキャン（medium）で監査する。** PR を通らずに入った変更も拾うためです。
- **月 1 回、またはリリースの前に、Claude Security（medium）でコード全体を監査する。** 差分だけでは見えない、複数の機能にまたがる問題を拾うためです。`poc-app`（約 1,300 行）で 1 回 $10・24 分でした。
- **Cloudflare Security Audit は、CI・コンテナ・LLM・クラウドの設定を変えたときと、四半期に 1 回だけ使う（quick）。** Web アプリの脆弱性では、見つけた数は Claude Security と同じなのに費用が 2〜4 倍でした。一方、Web アプリ以外の領域では、Claude Security が見落とした LLM を経由した指示の注入を見つけました。対象のコードを隔離して動かせる実行環境を用意したときだけ、指摘を「確認済み」にできます（用意しないと、すべて「要確認」のまま）。前回の記録を引き継いでも、費用は下がりませんでした（[SEC-6](../poc/results/security/README.md)）。
- **前回からコミットがなければ、その回は監査しない。**
- 実行には Claude Code のスケジュール実行を使います（新しいクラウドのセッションを決まった時刻に起動する機能）。
- 監査の記録は、対象とは別の非公開リポジトリに残し、次の回が前回の続きから監査できるようにします。

## 頻度ごとの役割

セキュリティの確認は、手前の段ほど軽く、頻繁に回します。定期監査は、その下の段で漏れたものを拾う役です。

| いつ | 手段 | 見る範囲 | 状態 |
|---|---|---|---|
| ファイルを編集するたび | Security Guidance | 編集中のコードと、その時点の差分 | 採用済み |
| PR ごと | `/security-review` | PR の差分 | 案（PoC の SEC-1〜SEC-3 で比べた） |
| 認証・セッション・権限に触れる PR | Claude Security の差分スキャン（medium） | PR の差分と、それが使う既存のコード | 案（SEC-3） |
| 毎日 | CodeQL・Dependabot・Secret Scanning | リポジトリ全体と依存パッケージ | 予定（標準 §2.6） |
| 週 1 回 | Claude Security の差分スキャン（medium。範囲: 前回の監査からの差分） | 前回から変わったところ | 案 |
| 月 1 回、またはリリース前 | Claude Security（medium。範囲: 全体） | コード全体 | 案 |
| CI・コンテナ・LLM・クラウドの設定を変えたとき、四半期に 1 回 | Cloudflare Security Audit（quick。隔離して動かせる実行環境で） | コード全体と設定 | 案（SEC-6） |

測った費用と時間（モデルは Opus 5.5）:

| ツール | 範囲 | 費用 | 時間 |
|---|---|---:|---:|
| `/security-review` | 差分（数ファイル） | $1.0〜1.2 | 2 分 |
| Claude Security（medium） | 差分（数ファイル） | $2.2〜2.6 | 4〜5 分 |
| Claude Security（medium） | 全体（約 1,300 行） | $10.5 | 24 分 |
| Cloudflare（quick） | 差分（数ファイル） | $9.6 | 20 分 |
| Cloudflare（standard） | 全体（約 1,300 行） | $39.4 | 45 分 |
| Cloudflare（quick・隔離あり） | 全体（約 1,300 行） | $31.3 | 45 分 |
| Cloudflare（quick） | CI・コンテナ・LLM を含む全体 | $12.2 | 25 分 |

Cloudflare をこれより広く使う（週次・月次に戻す）のは、次のどちらかが満たせたときです。
- 隔離して動かせる実行環境を、定期実行の仕組みとして用意できる。
- Web アプリの脆弱性でも、Claude Security が見落とすものを Cloudflare が見つける題材が見つかる。

## 実行の流れ（Claude Code のスケジュール実行）

1. スケジュール実行が、対象のリポジトリで新しいセッションを起動する。プラグイン Claude Security を有効にしておく。
2. 前回の監査の記録から、監査したコミットを読み取る。今のコミットと同じなら、その回は終える。
3. 週次なら前回のコミットからの差分（Claude Security の「Scan changes」）、月次なら全体（「Scan codebase」）を、medium で監査する。
4. 結果（`CLAUDE-SECURITY-<時刻>/`）は、リポジトリの中に書かれる。誤ってコミットしないよう、対象のリポジトリの `.gitignore` に入れておく。
5. 結果を記録用の非公開リポジトリに push し、要約を担当者に知らせる。指摘には、回をまたいでも変わらない ID（`claudeSecurityPluginFindingId`）が付くので、前回からの増減はこの ID で比べる。

### 結果の置き場と扱い

- 脆弱性の詳細は、公開の Issue や PR のコメントに書かない。
- 深刻度が high 以上のものは、GitHub の非公開のセキュリティアドバイザリにして、修正を担当者に割り当てる。
- Claude Security の深刻度は、正解より低く付くことがあった（脆弱性 12 件のうち 3 件。critical を medium にしたものもある）。medium の指摘も、担当者が深刻度を見直す。
- SARIF の出力（`CLAUDE-SECURITY-RESULTS.sarif`）は、GitHub のセキュリティのタブに取り込める。取り込むかどうかは、リポジトリの公開範囲を見て決める。

### この方法の注意点

- **スケジュール実行は、作成した人のアカウントに紐づく。** 担当者が異動・退職すると止まるため、担当者と引き継ぎ方を決めておく。
- **Claude Security は、既定で利用状況を Anthropic に送る。** 止めるときは、セッションの環境変数に `DISABLE_TELEMETRY=1` を設定する。
- 記録用リポジトリへの push のため、セッションから GitHub に接続できる必要がある。

## 進め方

1. **`poc-app` で測る。** 済み（2026-11-11。[結果](../poc/results/security/README.md)）。
2. **頻度と費用の上限を決める。** この文書の案（PR ごと・週次・月次）を、チームで決める。費用の目安は上の表のとおり。対象のコードの規模が `poc-app` より大きいと、費用はそれに応じて増える。
3. **配る雛形に入れる。** 決めた形を、スケジュール実行に渡す指示文と `.gitignore` の行として `templates/` に入れ、各プロジェクトが同じ形で使えるようにする。

## まだ確かめていないこと

- `poc-app` より大きいコード（数万行）での費用と時間
- PR ごとの監査を、人が呼ぶのではなく GitHub Actions で自動で回す手順
- 記録用リポジトリを、プロジェクトごとに分けるか、1 つにまとめるか

## 参考: Cloudflare Security Audit の性質

固定コミット（`cloudflare/security-audit-skill@c1c8a8c`、`scripts/poc-profile.sh` が配置するもの）の `SKILL.md` と README を読んで分かったことです。PoC で動かして確かめた点は、括弧の中に書きました。

- **1 回の全体監査が重い。** 次の 6 段階で進みます。
  1. 構成の調査
  2. 範囲を分けた探索
  3. 指摘の候補の検証
  4. 構造化した出力
  5. 独立した再確認
  6. 報告書の作成

  調査役 4 つ、探索役、漏れを確認する役、候補 1 件ごとの検証役を、別々のエージェントとして動かします。毎日全体を監査すると、費用がかさみます（全体の standard で、エージェントを 61 回起動し $39 かかった）。
- **前回の続きから監査できる。** 前回の網羅の記録（`coverage-ledger.json`）と指摘（`findings.json`）を読み込み、変わったところと前回確認しきれなかったところを優先します。定期実行に向いた作りですが、前回の記録が残っていることが前提です。
- **深さと範囲を選べる。**
  - 深さは `quick`（小さな対象や再実行向け）・`standard`（既定）・`deep`（重要な対象向け）の 3 段階です。
  - 範囲は、パスや、2 つのコミットの間の差分に絞れます。範囲を絞った回は、報告書に「一部だけを監査した」と書かれます。
  - 動かすエージェントの数の上限を、予算として決められます。上限を超えそうなときは、黙って省かずに未完了として記録します。
- **記録は対象のリポジトリの外に書く。** 既定の置き場は `~/security-audit-skill/<リポジトリ名>/run-<番号>` です。クラウドのセッションは終わると消えるため、置き場を別に用意しないと前回の続きから監査できません。
- **稼働中の環境には触れない。** 本番や共有の環境への接続、依存パッケージの追加、課金のある API の呼び出しはしない作りです。対象のコードを動かして確かめるのは、OS の機能で隔離できる場合だけです。隔離できない場合は、コードを読むだけで判断し、確かめきれない点を「要確認」（`needs_validation`）として残します（クラウドのセッションでは隔離できず、指摘はすべて要確認になった。Sonnet 5.5 では、探索役のエージェントが安全機構に止められて動かなかった）。
