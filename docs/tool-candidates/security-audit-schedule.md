# セキュリティ監査の定期実行（案）

コードのセキュリティ監査を、人が思い出したときだけでなく決まった頻度で回すための方針の案です（検討日: 2026-11-11）。
**頻度と費用の上限は、まだ決めていません。** まず `poc-app` で 1 回あたりの費用と時間を測り、その結果で決めます。

## 結論（案）

- **毎日は、LLM を使わない検査に任せる。** CodeQL・Dependabot・Secret Scanning は決まった規則で安く安定して回るため、毎日回す役に向いています。
- **週 1 回、前回の監査から変わったところだけを Cloudflare Security Audit で監査する。**
- **月 1 回、またはリリースの前に、コード全体を監査する。** 差分だけでは見えない、複数の機能にまたがる問題を拾うためです。
- **前回からコミットがなければ、その回は監査しない。**
- 実行には Claude Code のスケジュール実行を使います（新しいクラウドのセッションを決まった時刻に起動する機能）。
- 監査の記録は、対象とは別の非公開リポジトリに残し、次の回が前回の続きから監査できるようにします。

## 頻度ごとの役割

セキュリティの確認は、手前の段ほど軽く、頻繁に回します。定期監査は、その下の段で漏れたものを拾う役です。

| いつ | 手段 | 見る範囲 | 状態 |
|---|---|---|---|
| ファイルを編集するたび | Security Guidance | 編集中のコードと、その時点の差分 | 採用済み |
| PR ごと | `/security-review`（Claude Code に最初から入っているコマンド）、または Claude Security の差分スキャン | PR の差分 | 未定（PoC §5.2 で比べる） |
| 毎日 | CodeQL・Dependabot・Secret Scanning | リポジトリ全体と依存パッケージ | 予定（標準 §2.6） |
| 週 1 回 | Cloudflare Security Audit（範囲: 前回の監査からの差分） | 前回から変わったところと、前回確認しきれなかったところ | この文書の案 |
| 月 1 回、またはリリース前 | Cloudflare Security Audit（範囲: 全体） | コード全体 | この文書の案 |

週次と月次に Cloudflare を使うのは、PoC §5.2 で Cloudflare が Claude Security を下回らなかった場合です。下回った場合は、同じ枠で Claude Security を使います。

## Cloudflare Security Audit の性質（頻度を決める根拠）

固定コミット（`cloudflare/security-audit-skill@c1c8a8c`、`scripts/poc-profile.sh` が配置するもの）の `SKILL.md` と README を読んで分かったことです。まだ動かしてはいません。

- **1 回の全体監査が重い。** 次の 6 段階で進みます。
  1. 構成の調査
  2. 範囲を分けた探索
  3. 指摘の候補の検証
  4. 構造化した出力
  5. 独立した再確認
  6. 報告書の作成

  調査役 4 つ、探索役、漏れを確認する役、候補 1 件ごとの検証役を、別々のエージェントとして動かします。毎日全体を監査すると、費用がかさみます。
- **前回の続きから監査できる。** 前回の網羅の記録（`coverage-ledger.json`）と指摘（`findings.json`）を読み込み、変わったところと前回確認しきれなかったところを優先します。定期実行に向いた作りですが、前回の記録が残っていることが前提です。
- **深さと範囲を選べる。**
  - 深さは `quick`（小さな対象や再実行向け）・`standard`（既定）・`deep`（重要な対象向け）の 3 段階です。
  - 範囲は、パスや、2 つのコミットの間の差分に絞れます。範囲を絞った回は、報告書に「一部だけを監査した」と書かれます。
  - 動かすエージェントの数の上限を、予算として決められます。上限を超えそうなときは、黙って省かずに未完了として記録します。
- **記録は対象のリポジトリの外に書く。** 既定の置き場は `~/security-audit-skill/<リポジトリ名>/run-<番号>` です。クラウドのセッションは終わると消えるため、置き場を別に用意しないと前回の続きから監査できません。
- **稼働中の環境には触れない。** 本番や共有の環境への接続、依存パッケージの追加、課金のある API の呼び出しはしない作りです。対象のコードを動かして確かめるのは、OS の機能で隔離できる場合だけです。隔離できない場合は、コードを読むだけで判断し、確かめきれない点を「要確認」（`needs_validation`）として残します。

## 実行の流れ（Claude Code のスケジュール実行）

1. スケジュール実行が、対象のリポジトリで新しいセッションを起動する。
2. セッションが、Skill を固定コミットから配置する（`scripts/poc-profile.sh sec-cloudflare` と同じ方法）。
3. 記録用の非公開リポジトリを、対象とは別のディレクトリに clone する。
4. 前回の記録から、監査したコミットを読み取る。今のコミットと同じなら、その回は終える。
5. 週次なら前回のコミットからの差分、月次なら全体を範囲にして監査する。記録用リポジトリの `<対象リポジトリ名>/run-<番号>` を出力先にする。
6. 記録を記録用リポジトリに push し、結果の要約を担当者に知らせる。

### 結果の置き場と扱い

- 脆弱性の詳細は、公開の Issue や PR のコメントに書かない。
- 確認済み（`confirmed`）で深刻度が high 以上のものは、GitHub の非公開のセキュリティアドバイザリにして、修正を担当者に割り当てる。
- 要確認（`needs_validation`）は、記録用リポジトリに残し、次の回で確かめ直す。

### この方法の注意点

- **スケジュール実行は、作成した人のアカウントに紐づく。** 担当者が異動・退職すると止まるため、担当者と引き継ぎ方を決めておく。
- **クラウドのセッションで、対象のコードを隔離して動かせるかは確かめていない。** 動かせない場合は、コードを読むだけの監査になり、要確認が増える可能性がある。
- 記録用リポジトリへの push と Skill の取得のため、セッションから GitHub に接続できる必要がある。

## 進め方

1. **`poc-app` で測る。** PoC §5.2 の試行（脆弱性を仕込んだ `poc-app` のスナップショット）と同じ時期に、次の 3 つを 1 回ずつ回す。
   - 全体を `quick`
   - 全体を `standard`
   - 脆弱性を 3 件含む差分を `quick`

   記録するもの:
   - 動いたエージェントの数、費用、所要時間
   - 確認済み・要確認・却下の件数
   - 正解リストとの照合の結果（見つけた数、誤検知の数）
2. **頻度と費用の上限を決める。** 測った費用から、週次の深さ（`quick` か `standard`）、月次の深さ、1 回あたりのエージェント数の上限を決め、この文書を更新する。
3. **配る雛形に入れる。** 決めた形を、スケジュール実行に渡す指示文と記録用リポジトリの作り方として `templates/` に入れ、各プロジェクトが同じ形で使えるようにする。

## まだ確かめていないこと

- 1 回あたりの費用・時間と、誤検知の多さ（進め方の 1 で測る）
- クラウドのセッションで、対象のコードを隔離して動かせるか
- 記録用リポジトリを、プロジェクトごとに分けるか、1 つにまとめるか
