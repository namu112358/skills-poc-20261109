# Issue・PR の書き方（AI エージェント・人間共通）

このルールは Claude Code・GitHub Copilot・Codex など、どのエージェントにも同じものを読ませる前提で書いています。
各ツール固有の設定ファイル（`CLAUDE.md`、`AGENTS.md`、`.github/copilot-instructions.md`）からはこのファイルを参照するだけにして、内容を複製しないでください。

リポジトリのルールファイル（`AGENTS.md` など）にこの文書と異なる指示がある場合は、そちらに従ってください（例: 「PR 本文は人間が書く」と定めているリポジトリでは、本文を書かずに下書きを提示する）。

## 1. 最優先: 人間が読んで分かること

- 冒頭は **利用者・業務・システムの振る舞い** を主語にする。ファイル名・関数名・コンポーネント名を主語にしない。
  - 悪い例: 「`approval-service.ts` の `transitionStatus()` を修正し、`useApprovalMutation.ts` のキャッシュ無効化を変更する」
  - 良い例: 「申請が差し戻された際、申請者が内容を修正して再提出できるようにする」
- 技術用語を羅列しない。非エンジニアが「何のための変更で、誰に影響するか」を把握できるようにする。
- 実装の詳細（ファイル・関数・内部処理）は本文の後方に短く置くか、省略する。変更ファイルの一覧はレビュー画面で見えるので書かない。
- 分量は変更の大きさに合わせる。1 行で済む変更に長い説明を付けない。
- エージェントとの会話を見ていない読者に向けて書く。会話の中だけで通じる言葉（「さっきの案」「方針 B」など）を使わない。試して捨てた案や作業の経過は書かず、結論と、判断に必要な理由だけを書く。
- 例外: リファクタリング・技術的負債・基盤更新など、技術自体が目的のものは技術的な記述をしてよい。ただし「なぜ必要か」は平易に書く。

## 2. Issue と PR の役割

| | Issue | Pull Request |
|---|---|---|
| 答える問い | 何を実現するか（What / Why） | 何が変わり、どう検証したか |
| 主な内容 | 背景・課題、目的、期待する動作、受入条件、制約 | 概要、背景・目的、変更内容（変更前 / 変更後）、検証結果、注意事項・残課題、関連 Issue |
| 書かないこと | 実装作業のログ、進捗メモ | 変更ファイル・関数名の一覧、Issue の受入条件の書き写し |

- **受入条件の正本は Issue**。PR や実装計画には複製せず、Issue を参照する。
- 大きな実装計画は Issue 本文に詰め込まず、リポジトリ内の `docs/plans/<issue番号>-<短い名前>.md` に置いて Issue からリンクする。
- 作業中のメモや途中経過は Issue のコメント、または PR に書く。Issue 本文を作業ログにしない。

## 3. Issue の情報の置き方

次の 3 層を意識する。内容が少なければ 1 つの欄にまとめてよい。

1. **人間向けサマリー**: 概要・背景・期待する動作（テンプレートの上の欄）
2. **人間と AI の共通仕様**: 受入条件・制約（チェックリストで、検証可能な書き方に）
3. **AI 向け実装コンテキスト**: 関連コード、参考資料、技術的制約（テンプレート最後の「補足・制約」欄）

## 4. PR の書き方

- **まだマージしてはいけない PR は draft で作る。** 作業の途中、結果や検証を後から追加する予定がある、ほかの PR を先にマージする必要がある、などの場合が当てはまる。PR の内容がそろい、検証結果を本文に書いた時点で Ready（レビュー可能）にする。Ready にしたことを、マージしてよいという承認とはみなさない（マージは人が判断する。自動マージは、リポジトリのルールやユーザーの指示で許されている場合だけ有効にする）。
  - 本文に「追って追加する」「未完了」と書く PR は draft にする。Ready の PR には書かない。
  - 使うツール（Skill・プラグイン）が既定で Ready の PR を作る場合も、このルールを優先する。
- テンプレート（`.github/pull_request_template.md`）の見出しに沿う。該当しない欄は削除してよい。
- 「背景・目的」には、なぜこの変更が必要かを書く。Issue に詳しく書いてあれば 1〜2 文で要約して Issue を参照し、背景を丸ごと書き写さない。
- 「変更内容」は「変更前」と「変更後」を対にして、振る舞いがどう変わったかを書く。変更ファイルの一覧にしない。
- 「検証結果」には実際に行ったことだけを書く。**テストを実施していない場合は「未実施」と書き、理由を添える**。実行していないテストを「確認済み」と書かない。
- 次に当てはまる場合だけ、「設計判断」「DB マイグレーション」「互換性」「ロールバック手順」の見出しを追加する: スキーマ変更、公開 API・設定の非互換変更、認証・権限・課金に関わる変更、本番データに触れる変更。
- 関連 Issue は `Closes #123`（完了させる場合）か `Refs #123`（参照のみ）で書く。
- AI エージェントが作ったコミットや PR では、ツールが付ける帰属表示（コミットの `Co-Authored-By:` の行、PR 本文の末尾の「Generated with ...」など）を消したり書き換えたりせず、そのまま残す。AI が関わった変更を後から見分けられるようにするため。

## 5. CLI / API で作成するとき（重要）

`gh issue create --body` / `gh pr create --body` や REST API で作成すると、Web UI のようなテンプレートの自動適用・必須項目チェックは**行われない**。エージェントは次の手順で本文を組み立てる。

1. 対象リポジトリのテンプレートを読む: `.github/ISSUE_TEMPLATE/*.yml`、`.github/pull_request_template.md`（ルートや `docs/` に置かれている場合もある）。テンプレートがないリポジトリでは、この文書の §2〜§4 の構成で書く。
2. Issue Forms（YAML）の場合は、`body` の各要素の `attributes.label` を `### <label>` 見出しにして本文を作る（Web UI で投稿された Issue と同じ形になる）。`required: true` の欄は必ず埋める。任意欄で書くことがなければ `_No response_` とする。
3. テンプレートの `labels` を `--label` で付ける（存在するラベルのみ）。`title` の接頭辞（例: `[Bug]: `）も付ける。
4. 本文は一時ファイルに書き、`--body-file` で渡す（シェルのエスケープ事故を避ける）。
5. まだマージしてはいけない PR は `--draft` を付けて作る（§4）。完了したら `gh pr ready <番号>` で Ready にする。API では `draft: true` を指定する。

```bash
gh issue create --title "[Feature]: 差し戻された申請を再提出できるようにする" \
  --label enhancement --body-file /tmp/issue.md
gh pr create --title "差し戻された申請を再提出できるようにする" --body-file /tmp/pr.md
# 作業途中の PR
gh pr create --draft --title "差し戻された申請を再提出できるようにする" --body-file /tmp/pr.md
```

## 6. 作成前のセルフチェック

- [ ] 冒頭 1〜3 文だけ読んで、目的と影響が分かるか
- [ ] ファイル名・関数名が冒頭の主語になっていないか
- [ ] 必須欄がすべて埋まっているか（Issue Forms の `required: true` / PR テンプレートの見出し）
- [ ] 検証していないことを検証済みと書いていないか
- [ ] 変更の大きさに対して長すぎないか
- [ ] まだマージしてはいけない PR を Ready で作ろうとしていないか（その場合は draft にする）
