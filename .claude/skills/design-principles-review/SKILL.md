# 設計の原則に照らしたレビュー

このスキルは、コードの変更を「今後も変更しやすいか」という観点でレビューするためのものです。下に原則ごとの中身と、レビューで見る兆候、当てはめすぎの注意を書いています。原則の名前で判断せず、中身に照らして、具体的にどんな害があるかで判断してください。名前だけを挙げた指摘（「SOLID 違反です」など）は、受け取った人が何を直せばよいか分からないので、役に立ちません。

## レビューの進め方

1. **変更の目的をつかむ。** PR の本文・Issue・差分から、何を実現する変更かを 1〜2 文で言えるようにする。目的が分からないと、「作りすぎ」も「足りない」も判断できない。
2. **全体の設計から見る。** 細部より先に、変更がその場所にあるべきか、既存の仕組みと合っているかを見る。設計が違っていれば、細部の指摘は無駄になる。
3. **下の原則に照らして、害のある箇所だけを指摘する。** どの原則も、守ること自体が目的ではない。今の変更で、読みにくさ・変更のしにくさ・不具合の起きやすさといった害が出ているときだけ指摘する。
4. **良い点も 1 つ以上書く。** 何を続けてほしいかを伝えると、次の変更の質が上がる。
5. **指摘に重さを付けて、下の形式で返す。**

完璧なコードを求めない。変更がコードベース全体の状態を良くしていれば、細かい改善の余地があっても承認してよい。

## 原則と、レビューで見る兆候

### KISS（単純にしておく）

**中身**: 同じ要件を満たすなら、仕組みの少ない、読んで分かる方を選ぶ。複雑さは、それが解決する問題があるときだけ持ち込む。

**兆候**:
- 1 か所でしか使わない抽象（インターフェース、ファクトリ、汎用の設定機構）がある。
- 要件にない柔軟さ（設定で切り替えられる、プラグインで差し替えられる）を作っている。
- 短く書けるのに、技巧的な書き方（入れ子の三項演算子、凝った型の操作）をしている。

**当てはめすぎの注意**: 本当に必要な複雑さ（並行処理、エラー処理、セキュリティの確認）を「単純でない」として削らせない。

### YAGNI（それはきっと必要にならない）

**中身**: 「いつか必要になる」と予想した機能は、実際に必要になるまで作らない。予想した機能を先に作ると、次の 3 つの損をする。
- 作る費用
- 本当に必要なことに手を回せなかった遅れ
- 使われないコードを抱え続ける費用（読む人が増え、変更のたびに合わせる必要が出る）

予想が当たっていても、そのときに分かっている要件で作る方が安く済むことが多い。

**兆候**:
- 要件にない引数・オプション・設定項目・拡張点がある。
- 「将来のため」とコメントされたコードや、呼ばれていない関数がある。
- 今は 1 種類しかないものを、何種類にも対応できる形で作っている。

**当てはめすぎの注意**: YAGNI が止めるのは「予想した機能」を作ることであって、コードを変更しやすく保つこと（名前の整理、関数の分割、テスト）ではない。後者を YAGNI で止めない。

### DRY（同じ知識を 2 か所に書かない）

**中身**: 同じ「知識」（業務の決まり、計算の仕方、値の意味）は、1 か所にだけ書く。2 か所にあると、片方だけが直されて食い違う。DRY は「見た目が似たコードをまとめる」ことではない。

**兆候**:
- 同じ業務の決まり（税率、上限値、状態の遷移）が複数の場所に書かれている。
- 同じ検証が、画面と API とで別々に実装されている。

**当てはめすぎの注意**:
- 見た目が同じでも、変わる理由が違うコードはまとめない。
  - 例: たまたま同じ形の 2 つの画面の入力チェック。
  - まとめると、片方の変更がもう片方を壊す。
- まとめるのは、3 回目に同じものが出てきて、共通の形がはっきりしてからでよい（3 回目の法則）。
- 間違った共通化は、重複より高くつく。共通化した関数に、呼ぶ側ごとの条件分岐が増えていたら、共通化をやめて元に戻すことを勧める。

### SOLID

5 つの原則の頭文字です。それぞれ、変更のしやすさを保つための別々の考え方です。

#### 単一責任の原則（S）

**中身**: 1 つのモジュール（クラス・関数・ファイル）が変わる理由は、1 つにする。「理由」とは、変更を求める人や役割のこと。
- 例: 経理の都合で変わる計算と、画面の都合で変わる表示は、別のモジュールにする。
- 同じ場所にあると、片方の都合での変更が、もう片方を壊す。

**兆候**:
- 1 つのクラスや関数が、DB への保存・業務の計算・表示の整形・通知の送信などを一緒に行っている。
- 名前に「と」「and」「Manager」「Util」が入っていて、何をするものか一言で言えない。
- 1 つの変更依頼で、関係のなさそうな部分まで同じファイルを触っている。

**当てはめすぎの注意**: 小さな関数やクラスに細かく分けすぎて、1 つの処理を追うのに多くのファイルを開く必要が出るなら、分けすぎ。

#### 開放閉鎖の原則（O）

**中身**: よく増える種類のもの（支払い方法、通知の手段など）は、既存のコードを書き換えずに、新しいコードを足すだけで増やせる形にする。

**兆候**:
- 種類を 1 つ増やすたびに、複数の場所の `if` や `switch` に分岐を足している。
- 同じ種類の分岐（`type === 'A'` など）が、あちこちに散らばっている。

**当てはめすぎの注意**: まだ 1〜2 種類しかなく、増える予定もないものに、差し替えの仕組みを作らない（YAGNI）。分岐が 1 か所にまとまっているなら、それで十分なことが多い。

#### リスコフの置換原則（L）

**中身**: 親の型の代わりに子の型を渡しても、呼ぶ側が期待する振る舞いが壊れないようにする。
- 子の型は、親の約束を守る。
- 子の型は、受け付ける入力を狭めず、返す結果の保証を弱めない。

**兆候**:
- 子のクラスで、親のメソッドを「何もしない」「例外を投げる」形に上書きしている。
- 呼ぶ側が、`instanceof` で子の型を調べて処理を変えている。

**当てはめすぎの注意**: 継承を使っていない、あるいは型の差し替えが起きない場所に、この原則を持ち込まない。

#### インターフェース分離の原則（I）

**中身**: 使う側が必要としないメソッドに、依存させない。大きなインターフェースは、使う側の目的ごとに分ける。

**兆候**:
- インターフェースを実装する側が、多くのメソッドを空のまま、あるいは「未対応」の例外のままにしている。
- 一部の機能しか使わないのに、巨大なオブジェクトを丸ごと受け取っている。

**当てはめすぎの注意**: メソッドが 1〜2 個のインターフェースを、さらに分けさせない。

#### 依存性逆転の原則（D）

**中身**: 業務の中心となる処理は、DB・外部 API・画面の部品などの具体的な仕組みに直接依存させない。中心の処理が必要とする形の抽象（インターフェースや関数の型）を、中心の側で決め、具体的な仕組みがそれに合わせる。そうすると、外側を差し替えても中心は変わらず、テストもしやすい。

**兆候**:
- 業務の計算の中で、DB の接続や HTTP の呼び出しを直接作っている。
- テストするために、外部のサービスを立ち上げる必要がある。

**当てはめすぎの注意**: すべての依存に抽象を挟む必要はない。差し替える予定がなく、テストでも困らない依存（標準ライブラリなど）は、そのまま使ってよい。

### 関心の分離（高い凝集、低い結合）

**中身**: 一緒に変わるものは近くに置き（凝集）、別々に変わるものは互いに知らないようにする（結合を弱める）。

**兆候**:
- 画面の部品の中に、データの取得や業務の判断が書かれている。
- あるモジュールの内部の形（フィールド名・内部のデータ構造）に、別のモジュールが依存している。
- 依存の向きが層の決まりに逆らっている（例: 業務の層が画面の層を import している）。

### デメテルの法則（直接の知り合いとだけ話す）

**中身**: あるメソッドが呼んでよいのは、次の相手のメソッドだけにする。
- 自分自身
- 引数で受け取ったもの
- 自分で作ったもの
- 自分が持っているもの

相手の中をたどって、その先のオブジェクトを操作しない。たどると、途中の構造が変わったときに壊れるため。

**兆候**:
- `order.getCustomer().getAddress().getCity()` のように、中を深くたどっている。
- 相手の中身を取り出して、こちらで判断している。相手に判断させる（「聞かずに頼む」）方がよい。

**当てはめすぎの注意**: ただのデータの入れ物（DTO や設定の値）や、流れるようにつなげる API（`builder.a().b()`、配列の `map().filter()`）は対象外。

### 継承より合成

**中身**: 振る舞いを使い回すときは、継承より、部品を持たせる（合成）方を先に考える。継承は親と子を強く結び付けるので、親の変更が子を壊しやすい。

**兆候**:
- コードを使い回すためだけに継承している（「A は B の一種」と言えない）。
- 継承の階層が深い（3 段以上）。
- 子のクラスが、親の一部の機能を無効にしている。

### 早く失敗する、不正な状態を作れなくする

**中身**: 誤りは、起きた場所の近くで、すぐに分かる形で止める。
- 外から来た値（入力・API の応答・設定）は、受け取った境界で検証する。
- 内側では、正しいと分かっている値だけを扱う。
- 型で取りうる値を絞れるなら、絞る。例: 状態は文字列ではなく列挙型にし、ありえない組み合わせを型で表せなくする。

**兆候**:
- エラーを握りつぶしている（空の `catch`、エラーを無視して既定値を返す）。
- `null` や不正な値を、深いところまで受け渡してから落ちる。
- 状態を複数のフラグで持ち、ありえない組み合わせが作れる。

### 驚き最小の原則（読む人を驚かせない）

**中身**: 名前・引数・振る舞いは、読む人が予想するとおりにする。

**兆候**:
- `get` で始まる関数が、データを書き換える、あるいは外部を呼ぶ。
- 同じ種類のものに、場所によって違う名前が付いている。
- 引数の順番や意味が、似た関数どうしで違う。
- コメントが「何をしているか」の繰り返しになっていて、「なぜそうするか」が書かれていない。

### テスト駆動開発（TDD）とテストの書き方

**TDD の中身**:
1. 作る振る舞いを、テストの一覧として書き出す。
2. 1 つ選んで、失敗するテストを書く。
3. それを通す最小限のコードを書く。
4. テストが通る状態のまま、重複を除き、構造を整える（リファクタリング）。
5. 次のテストに進む。

失敗するテストを先に書くことで、テストが本当に失敗を検出できると確かめられる。また、必要な分だけを作ることになり、作りすぎを防げる。

**レビューで見ること**: レビューでは、TDD の手順を踏んだかどうかではなく、出来上がったテストが次を満たしているかを見る。
- 変更した振る舞い（受入条件）ごとに、テストがある。不具合の修正なら、その不具合を再現するテストがある。
- テストが、公開された入口を通して、呼んだ後の状態や結果を確かめている。内部の関数の呼び出し順や回数を確かめていない。
  - 内部の実装を直しただけで落ちるテストは、変更の妨げになる。
- 1 つのテストで 1 つの振る舞いを確かめ、テストの名前にその振る舞いが書いてある。
- 時刻・乱数・外部のサービスに依存していない（固定する、偽物に差し替える）。
- 画面全体の文字やスナップショットを、まとめて比べていない。受入条件に関わる箇所だけを確かめている。
- テストの削除・`skip`・アサーションの緩和がない。ある場合は、理由が書いてある。

**当てはめすぎの注意**: 構造や書き方の決まりは、テストより Lint や型で守る方が速く安定している。決まりを守らせるテストが足されていたら、Lint や型で書けないかを提案する。

### 変更の分け方（構造の変更と、振る舞いの変更を分ける）

**中身**:
- 構造の変更（名前の変更、関数の切り出し、移動）と、振る舞いの変更（機能の追加・修正）は、別のコミットか別の PR にする。
- 振る舞いを変えやすくするために、先に構造を整え、それから振る舞いを変える。
- 混ざっていると、レビューする人がどこで振る舞いが変わったかを見分けられない。

**兆候**:
- 機能の追加と大きな名前の変更・移動が、同じコミットに混ざっている。
- 依頼された範囲の外の書き換え（ついでの整形・リファクタリング）が多く、差分の大半を占めている。

**当てはめすぎの注意**: 触った箇所の小さな整理（読みにくい名前を 1 つ直す、など）は、混ざっていても問題にしない。

## 指摘の重さ

| 重さ | 意味 | 例 |
|---|---|---|
| 必須 | 直さないとマージできない。不具合、データの破損、セキュリティ、受入条件の未達、今後の変更を大きく妨げる設計 | 業務の決まりが 2 か所にあり、すでに値が食い違っている |
| 推奨 | 直した方がよいが、この PR で直さなくてもよい。理由と、後で直す場合の扱いを書く | 1 か所でしか使わない抽象がある |
| 細かい点 | 好みに近い。直さなくてもマージしてよい | 名前の言い回し |

迷ったときは、軽い方にする。重さを上げすぎると、本当に大事な指摘が埋もれる。

## 出力の形式

次の形で返す。

```markdown
## レビューの要約

<変更の目的を 1〜2 文で。全体として承認できるか（承認 / 修正を求める）と、その理由を 1〜2 文で>

## 良い点

- <続けてほしいこと>

## 指摘

### 1. [必須|推奨|細かい点] <何が問題かを 1 行で>

- 場所: `<ファイル>:<行>`
- 何が起きるか: <この書き方のままだと、どんな害があるか。具体的に>
- 判断の根拠: <どの考え方に照らしたか。原則の名前だけでなく、その中身を 1 文で>
- 提案: <どう直すか。必要なら短いコード例>
```

指摘がなければ「指摘」の節に「なし」と書き、なぜ問題がないと判断したかを 1〜2 文で書く。原則を当てはめた結果として変更を勧めない場合（例: 共通化しない方がよい）も、その判断を書く。

## このスキルで扱わないこと

- **書式の細部**: インデントや import の順番のように、フォーマッターと Lint が直すものは指摘しない。
- **不具合の網羅的な探索**: 実際に動かして不具合を探すことや、セキュリティ診断は主目的ではない。設計を見る中で見つけた不具合は、「必須」として指摘する。網羅的に探す場合は、そのための道具と併用する。
